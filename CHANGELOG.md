# Changelog

All notable changes to Aperio are documented in this file. The format is
based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the
project follows semantic versioning per release tag.

## [Unreleased]

### Security

- **A `forward` verdict was cached against the credential alone, so one path's "yes" admitted every other path.** The endpoint is told the method and the path of the request it is being asked about, and answering on them is the ordinary way this pattern is used: `/reports` yes, `/admin` no. The cache key was the endpoint, the hostname and the credential headers, and nothing else, so within the `cache:` window a visitor admitted for one path was admitted for all of them, and a per-request authorization had quietly become a per-session one. The key is now a hash of everything the subrequest carries, method and path included. A cache may only key on less than its answer depends on if it is willing to be wrong.

  **The visitor's address is part of that key as well**, which it was not when the rest of the subrequest became part of it. The address crosses to the endpoint as `X-Forwarded-For`, and allowlisting source addresses is one of the commonest things this method is put in front of, so a key that left it out remembered the admission given to an allowed address and handed it to every other address asking the same question, without the endpoint being asked again. It was the easiest part to miss, because it is the one thing on the subrequest that is not a header the operator named.

- **A token that may not control the visitor gate was told its gate was accepted, and then had it dropped.** Declaring a gate needs the same token permission as `public`. The handshake announced the methods this build accepts without consulting the token, so a client whose token lacked the permission negotiated successfully and went on serving, believing the `auth:` in its own config was in force; the server then discarded the policy when the Ping arrived, and on a server with no `auth:` of its own the route came up reachable by anyone. The only trace was a server-side log line, and for the policy form there was not even that. The announcement now describes the connection rather than the build: a token that may not declare a gate is told so on the handshake and holds the service back, which is what the negotiation does everywhere else, and the drop says why in the log when it still happens.

- **A client's `auth:` gate could still be lost silently against an older server.** The handshake negotiation exists so a gate a server cannot understand holds the service back rather than being ignored into an open route, and it checked the method *names* against what the server announced. That misses the shape: `basic` is a method every server has always understood, but two credentials under it can only travel in the field a server too old to announce anything does not read. Such a server saw no gate, and the route came up open while the client's config and logs said it was closed. It is the case that looks safest, since nothing in the policy is exotic. A policy the old scalar field cannot carry is now refused against a server that announced nothing, with a message saying the server is too old for a gate of that shape rather than naming a method it does support.

- **A gated WebSocket handed the gate's own credential to the backend.** What opens Aperio's visitor gate is Aperio's, and the HTTP path takes it back off the request before forwarding: the `Authorization` header once it has been consumed, and the `aperio_token=` query parameter, on the same rule that strips the session cookie. The upgrade path did neither. It matters most in the form a browser has to use, since a `WebSocket` cannot carry a header: a socket opened as `wss://site/ws?aperio_token=<secret>` arrived at the backend with the parameter still on it, in the request line that most servers write to an access log. That secret is shared by every visitor of the route and opens every `bearer`-gated route on the hostname. Both forms are stripped now, and so are the `x-aperio-` namespace and the `__Host-` spelling of the session cookie, which the upgrade path had also been passing on. The two paths now filter through one piece of code rather than two that agree by hand.

- **A visitor could forge the identity header a `forward` endpoint delivers.** The `response_headers:` list is how that method hands an identity to the backend, and the operator names those headers precisely so the backend can trust what is in them. A visitor's own copy of one of those names was never stripped: it travelled with the request and arrived alongside the endpoint's authentic value, the visitor's copy first. Two headers of one name is not a contradiction a backend is obliged to notice, and the common frameworks read the first, so `X-Auth-User: admin` sent by anyone who could pass the gate at all was the identity the application saw. Any name on the list was forgeable this way. A visitor's copy is now dropped before the request is forwarded, whether or not the endpoint answered with one, which is the rule the `x-aperio-` namespace already had.

- **A `forward` endpoint was told the address the visitor claimed rather than the one the server decided on.** The gate read `X-Forwarded-For` straight off the request to fill in the address it sends the endpoint, without the `trust_proxy` and `trusted_proxies` rules every other consumer of a caller's address goes through, and with no fallback to the socket's own peer. On a server that is itself the edge, which is the default, a visitor writing `X-Forwarded-For: 10.0.0.5` was described to the endpoint as calling from that address, so an endpoint allowlisting internal ranges, the standard `auth_request` shape, admitted them. The same gap in reverse: a visitor sending no such header reached the endpoint with no address at all, so its address rules never fired for legitimate traffic either. The gate is now handed the address the server already resolved for rate limiting and the access log, which is a real one for every request.

- **A webhook receiver could redirect the server past the outbound policy.** The policy is checked against the URL that was stored, at the moment of delivery, which is what lets a fence added later cover webhooks created before it. The delivery then followed redirects, so the destination the policy vetted was not necessarily the destination that received the request: a receiver that passed the fence could answer `302` and aim the server at the cloud metadata service, at something on the loopback, at anything `APERIO_OUTBOUND_BLOCK_PRIVATE` and `APERIO_OUTBOUND_ALLOWLIST` exist to refuse, and the delivery log then reported how that internal address answered. Autoscaling hooks had never followed redirects, for exactly this reason; webhook delivery had simply not been given the same treatment. It has now, and so has the key-set fetch a `jwt` visitor-auth method makes, which had the same shape. A redirect is reported as the status it is, which is also what tells an operator that their receiver has moved.

- **The OIDC calls were the last outbound destinations outside the fence.** The webhook, autoscaling, key-set and `forward` paths all check their destination against `APERIO_OUTBOUND_ALLOWLIST` / `APERIO_OUTBOUND_BLOCK_PRIVATE`, refuse redirects and bound what they read back. The OIDC calls did none of the three, although they are the same shape and then some: the discovery URL is configured (or comes from an organization's stored settings), and the token and userinfo endpoints are read out of the document that URL serves, so they are chosen by something outside the deployment entirely. An issuer that answered a `302`, or a discovery document naming an internal address, sent the server there with the client secret on the request. All three now go through the policy, follow no redirects, and read a bounded answer. The endpoints are checked at each login rather than once when the runtime was built, so a fence tightened later covers a runtime that is already cached.

- **The visitor password was a full dashboard admin credential.** `server.auth` (`APERIO_SERVER_AUTH`) is documented as a login form in front of proxied traffic, and it is the value an operator hands to whoever should be able to see the *site*. The session it created had no host scope, because the gate it belongs to is server-wide, and "no host scope" was read everywhere as "a full session": the dashboard, its API, every settings change, every token. So anybody given the password to look at a staging site could open Aperio itself as an admin, and nothing anywhere said so. Sessions now record **which plane** they belong to, administering Aperio or viewing a site behind it, and the dashboard requires the first. The master token, a named dashboard user, a passkey and OIDC create admin sessions exactly as before; the server's visitor password and a client's own `auth:` create visitor ones.

  **The scope of a session and the plane it belongs to are different questions**, and answering only the first is what caused this, so the fix does not conflate them either: a visitor session still reaches every proxied hostname, because the gate is server-wide and a visitor who signed in on one hostname should not be asked again on the next. Only Aperio itself is closed to it. Sessions that predate this field read as visitor sessions, which signs out the admin sessions live at the moment of the upgrade; that is what a privilege fix should do, and they last a day anyway. If you were signing in to the dashboard with the visitor password, use the master token (`aperio:<token>`) or a named user.

- **A dashboard session from one organization walked past the visitor gate on every other organization's sites.** The dashboard and the visitor gate share one session store, and the gate asked it only one question: is this a global session. That is the right question for the dashboard and the wrong one for a proxied request. A session fixed to a tenant, a per-organization SSO login or a named user of a child org, satisfied it, so its holder could open **any** gated hostname on the server, including ones served for other tenants and for master. A read-only Viewer of one organization could browse another organization's private site, and the credential for it was an ordinary sign-in to their own dashboard. The visitor path now asks the organization as well, with the same rule maintenance flags and share links already use: the hostname must be covered by the organization's fence *and* not currently served by another organization's client, because coverage alone is not ownership (the master token is never fenced, so a master client can be serving a name inside a tenant's fence). A request that names no hostname at all is refused for a fenced session, since that is the same hole wearing a missing header. Master sessions are unfenced here as they are everywhere else, so an operator's own dashboard login reaches their own sites exactly as before.

  **The same fence now covers a gate a client declares for itself**, which it did not when the entry above was written. Two branches run *before* the server's own gate, a client's `auth:` policy and a client's per-service visitor password, and both kept asking the old question. It is the wrong one there for the same reason and with the same consequence, and those are the routes most likely to be gated at all, since gating a service where it is served is the ordinary way to do it. A session scoped to exactly the hostname being requested is unaffected, which is the kind the per-service login issues: it was created by the gate on that name and reaches nothing else.

- **Releases are now signed, carry their provenance, and ship an SBOM, so "I downloaded a binary from the internet" is something you can check rather than something you trust.** Every release gets a `SHA256SUMS` manifest covering all of its assets, signed with Sigstore keyless signing (no long-lived private key exists to be stolen), and the archives, the manifest and the published container images carry [build provenance attestations](https://docs.github.com/actions/security-guides/using-artifact-attestations) naming the workflow, the commit and the runner that produced them: `gh attestation verify <file> --repo co3moz/aperio`. An SPDX SBOM (`aperio.spdx.json`) is attached as well, so anyone asking "are we affected by CVE-X" can answer it themselves instead of reading our lockfile. The exact verification commands are in the new [SECURITY.md](SECURITY.md).

- **Taking a topic away from a token left the clients already connected under it still receiving that topic.** `PUT /aperio/api/tokens/{id}` narrowed `topics` in the store, and the permissions a tunnel connection enforces are a snapshot taken at the handshake, so nothing re-read it: only `revoke` dropped live connections. A subscription is the one messaging capability the server goes on holding *for* a client between requests, a bind is checked when it is declared and a publish when it is made, so narrowing either is felt at the next attempt, while a subscription once admitted keeps delivering on its own. The edit therefore did not take effect until the client happened to reconnect, which for a tunnel client is measured in weeks, and the dashboard reported it as applied. The connections under the edited token now have their cached grant refreshed in place and every subscription the new list no longer covers withdrawn at once, reported to the client as the same refusal it logs by name for a filter it never got. The connection is not dropped: it is serving its routes under a grant that is still valid, and only one thing changed.

- **A QoS 1 redelivery picked its target by an identifier the client chooses, without checking the organization.** The initial fan-out of a message is fenced on the organization and always was. The retry path was not: unacknowledged messages were queued under the subscribing *process* alone, and the process is the `x-aperio-instance` handshake header, which the client writes and nothing validates. Two tenants announcing the same instance id therefore shared one queue, and the resend handed it to whichever of them the client map yielded first, which is HashMap order. A wrong target did not even need a matching subscription, because a resend writes the already-serialized frame straight to the socket, and an acknowledgement from the wrong tenant cleared the other's queue. Exploiting it meant guessing a v4 UUID, which is what a client announces by default, so this is a missing check rather than an open door, but it was the one place in the messaging path where the boundary was not enforced. Queues are now keyed by organization *and* process, the resend re-checks the organization when it picks a connection, and an acknowledgement can only clear its own tenant's queue. Server events are unaffected either way: they are published at QoS 0 and never enter this path.

- **A token granted `#` silently carried the server's own event namespace.** The messaging permission has two halves and they disagreed. Delivery refuses to let a leading wildcard match a `$aperio/` topic, the way MQTT keeps `#` away from `$SYS`, so a client debugging with `#` was never enrolled in infrastructure events. The *grant* check had no such rule: `covers("#", "$aperio/#")` returned true at the first level, so a token holding `#` (or `*`, which is minted as `#`) could ask for the reserved namespace by name and get it. "All topics" is what an operator writes meaning "our own messages", and it was also handing over every client connecting with its address, every token minted, every tunnel and share link created, and every hostname put into maintenance, for the whole organization. The grant half now mirrors the delivery half: `$aperio/` is covered only by a filter that names it, and a subscription refused for this reason says exactly that and which filter to add, rather than reading as a token that lost a permission it thought it had.

  **This changes what an existing token may do.** A token that today subscribes to `$aperio/...` on the strength of a `#` or `*` grant stops receiving those events after the upgrade and logs the refusal by name on every reconnect; give it the namespace explicitly (`topics: ["#", "$aperio/client/#"]`) to restore it. The master token is unaffected, it is unrestricted everywhere, and so is any token that already named the namespace. Nothing else about the grant changes, and no configuration file is involved: `topics` lives on the token, in the store and the API, not in `aperio-server.yaml`.

### Fixed

- **Revoking an admin key on a full disk answered "not found" while the key went on working.** The rollback that keeps memory and disk in step reached every store, but the distinction between "no such record" and "the write failed" only reached the token store, so the smaller ones still returned one value for both and their endpoints answered `404`. That is the worse way round than it sounds: on a `DELETE`, a 404 reads as *already gone*, which is precisely what somebody pulling a compromised credential wants to hear, so the one answer that must never be guessed was the one the conflation produced. The key kept authenticating, and nothing prompted a retry. `DELETE /aperio/api/admin-keys/{id}` and `DELETE /aperio/api/webhooks/{id}` now answer `500` when the change could not be saved, as the token endpoints already did, and `DELETE /aperio/api/inbox` does the same rather than reporting `{"status": "ok", "removed": 0}`, which was indistinguishable from an inbox that was already empty while every entry was still there. The two answers now come from one type shared by the stores, since the reason this was missed twice is that each store had written its own.

- **A client's `auth:` naming more than one user gated its route against everyone, including the users it named.** A `basic` method with two or more credentials has no scalar spelling, and the login form looked up the route's credential only in that scalar form, so it found nothing and compared the submitted `user:password` against the server's own gate instead. The gate had already sent the visitor to that form, so a route written as `auth: {method: basic, users: ["alice:one", "bob:two"]}` came up closed to alice and bob alike, looping back to the login on every attempt. It failed closed, which is the right direction to fail, but the gate could not be opened by anyone it was written for. The form now asks the declared policy the same way it asks the server's own, so a method naming several users admits any of them, and the session it creates is scoped to that client's hostname exactly as the single-credential form always was.

- **The server's outbound callbacks can go through a proxy, and the outbound policy now says what it still covers when they do.** `outbound.proxy` (`APERIO_OUTBOUND_PROXY`) sends webhook deliveries, autoscaling hooks, JWKS fetches, `forward` auth and the OIDC calls through an HTTP proxy, and `outbound.no_proxy` (`APERIO_OUTBOUND_NO_PROXY`) lists the destinations that skip it, which is the ordinary shape: an auth endpoint or issuer inside your network and receivers outside it. Loopback is always direct. **The ambient `HTTP_PROXY`, `HTTPS_PROXY` and `ALL_PROXY` are no longer read by anything**, which is the point rather than a side effect: the HTTP client used to read them, so a deployment could be proxying its callbacks with nothing in its configuration saying so, and the policy had no way to know. A server that still has them set is told at startup that they do nothing and what to set instead.

  **What a proxy costs the policy is now stated instead of being silently true.** Half of the policy reads the URL as text, a literal address or a hostname pattern, and is unaffected. The other half resolves the destination here and looks at the addresses, and through a proxy the name is resolved on the proxy's network, so that half is not run rather than run on an answer that does not apply: `block_private` covers addresses written as addresses, and CIDR allowlist entries cannot admit a named destination. One startup line says so, naming the setting and counting the entries it cannot honor. Destinations on `outbound.no_proxy` are dialed by the server itself and keep the **whole** policy, which is why the bypass list is part of this and not a convenience. This replaces the startup refusal from earlier in this cycle, which never appeared in a release.

- **An outbound callback policy did half its job on a server with a proxy in its environment, and said nothing.** `APERIO_OUTBOUND_ALLOWLIST` and `APERIO_OUTBOUND_BLOCK_PRIVATE` decide by resolving the destination on this server and looking at the addresses it maps to, which is the only reason they can refuse a hostname that points at `127.0.0.1` or the metadata service. A proxy takes that apart: the client stops resolving the name at all and hands it to the proxy, which resolves it on its own network and connects on the server's behalf, so the addresses the policy vetted are not the addresses anything reached. Measured rather than reasoned about: with `HTTPS_PROXY` set, a request for a name that does not resolve on this machine still left as `CONNECT` to the proxy. The two halves that read the URL as text, a literal IP and a hostname pattern, went on working, which is what made the other two halves' silence hard to notice. A proxy is now something the server is told about rather than something it inherits, so the two are reconciled instead of disagreeing: see the entry above for `outbound.proxy` and what the policy still covers through one. `NO_PROXY` is not accepted as an escape anywhere, because it was measured not to be one: a loopback request with `NO_PROXY=*` set still went to the proxy, which is why the bypass list is ours and applied by us.

  **This was first shipped in this cycle as a refusal to start**, which never appeared in a release and is gone: the setting above replaced it before the version was cut.

- **On a machine with `HTTP_PROXY` set, the client sent its backend requests to the company proxy.** The backend is the one destination a client has that is not the internet: `127.0.0.1:3000`, a container beside it, a socket on the same host. reqwest reads `HTTP_PROXY` and `HTTPS_PROXY` from the environment by default, and a workstation inside a company network has them set because everything else on it needs them, so the client asked the corporate proxy to fetch an address only the local machine can see. The proxy refused, and the refusal arrived at the visitor as their own site answering `502`; the health probe went the same way, so the service never became routable in the first place. `NO_PROXY` covers it on a machine where that variable is right, which is what kept this from being noticed. Requests to the backend now ignore the proxy environment unconditionally, and they take that rule from one place rather than each having been written correctly by hand. The calls that really are internet-bound, the API and discovery calls to the tunnel server, are unchanged and still honor it.

  **This is not proxy support**, which the client still does not have: the tunnel itself dials the server directly and cannot yet be pointed through a proxy at all. That is `planned_features.md` #117. What changed here is only that the environment no longer misroutes the request that was never meant to leave the machine.

- **The published guide printed em dashes the project does not write.** In LaTeX the em dash is spelled `---`, three hyphens the typesetter joins into one character, and that ligature is deliberately left switched on here (the comment above the line-breaking rules says why it is kept that way). So a check that looks for the character passed on this file while the PDF carried the dash anyway, on the three code-card titles in *What to expose*, in the *Names* section, and in two reference-table rows. All seven are a comma or a second sentence now. The typesetting is unchanged, the same nine box warnings before and after, none of them new.

- **A `forward` refusal that set more than one cookie lost all but the first.** The refusal an endpoint gives is forwarded to the visitor verbatim, which is the point of the method, but only the first value of each header was copied. `Set-Cookie` is precisely the header that is sent more than once and may not be folded into a comma-joined line, and a login handoff is routinely two of them: clear the stale session, set the nonce the login is about to check. The visitor arrived at the endpoint's own login missing half of what it had just been sent, so the login failed or looped, on every gated request. Every value of each relayed header now crosses, which also covers `WWW-Authenticate` offering more than one challenge.

### Added

- **The client can dial the tunnel server through an HTTP proxy, for a network that allows no direct outbound connection.** Plenty of companies work this way, and until now a client on one of those networks simply did not connect: the dial opened its own socket to the server and there was nowhere to put a proxy. `egress_proxy:` (`APERIO_EGRESS_PROXY`, `--egress-proxy`) takes `host:port` or `http://host:port`, with an optional `user:password@` in front. The client sends `CONNECT` and then runs TLS and the WebSocket handshake inside the tunnel the proxy opens, so **TLS stays end to end** and the proxy sees the hostname it was asked for and nothing else. An `https://` proxy, meaning TLS to the proxy itself, is refused rather than quietly dialed in the clear.

  **The tunnel only.** Requests to your own backend are never sent through it, which is the other half of the same story: the backend is the one destination a client has that is not the internet. Two details worth knowing: with a proxy configured, `ip_family` and the address fallback apply to the *proxy's* addresses, since the server's name is resolved by the proxy and never locally; and a proxy that refuses `CONNECT` fails the dial with the proxy and the status it returned named, a `407` saying whether the credential was missing or rejected. `aperio-client check` goes through the proxy too and reports the route it took, so the command you run to diagnose this does not report a failure that exists only because it dialed direct. The credential never reaches a log: everything printable about a proxy is host and port.

- **A Helm chart for the server, and a documented sidecar for the client.** The largest population of self-hosted deployments is on Kubernetes and there was no supported way in. `charts/aperio-server` is a StatefulSet with a PersistentVolume for the SQLite store, a Service, an optional Ingress, a Secret for the master token, and the `healthz`/`readyz` probes wired to what they were built for.

  **The values file is the server's own configuration, and that is the design rather than a detail.** Everything under `config:` is written out as `aperio-server.yaml` and handed over unchanged, so the reference is `docs/configuration.md` and the published JSON Schema, not a second vocabulary, and a setting added to Aperio works in the chart the day it ships without the chart being touched. The chart's own values are only what Kubernetes needs and Aperio has no opinion about. CI proves the claim rather than asserting it: the rendered ConfigMap is fed to `aperio-server --check-config`, the same validator an operator would run against a hand-written file.

  A StatefulSet and one replica, both deliberate: SQLite on a `ReadWriteOnce` volume has one writer, and a Deployment with a PVC would hand the same volume to a new pod while the old one may still hold it. Scaling out means a second deployment with its own volume and hostnames, which is a decision to make rather than a number to raise. The client is a **sidecar** in your workload's pod, where `localhost` is the backend and nothing in the cluster needs a Service, an Ingress or a NetworkPolicy to reach it; scaling the workload scales the tunnel, since every replica dials in and the server balances across them. New documentation: [docs/kubernetes.md](docs/kubernetes.md).

- **Scheduled snapshots can be encrypted, with AES-256-GCM and a key that is not allowed to sit next to them.** A snapshot is a copy of the whole store, hashed credentials, sessions, organizations and tokens, written to a directory that usually has a longer life and a wider audience than the data directory. `backup.key_file:` (`APERIO_BACKUP_KEY_FILE`) or `backup.key:` (`APERIO_BACKUP_KEY`) turns each one into `aperio-<epoch>.db.enc`; unset keeps writing them in the clear exactly as before. The cipher comes from `ring`, which rustls already puts in the binary, so this adds an algorithm rather than a crypto stack.

  **The key handling is the part that had to be real, because a key sitting next to the backup is decoration.** A key file inside the backup directory is **refused** with a message saying why: whoever has the backups would have the key. Two key sources at once are refused, so there is never a question which is in force. A key that is the wrong length, unreadable or unparseable **disables backups** rather than quietly falling back to plaintext, since an operator who configured encryption and got clear snapshots has the opposite of what they asked for and no way to see it from the files. A key file readable beyond its owner is warned about.

  **Restore is `aperio-server --decrypt-backup <snapshot.db.enc> [out.db]`**, because an encrypted backup nobody can open is worse than no backup, and the moment somebody needs it is the moment they are least able to write a decryption script. It is also the one subcommand that runs *before* the config-version check: that check exits on a security-relevant change, and turning ciphertext back into bytes does not depend on what a config key means, so a blocked restore would be the worst possible time to find out. Nothing is written to the output path unless the whole file decrypted, so a wrong key or a truncated backup leaves no half-database to be restored by mistake.

  Two things worth knowing: `VACUUM INTO` needs a path, so an encrypted snapshot is written in the clear first and encrypted after, with the intermediate file created owner-only and removed either way; and the format is chunked with each chunk's position, length and end-of-file flag authenticated, so reordering, a rewritten frame and truncation are refused rather than absorbed into a shorter database.

- **A Homebrew formula and a Scoop manifest are attached to every release, so both binaries install in one line without a tap or a bucket existing.** `brew install` is how a large share of the audience tries a tool at all, and a client nobody can install in one line is a client nobody evaluates. Both files are generated from the release's own `<file>.sha256` artifacts rather than by recomputing anything, so a formula and the signed checksum manifest cannot disagree: they are the same number, read once. They are rendered before the checksum step, which puts them under the same manifest and signature as every other asset.

  ```bash
  brew install --formula https://github.com/co3moz/aperio/releases/latest/download/aperio-client.rb
  scoop install https://github.com/co3moz/aperio/releases/latest/download/aperio-client.json
  ```

  A tap is nicer where it exists, since `brew upgrade` keeps working afterwards, and the release workflow pushes the formulae to one when `HOMEBREW_TAP_REPO` and `HOMEBREW_TAP_TOKEN` are configured. That step is **optional and skipped with a notice** when they are not: a release must not fail because an optional distribution channel is not set up.

- **Every release now carries a `.deb` and an `.rpm` for both binaries, each with a hardened systemd unit.** Installing on an ordinary Linux box meant `install.sh` and then writing your own unit file, which is where hardening quietly does not happen: the tarball path gives you a binary and no opinion about the account it runs as, what it may write, or which syscalls it may make. The packages (amd64 and arm64, built by the release job from the same binaries as the tarballs, and covered by the same checksum manifest and build-provenance attestation) put the binaries in `/usr/bin`, config in `/etc/aperio` at `0640`, and units that run as a named `aperio` account under `ProtectSystem=strict`, `NoNewPrivileges`, `MemoryDenyWriteExecute`, `SystemCallFilter=@system-service` and the `ProtectKernel*` set, with `RestrictAddressFamilies` narrowed to IP for the server and IP plus unix sockets for the client. The client's unit is a template, so `systemctl enable --now aperio-client@myapp` runs an instance from `/etc/aperio/myapp.yaml` and a machine fronting several things does not accumulate copies of a unit file that drift. Both packages install side by side; they share no files. New documentation: [docs/packages.md](docs/packages.md), and a section in the guide.

  **Installing starts nothing**, and that is deliberate: the shipped server config carries a placeholder master token, and a tunnel server that comes up on `apt install` with a token published inside a package is worse than one that does not come up at all. Set `server.token`, then `systemctl enable --now aperio-server`. One consequence of the sandbox is worth knowing in advance: `ProtectSystem=strict` makes the filesystem read-only apart from what is named, so moving the data directory is `Environment=APERIO_DATA_DIR=` **and** a matching `ReadWritePaths=` in a `systemctl edit` override. The config's `version:` key is stamped with the release that built the package, so the upgrade check works for someone who installed from a package and never edited that line.

- **The client can pin the TLS floor, and the cipher suites, of its tunnel dial.** Over `wss://` the tunnel used rustls' defaults as they come, TLS 1.2 and 1.3 with rustls' own suite order. That is the right default and an awkward answer to a compliance questionnaire that wants the floor named in writing, because "we use the library's defaults" is a statement about a dependency rather than about the deployment. `tls_min_version:` (`APERIO_TLS_MIN_VERSION`) takes `1.2` or `1.3`, and `tls_cipher_suites:` (`APERIO_TLS_CIPHER_SUITES`) takes IANA suite names comma-separated, for the rare case something external requires an exact set. Neither changes what a correct peer negotiates; they change what is offered, and what can be shown to someone who asks. Unset leaves the dial byte for byte as it was.

  **A value that cannot be honoured is refused at startup, never ignored.** A misspelled version, a suite name this build does not have, and the one contradiction the two keys can describe together (a 1.3 floor with only 1.2 suites named, which each half considers valid and rustls rejects only once assembled) all stop the client with a message naming what was written. An operator who pins a floor is asking for a stricter dial than they had, so falling back to the default would hand them the opposite of what they asked for and say nothing. Both are fixed for the life of the process, like `ip_family`: a hot reload does not change the terms the current connection was made under.

- **A client can declare the richer gates too, negotiated on the handshake rather than assumed.** `auth:` is one grammar on both sides, and until now only two of its methods could actually reach the server from a client: the tunnel handshake carries a client's gate as a single `user:password`, so a client declaring `bearer` or `jwt` refused to start. It can now declare `none`, `basic`, `bearer` and `jwt`, with the full policy travelling beside the scalar. `forward` stays server-side, and deliberately: its URL is called by the *server*, from the server's network, so a client writing `localhost:7070` would mean the server's localhost rather than its own.

  **The capability is announced on the handshake response**, which is what makes this safe rather than merely additive. The client reads it before it has declared anything, so a policy this server does not understand means leaving without ever claiming a route, and a server too old to send the announcement sends nothing, which reads as the two methods that always travelled. The failure being avoided is specific and quiet: a server that ignored a policy it did not understand would read the client as declaring *no* gate, and the route would come up open. When a service cannot be served under the gate that was written, only that service stops, with a log naming which side is too old and what it does accept; its siblings are untouched, which is the improvement over refusing to start and taking the whole client down.

  Declaring a policy needs the same token permission a client-set password and `public: true` already need, `APERIO_IGNORE_CLIENT_AUTH` still drops the whole client-declared gate whatever shape it is, and a route whose clients declare different policies falls back to the server's gate, the same unanimity rule the scalar spelling always followed.

- **A `forward` method: a route can hand its gate to an endpoint you run.** What nginx spells `auth_request` and Traefik spells ForwardAuth. Before dispatching, the server asks a URL you name; a `2xx` admits the request and anything else refuses it, with the endpoint's own answer relayed to the visitor so it can send a browser to a login of its own. It is the escape hatch that lets the method set stay closed rather than becoming a plugin interface: LDAP, SAML, or a rule nobody anticipated is thirty lines behind that URL, in a process that is not Aperio's, with a contract that is two HTTP messages rather than an ABI.

  Five decisions, all deliberate and all documented. **What crosses to the endpoint** is a `GET` describing the request rather than replaying it (`X-Forwarded-Method`, `-Proto`, `-Host`, `-Uri`, `-For`) plus the request headers you name, defaulting to `cookie` and `authorization` rather than everything the visitor sent, since handing over the whole request makes every header it happens to read part of a contract nobody wrote down. **What crosses back** is only the response headers you name, and that list is empty by default, because it is how the pattern delivers an identity onto the request reaching your backend and an open list is how it becomes a header injection. **A timeout refuses**, so the endpoint's availability becomes the route's, which is the trade being made rather than an accident. **`cache:` remembers a verdict** for an identical credential so a busy route does not pay a round trip per request, and it remembers admissions only: caching a refusal would keep turning away somebody who has just been given access. **The destination goes through the outbound policy**, like webhooks, scaling hooks and key-set fetches. A share link still gets its chance: a refusal from the endpoint is held rather than returned until that has been tried.

  One detail worth naming because it is the difference between working and not: redirects from the endpoint are **not** followed. A `302` is the commonest refusal it can give and the entire reason to relay its answer, and the HTTP client's default is to chase it, which would have turned an answer meant for the visitor into a request Aperio makes.

- **A `jwt` method: the visitor already holds a token, and Aperio can check it.** `auth:` takes `{method: jwt, jwks_url: ...}`, verifying a token against the public keys an issuer publishes, or `hmac_secret:` for `HS256` where the issuer is your own service. `issuer:`, `audience:` and any number of exact-match `claims:` narrow what is accepted, and `cookie:` reads the token from where an identity-aware proxy in front writes it instead of from `Authorization: Bearer`. It costs a signature check and no round trip per request, which is the operational difference from delegating to an endpoint, and it subsumes a shelf of provider integrations that would otherwise each have arrived as their own method: Cloudflare Access, an ALB doing OIDC, and anyone running their own auth service all hand out the same thing. Key sets are cached for an hour and fetched again when a token names a key id that is not in the cache, so a rotation needs no restart, with a floor between fetches so a stream of invented key ids cannot be aimed at the issuer through the server. The key-set URL goes through the outbound policy like every other destination the server is told to call. The identity it establishes is the `email` claim, else `sub`, which is what the visitor identity headers forward.

  **`iss` and `aud` are checked only when the file asks, and asking means the claim must be present.** An unset `audience:` is not "accept any audience", and a configured one refuses a token that carries none, which is exactly the token the requirement was written to keep out. `exp` is required whatever the file says: a token with no expiry is one that never stops working. A key set holding several keys, against a token that names no `kid`, is refused rather than tried against each of them; guessing which key signed something is how a verifier ends up accepting a signature the issuer did not mean to make. A token in the `Authorization` header is Aperio's credential and does not travel to the backend; one in a `cookie:` is the visitor's own and does, since stripping the cookie header would take the application's session with it.

  The one new dependency, `jsonwebtoken`, is pinned to its 9 line on purpose: it builds on `ring`, which rustls already puts in every Aperio binary, so this adds no crypto implementation and no cross-compilation surface on the musl and Windows targets. Later versions want a different backend, which would be a third crypto stack in one binary, so moving off the pin is a decision rather than a bump, and `aperio-server/Cargo.toml` says so where someone would make it.

- **The backend can be told who the visitor is.** The gate has always been a wall: it decided whether a request continued and told the backend nothing, so an application behind a tunnel could not greet anyone without building a second login next to Aperio's. `visitor_identity_headers` (`APERIO_VISITOR_IDENTITY_HEADERS`) adds `x-aperio-visitor-how` to the forwarded request, one of `session` / `bearer` / `share`, and `x-aperio-visitor-id`, the email or username behind a session where there is one (a `bearer` secret identifies a caller rather than a person, so it carries no id). Off by default, the same new trust surface as `identity_headers` and adopted the same way. A route that is open or ungated identifies nobody and sends neither header, since a value meaning "anonymous" is noise a backend has to learn to ignore. The forgery half was already done: inbound `x-aperio-*` headers are stripped from every proxied request whatever this is set to.

  **A related leak, found by the test written for this:** the `Authorization` header that opened Aperio's own gate was being forwarded to the backend, so a backend and its logs learned a secret that opens every route that gate protects. It is now stripped when it was the credential that admitted the request, on exactly the rule that already strips the `aperio_session` and `aperio_share` cookies while leaving every other cookie alone. An `Authorization` header that did *not* open the gate is the visitor's own message to the backend and still travels untouched.

- **`default_access: deny` makes a route reachable because something said so, instead of because nothing said otherwise.** With no `auth:` configured anywhere, every proxied route served everyone, and `public: true` was an exemption from a gate that might not exist rather than the thing that opened one. The visible symptom was operators writing a throwaway `auth: DUMMY:DUMMY` on services they did not want public, which is a configuration language admitting it cannot express *closed*. `default_access` (`APERIO_DEFAULT_ACCESS`) now says what an ungated route means: `allow` is the old behaviour and remains the default, `deny` refuses anything that no `auth:` policy admits and that nothing declared open with `method: none` / `public: true`. The refusal is the same answer an unclaimed hostname already gives, so under `deny` the existence of something at an undeclared route never leaks to a caller who was not going to be let in. A route that *is* gated behaves exactly as before: the posture decides what an unstated route means and nothing else. An unreadable value refuses the start rather than being guessed at, since `off`, `false` and `no` could each plausibly mean either side of this.

  **The default is not flipped here, deliberately, and there is now a number behind that.** The flip was written and measured: a server with `server.auth` or OIDC is unaffected, since its routes are gated and therefore reachable after a login, but a server with no visitor auth at all, which is a tunnel publishing a public site, goes dark until every service declares `public: true`. Against the end-to-end suite that is 129 of 241 phases. So the flip is a migration for the commonest deployment there is rather than a patch note, and it will ride a major release that says so. While the default is still `allow`, a client connecting with a service that nothing gates logs a warning once per connection naming exactly what to write, and under `deny` the refusal logs its own message on the connection being refused, so "the site went dark after we upgraded" has a one-line answer either way.

- **A gated route can finally be reached by something that is not a browser: the `bearer` method, and a refusal that says what to present.** A machine could administer Aperio without a screen (admin API keys, the master token, `APERIO_METRICS_TOKEN`) and could not *use* a tunnelled service without one. The visitor gate read the session cookie and nothing else, `Authorization` on a proxied request meant nothing, and every refusal was a `302` to an HTML login form, so there was no way to `curl` a gated route at all. `auth:` now takes `{method: bearer, secret: ...}`, an opaque secret presented as `Authorization: Bearer`, with `secret:` accepting a list so a key rotates by adding the new one before withdrawing the old. Beside it, refusals gained a shape: a browser navigation (`GET` with `Accept: text/html`) still goes to the login page, and anything else on a gate with a `bearer` method gets `401` with `WWW-Authenticate: Bearer`. Since the policy is a list, one route now says "a person signs in, a script presents a key" and answers each in the form it can act on.

  **`query: true` additionally accepts the secret as `?aperio_token=`**, for the callers that cannot set a header: an `<img src>`, a link in an email, a sender with a fixed request shape. It is off by default, because a query string reaches the `Referer` header, browser history and every proxy in front, and it is a per-method decision so a gate that never asked for it cannot be opened that way. What Aperio itself records stays clean: the access log has only ever kept the path, the inspector masks the value alongside `aperio_share`, the parameter is stripped before the request reaches the backend the way the session cookie already was, and a *page load* carrying one is answered with a redirect to the clean address plus a short-lived cookie, so the secret is not repeated on every asset of that page. That last move is what a share link already does on its first click, and it reuses the same cookie rather than inventing a second one.

  A `bearer` secret is compared verbatim rather than hashed, unlike a `basic` password, because it is a high-entropy value the operator generated: no dictionary to defend against, and no user half to slow a guess down. Its length is therefore the whole of its strength, which is why one shorter than 16 characters is refused where it is written. The method is server-side for now: the tunnel handshake carries a client's gate as one `user:password`, so a client declaring `bearer` refuses to start rather than announcing something weaker than what was written.

- **`auth:` is now one grammar with a `method:`, on both sides of the tunnel.** The visitor gate could say exactly two things: a server-wide `user:password` and a client's `user:password` for one service. Everything else needed another top-level key, which is why the area read as a pile of unrelated settings rather than one decision. `auth:` now accepts the scalar it always did, one `{method: ...}` block, or a **list of them**, and the list is any-of, a visitor is admitted by the first method that admits them. The list is the shape from the start because "a browser signs in, a script presents a key" is what this is for, and widening a single choice later would change every line already written. Two methods exist today: `basic`, the `user:password` login, now taking several credentials on one gate; and `none`, deliberately open, which is the long spelling of a client's `public: true` and needs the same token permission. The set is closed on purpose (a plugin interface was considered and refused), and a `method:` a build does not know **refuses the start** while naming the ones it does, because an operator who wrote a gate must never be handed no gate. The server also refuses to start on an `auth:` section it cannot parse, rather than falling back to `APERIO_SERVER_AUTH` and running with a gate nobody asked for.

  **Nothing written today changes meaning.** The scalar is still what `APERIO_SERVER_AUTH`, `APERIO_VISITOR_AUTH`, `--visitor-auth` and the dashboard's visitor-password field carry, and it still folds to exactly one `basic` credential. A policy the scalar cannot express shows as empty in that field, so `GET /aperio/api/settings` reports `visitor_auth_methods` beside it and what is in force stays readable. Nothing on the tunnel changed either: a client whose `auth:` says more than the handshake can carry refuses to start, instead of announcing a gate weaker than the one written.

  One behaviour was pinned down rather than changed on the way past: `APERIO_SERVER_AUTH=secret`, with no separator, has always produced a gate no ordinary login can open, and it still does. Reading a value like that as "no gate" would turn one typo into every route on the server going public, so the compile step fails closed everywhere, and a `basic` method carrying nothing usable locks rather than opens.

- **A notification bell in the dashboard, so a client dropping is something you are told rather than something you notice.** Token expiry, a client that connected or disconnected, maintenance left on, an alert that fired: all of these were already events, delivered to webhooks and published on the `$aperio/` topics, and the only way to find out from the dashboard was to spot a changed row in a table. They now also arrive on the dashboard's existing Server-Sent Events stream (`/aperio/api/stream`, `notification` frames) and collect behind a bell in the header, newest first, with an unread count that survives a reload and a coloured dot matching the green/red/amber of the chat-service webhook cards. The events are fenced to the caller's organization by the server, exactly as live traffic is, so a child organization's dashboard never sees master's events or another organization's. The event name is shown untranslated on purpose: it is the identifier a webhook subscribes to and the audit log filters by. Nothing is stored server-side and nothing is kept for a tab that was closed, the record of what happened stays the audit log.

### Changed

- **Every released client is now paired with each new server after the release, and the result published as a table.** The gate added alongside this covers one release of skew in both directions and fails the build; this is the wider half and deliberately does not, because an old client failing against a new server is information rather than a regression. A workflow runs on `release: published`, pairs the newly released server binary with the `aperio-client` binary of every previous release, and writes the table to the job summary. Both sides are downloaded release artifacts, so what is measured is what people install. Rehearsed over all nineteen releases against the 0.9.0 server: **every released client from 0.1.0 onward passes**, which is the first time that sentence has been a measurement rather than a hope. The upgrade guide now states it and says how to reproduce a single pairing.

- **The client/server compatibility promise is now checked against the previous release's real binaries instead of only being written down.** The upgrade guide has always described a protocol designed to tolerate skew, which is the right design and was nonetheless an assertion: everything CI ran tested one tree against itself, which is exactly the pairing no deployment runs, since the server is one box and the clients are a fleet. A `compat` job now runs a slice of the end-to-end suite in both directions against the binaries of the previous release, downloaded from its GitHub Release: that client against this server, and this client against that server. The slice is proxying a request end to end plus the admin API, because that is what the promise is about, whatever else changed between two versions, a request still reaches the backend and an operator can still see it. The guide gained a *What is actually checked* section stating the window this proves (one release of skew) and the two environment variables (`APERIO_CLIENT_BIN`, `APERIO_SERVER_BIN`) that let anyone measure a specific pairing themselves.

- **The Complete Guide's *What to expose* section now shows a complete `aperio.yaml` per case instead of one line each.** The three ways a client exposes something (a backend URL, a directory, a private TCP port) were a three-item list of fragments, which answers "what are my options" and not "what do I write down", the question a reader on that page actually has. Each is now its own worked example: an application server with a health probe and concurrency, a built static site with caching and security headers, and a pair of private tunnels bound by name from another machine, each the whole file rather than the interesting line out of it.

- **The guide now says who receives the server's own `$aperio/` events.** *The server's own events* described what is published and how to ask for it, and left the two questions a reader of that page actually has unanswered: who is allowed to subscribe, and whether one organization can hear another's. Both are answered now, and separately, because they have different answers: subscribing is the ordinary `topics` token permission with no extra flag, delivery is fenced on the organization exactly as an ordinary message is with master no superset of its children, and events belonging to the server rather than to a tenant (an alert, a setting change, a backup) have no organization and reach only the un-fenced clients. It also states the consequence of granting a token `#`, which covers the reserved namespace too, so "all topics" quietly includes the infrastructure feed.

- **The guide's *Alert rules* section lists the watchable metrics in a table, with their aliases, units and platform limits.** The four quantities a rule may watch were a sentence naming them, which is enough to recognise one and not enough to write one: it did not say that `clients`, `pending`, `disk_bytes` and `memory_bytes` are accepted spellings of the same four, what unit each is in, or which of `above:`/`below:` a given metric is usually paired with. There is now a table per question, one for the metrics and one for the four keys of a rule, and the example shows a `below:` rule beside the `above:` one.

### Fixed

- **The same false success across the other stores: users, organizations, admin keys, webhooks, the webhook inbox and autoscaling records.** The token store was fixed first; this is the rest of the count it produced, about forty mutations that ignored what the write returned. Creating a user, deleting one, moving an organization's hostname fence, setting a quota, enrolling or disabling TOTP, adding or removing a passkey, creating an admin key or a webhook, deleting an inbox entry, disarming an autoscaling record: each of them answered success on a store that could not be written, and each is now rolled back and reported with a `500` that the OpenAPI document declares. Two of the stores could not even notice, their `persist` discarded the result before anyone could look at it.

  **Two of these are sharper than the rest, because single use is a property of the record and not of the check.** A recovery code that the store failed to mark as spent, and a TOTP step it failed to record, now **refuse the login** rather than accepting it: signing someone in on a code that still works, or on a step that can be replayed after a restart, is precisely what those records exist to prevent. A refused login is visible and recoverable; a silent replay window is neither.

  **And one pre-existing bug of the same family:** `update` on a user applied the role and enabled flag *before* validating the password, so a rejected password left a role change sitting in memory that was never saved and never undone. The account was an admin until the process restarted, while the API had answered with an error. Rolling back on a rejected change as well as on a failed write makes that shape impossible to write again.

  Deliberately **not** changed: the server's own bookkeeping, a retention sweep, a disk-cap truncation, an inbox insert, a dump import, a re-announced autoscaling record. Nobody is waiting for an answer there, the next sweep does it again, and rolling back would mean holding data an operator asked to be rid of. The rule now sits in one place, above `store::replace_all`, and each of those methods points at it.

- **Creating, editing, rotating or refreshing a token reported success when the store could not be written.** On a full disk the record went into memory, the write failed with an error in the log, and the API answered `200`: the caller was handed a secret for a token that would stop existing at the next restart, and the dashboard showed a token the store did not have. `TokenStore::revoke` had always handled this correctly, putting the removed record back so memory matched disk and returning a failure, so the pattern existed and the other mutations simply ignored the result. Every mutation now goes through it: the change is undone and the endpoint answers `500` with a message saying it was rolled back. This is a change in what your tooling sees, a request that used to answer `200` on a failing disk now answers `500`, which is the point.

  **The two failures are also told apart, which they were not.** `revoke` returned one `false` for both "no such token" and "the write failed", so a caller could not distinguish a `404` from a `500`, and the honest answer to the second was never available. Related: a device pin that could not be recorded now **refuses the connection** rather than admitting it. Pinning exists to bind a token to one device, and a pin that was not written down does not bind the next connection to anything, so admitting the client would leave the operator with a control that reports itself enabled and holds nothing.

- **The same `auth:` policy behaved differently depending on which side wrote it.** A gate written on the server and the identical gate written on a client's service went through two hand-written sequences of the same helpers, and they had drifted: a `bearer` method with `query: true` got the clean-address redirect and its short-lived cookie when the server declared it, and a bare admission of that one request when a client did. A page opened through a client-declared gate therefore rendered and then failed to fetch a single one of its own assets, because each of them was a fresh request with no token and no cookie. Both branches now call one function, which is what "one grammar" was supposed to mean, and a test holds the two sides to the same answer.

- **Two size limits on the visitor-auth path were applied after the body was already in memory.** The `forward` method reads what the endpoint answered, and the `jwt` method reads an issuer's key set; both had a cap, and both checked it against a body they had just finished allocating. A limit applied afterwards is not a limit: it frees what it has already paid for, and how much that is was decided by whatever answered. On the `forward` path, which runs per visitor request when the verdict cache is off, that made a broken or hostile endpoint able to set the memory cost of every request through the gate. Both now stop reading at the limit, and refuse immediately on a declared `Content-Length` over it, so a body that is promised and never sent no longer costs the wait either. The two copies of that reader have become one, in the module that already owns the server's outbound calls.

- **Every forward-auth subrequest built its own HTTP client.** A `reqwest::Client` owns a connection pool, so building one per request meant a fresh TCP and TLS handshake for each visitor request on a gated route, which is the opposite of what a method sitting on the request path should cost. One client is now shared for the life of the process, with the method's timeout applied per request, where it belongs.

- **The guide's reference tables ran their long setting names into the next column.** `APERIO_MAX_CONNECTIONS_PER_SERVICE` is wider than the column it lives in, and a `\texttt` run offers TeX no place to break, so the appendix tables printed one column's text on top of the next one's and past the page edge: 414 overfull lines, almost all of them in the reference chapters, which are exactly the pages an operator reads by scanning. Literals may now break after the separators they are built from (the underscore of an env var, the dot of a grouped yaml key, the slash of a path) and never with a hyphen, since a hyphen inside a name reads as part of it; every reference column is set ragged right rather than justified, which is what was tearing the narrow ones apart; and the column widths were rebalanced so the Default column fits a value like `10485760` (10 MB). Four overfull lines remain, all of them prose or a diagram, none of them a table. The dotless `ı` in the tunnel-handle section, which the monospace font has no glyph for and was dropping from the page while explaining why it matters, is now set in the body font.

- **Two client settings had an empty yaml column in the guide's reference table.** `APERIO_SERVE_SPA` and `APERIO_SERVE_404` are `serve_spa:` and `serve_404:` in `aperio.yaml`, and the table showed a blank where the key should be, which reads as "environment only". *What to expose* named the environment spelling too, and now names the yaml one.

- **The guide told readers to point their editor at `./schemas/`, a directory that only exists after a build.** The Complete Guide's *Editor support* section handed out a `.vscode/settings.json` with relative paths into the repository's own git-ignored build output, which is the right advice for someone hacking on Aperio and useless for everyone else: an operator writing an `aperio.yaml` against an installed binary has no such directory, and the block silently gave them no completion at all. It now points at the stable schema URLs every release publishes (`releases/latest/download/aperio-{client,server}.schema.json`), the same ones [docs/configuration.md](docs/configuration.md) already documented, mentions the per-tag copies for pinning to the version a deployment actually runs, and keeps the build-from-source route as the offline alternative it is.

## [0.9.0] - 2026-08-05

### Security

- **A fenced organization could put another organization's site into maintenance, or mint a share link into it.** Both gates asked whether the caller's hostname allowlist *covers* the name, which is the right question for "may this be bound" and the wrong one for "is this yours": the master token is never fenced, so a master client can be serving a hostname inside an organization's fence, and coverage alone let that organization 503 it or hand out a link past its visitor gate. A share link is redeemed by hostname and path alone, so that gate was the whole of the isolation. Both now require the second half as well: the name must be inside the fence *and* not currently served by a client of another organization. A name nobody serves is still actionable, which is what keeps a fence usable before the first client connects, and was the behavior a previous fix went out of its way to restore. Two organizations given overlapping fences were exposed to each other the same way, and are covered by the same check.

- **`GET /aperio/api/explain` named the clients of other organizations.** The endpoint refuses a hostname outside the caller's fence, and that check was doing all the work: once a hostname was admitted, the report listed *every* connected client serving it, whoever it belonged to. A wildcard fence makes that a real overlap, an organization holding `*.example.com` could ask about a name a master client answers and be told which service answers it and on which connection, along with why each one was passed over. Connection ids made it look opaque; naming the clients by their service name made it readable, which is what brought it to light. A client outside the caller's organization is now counted without being named: no name, no id, and no reason it was passed over, so the report still answers "something else serves this" without answering "whose". The master organization is unfenced, since these reports exist for it. Clients inside the fence are named `org@name`, the address shape a tunnel handle already uses.

- **`min_tls_version` was ignored for `h2://` backends.** The floor was applied where the HTTP/1 client is built, which an HTTP/2 target never reaches, so a configuration asking for TLS 1.3 got it for every backend except the `h2://` ones: a setting refused nowhere and applied nowhere, which is the worst state a security setting can be in, because the file says the connection is protected. The HTTP/2 client is now built with the same floor.

- **An existing device-key file kept its old permissions when a new key was written into it.** The key file is opened with mode `0600`, but that mode only applies to a file the call actually creates. A path that already existed, which is what a failed earlier write or an operator's `touch` leaves behind, kept whatever mode it had, usually `0644`, and the pinning secret was written into it world-readable while looking as though it had been written owner-only. The permissions are set after the write now, so both paths end up at `0600`.

- **Signing in with a passkey or through OIDC issued an unprefixed session cookie.** The dashboard's session cookie is named `__Host-aperio_session` wherever `secure_cookies` allows it, and that prefix is the whole defence for a server that also proxies other people's hostnames: a browser only lets the exact host set a `__Host-` cookie, so a tenant on a neighbouring subdomain cannot set one that the dashboard would read. Password sign-in asked for the right name; the OIDC callback and both passkey completions wrote `aperio_session=` verbatim, so users of those two paths held a cookie a neighbour could imitate, and a session someone else chose could be walked into an operator's browser. All four paths now go through one builder, and a test walks the server's own sources to fail the build if a future sign-in path formats the cookie by hand again.

### Added

- **The Tunnels page names the declaring client instead of showing its id.** The Client column showed the connection id, which is a uuid unless an operator happened to write `client_id:` in the file, so the column that answers "who declared this tunnel" answered it with something nobody recognizes. It now reads `org@name`, the same address shape the tunnel's own name uses on that screen, taken from the `custom_name` or the `services:` entry name, with the connection id one hover away. `GET /aperio/tunnels` carries it as `client_name` beside the existing `client_id`. A client that named no service still shows its id, which is then all there is.

- **A capture names the client that served it.** The request inspector showed every stage of a request and never said which client answered it: the only clue was the `x-aperio-client-id` header among the forwarded request headers, a uuid, on a screen whose whole job is telling you where a request went. `GET /aperio/api/requests/{id}` now carries `client_id` and `client_name`, and the inspector shows the name above the timeline with the connection id one hover away, named the same way the clients table names it, the `custom_name` an operator set or the `name` of the `services:` entry. A client that declared neither shows its id, which is then all there is.

- **Canary releases and weighted routing (`canary:` on a route).** The load balancer picked between clients by priority tier and round robin, so "send twenty percent to the new version" and "send *me* to the new version if I set this header" could not be expressed at all. Both are the same mechanism seen from two angles, so they are one block: `weight` is who gets the new version by default, `header` is how somebody opts in regardless, and `weight: 0` with a header is the opt-in-only shape. Membership is by the client's service name, the `name` of a `services:` entry. The split is decided **per visitor**, by hashing their address, not per request: a per-request coin flip would send one page load's twenty assets to both versions, which is a mixture rather than a canary and breaks the thing being tested first. The hash is stable across processes and restarts, so two servers behind a load balancer agree about who is in the canary. It never empties the pool, a canary that is down gives way to serving the request, and a failover keeps a visitor on their side, since a re-dispatch that moved them would make the split mean nothing exactly when something is going wrong. Proxied WebSockets are not split, deliberately: a socket is one connection rather than a stream of requests.

- **The server says so when a capacity setting does not fit the machine.** Two checks run once at startup: `max_ws_connections` plus `max_tunnels` against this process's file-descriptor ceiling, and the response cache budget against the container's memory limit. Both name the setting and the ceiling, and neither changes anything. The first is the one that matters: every tunnel and every proxied WebSocket is at least one descriptor, and past the ceiling `accept` fails with `EMFILE`, so connections break at a number nobody configured and nothing in the config explains it. This deliberately **warns rather than derives**, which is a reversal of what the idea originally was: a limit that silently follows the host is the opposite of the work spent on making "which value is in effect, and where does it come from" answerable, and it changes under the operator who moved the same file to a bigger box. Nothing is derived from `max_body_size` times a concurrency limit either: that product is a worst case reached by roughly no deployment, and a warning that fires constantly is one nobody reads.

- **The request inspector's buffer is shared fairly between organizations.** The fifty captures kept in memory were evicted oldest-first, which is fair only if every tenant is equally busy. They are not: one organization serving a thousand requests a minute walked a quiet organization's captures out of the buffer within seconds, so a tenant investigating one request an hour could never find it. Eviction now drops the oldest capture belonging to whichever organization currently holds the most, so a noisy tenant evicts itself. Deliberately a fair share rather than a per-org ceiling: a ceiling has to be chosen, and it interacts badly with the total (five orgs capped at twenty each is a hundred entries in a buffer of fifty, so the total cap evicts across tenants again and the ceiling bought nothing). Fair share needs no number, lets an organization alone on the server use the whole buffer, and converges on an even split by itself. The multi-tenant hygiene the byte and client quotas already had.

- **Admin calls are charged by what they cost.** Every call against the per-IP bucket took exactly one token, so a login attempt, an ephemeral-tunnel provision and a full store export were all priced as a page view. That is wrong in two directions at once: a brute-force attempt gets the whole allowance of a bucket sized for ordinary reads, and an operator running one legitimate export spends the same as one page view while costing the server a thousand times more. Credential attempts (login, OIDC, WebAuthn, token refresh) now cost two, and calls that provision or read the whole store (ephemeral tunnels, export, import) cost five. The multiples are gentle deliberately: the bucket was sized when every call cost one, so a steeper price does not make that class cost more, it tightens the limit on it against a ceiling nobody re-chose. The expensive calls are charged after authentication and the argument checks, so a malformed request is answered `400` without paying for the work it was never going to cause. It stays **one** bucket at different prices rather than a bucket per class, because separate buckets would let an attacker spend a full allowance on each and the thing being protected, the server's capacity, is shared anyway. A refused call is not charged, since it was never served. Sizing is still `ip_limit_max` and `ip_limit_refill`.

- **A minimum-throughput floor for streamed responses (`stream.min_throughput`).** The pump already ended a stream whose consumer could not take a single chunk within the gateway timeout, so a reader that took *nothing* was covered. The hole was the one in between: a reader that accepts one chunk every twenty-nine seconds resets that timeout forever and holds the stream, the client-side `max_concurrent` slot behind it, and megabytes of server-side buffer, for as long as it likes. Flow control is what made this possible, by making the server well-behaved and therefore patient. A floor in bytes per second now ends such a stream. What makes it safe to switch on is the denominator: only the time the consumer actually kept data *waiting* counts, so a stream that is quiet because the backend has nothing to send, which is ordinary for server-sent events and long polling, is never ended for it. Judged over 30-second windows, long enough that a paused video or a phone changing network is not read as an attack. Off by default.

- **Shell completion: `aperio-client completions <shell>`.** bash, zsh, fish, elvish and powershell. The `api` surface grew eleven subcommands recently and now spans about twenty-five command groups, which is past the point where remembering the spelling of `--daily-max-bytes` is a reasonable thing to ask. The script is generated from the same clap definition the CLI is parsed from rather than written by hand, so it cannot describe a flag that no longer exists, and it prints before the client reads a config file or initializes logging: a completion run in a directory with a broken `aperio.yaml` still works, and no startup log line is pasted into the middle of a shell function.

- **A server can hand out the addresses of its alternates (`alternate_servers`).** A client knew exactly one server URL unless somebody had written `APERIO_SERVER_URLS` on it in advance, so a planned migration or a regional failover meant editing every client's config. A server now announces its alternates on every handshake and clients append them to the list they already rotate through. Three properties make that safe to accept from a server: they are appended **after** the servers the client's own config names, so the operator's list still decides the order; the rotation wraps, so failing over is never a one-way door and a server that was briefly restarting gets its clients back on the next pass; and the list is capped and filtered to `ws://`/`wss://` at both ends, since it is announced to every client and walked by every client. What it deliberately does not do is rescue a client that has never connected: there is nowhere to learn from, which is why this is for a migration announced in advance.

- **A client that has become slow stops being sent work it cannot do (`adaptive_concurrency`).** `max_concurrent` is announced once and never moves, so a client whose backend has fallen over keeps advertising the capacity it had at startup, and the server keeps dispatching into it. With this on, the client watches how long requests wait for a local permit, which is the one signal that means "the backend is behind" whatever the host's CPU says, and lowers the number it announces. Nothing on the server changes: it already queues rather than dispatching past the announced number, so it holds the request, picks another client in the pool, or asks for capacity through autoscaling, all of which beat a refusal. The movement is AIMD, for the reason TCP uses it: halve on trouble, climb back one at a time, because being too high costs every visitor in the queue while being too low costs some throughput and those are not symmetric. It never leaves the band `1..=max_concurrent`, an idle window is not treated as recovery (silence is not evidence the backend came back), and the local limiter is resized in step so a server that ignores the number cannot push past it either. Off by default, and it needs `max_concurrent` set, since that is the number being moved.

- **A per-visitor ceiling on concurrently open streamed responses (`max_streams_per_ip`).** Saturating a service's concurrency budget took one host holding many slow streams, each costing a client-side slot and roughly a couple of megabytes of server-side buffer. With this set, it takes a botnet. The slot is claimed at the moment a response turns out to *be* a stream, not when the request arrives, so a limit about streams never fires on traffic that would have answered in one buffered frame, and it is released when the body ends or the visitor walks away, which makes it a concurrency limit rather than a rate limit: opening and closing streams as fast as you like never trips it, holding them open does. Refusals are `429` and are counted as `aperio_rate_limited_total{limit="streams-per-ip"}` like every other ceiling. **Off by default and deliberately without a suggested value**: a NAT, and a carrier-grade NAT in particular, puts many real people behind one address, so any number chosen here would be a guess with a queue of users behind it. Check `trust_proxy` before turning it on, or every visitor behind your CDN shares one address.

- **A background loop that panics comes back instead of disappearing.** Under the default `unwind` strategy a panic unwinds only its own task, so the process survives and a `tokio::spawn`ed loop simply *stops*. Its function was then gone for the life of the process, and nothing noticed, because a ticker that has stopped and a ticker with nothing to do look identical from outside: alerting stopped firing and read as "no alerts", retention stopped pruning and read as "nothing expired". Every background loop is now supervised, the stats flush, the uptime ticker, config hot-reload, alerting, token-expiry warnings, the autoscaling sampler and pruner, retention, backups, the rate/session sweep and the QoS 1 ack sweeper. Restarting is bounded rather than blind: each restart is logged at error naming the loop, the delay grows from one second to a minute, and after five consecutive panics the loop is left down with a message saying so, because a loop that panics every time it runs is not fixed by running it again and an endless restart turns a loud bug into a quiet one that also burns CPU. A loop that survives five minutes has its budget restored. Tasks that *cannot* be restarted, because they own a channel receiver or a bound socket (the telemetry collector, the access-log writer, `expose:` listeners), are escalated instead: they get a log line naming the task and saying its function is lost until restart, which is what the panic hook's bare location could never say.

- **The OTel bridge is a token capability (`allow_otel`).** The bridge shipped with one switch, the server's, which meant enabling it for one edge host enabled it for every token on the server. A token now carries `allow_otel`, and both have to line up: the server's `otel_bridge` says forwarding happens at all, the token's flag says which clients may ask for it. They are different questions, one about the deployment and one about the tenant, and answering both with one setting is how an operator ends up granting more than they meant to. It is off by default for the same reason `topics` is: a capability that switches itself on for every token that predates it is how a permission model quietly stops meaning anything. A token without it gets `403` on the HTTP endpoint and a logged refusal on the tunnel; the master token has it, as it has everything. Reachable from all its surfaces, `aperio-client api token create --allow-otel`, `api token update <id> --allow-otel` / `--no-allow-otel`, the dashboard's token editor and its badge in the token list, and the `POST`/`PATCH` token API. Ephemeral tunnel tokens never get it: they exist for a preview URL, and every capability they do not need is one they do not get.

- **An OpenTelemetry bridge: telemetry from an edge host, over the tunnel it already has.** An edge host usually has exactly one outbound connection it is allowed to make, and its own telemetry has nowhere to go; shipping spans from there means a new firewall rule and a collector credential on a machine that should hold as few of those as possible. With `otel_bridge` on the server and an `otel_bridge:` block on the client, the client runs an OTLP receiver on loopback (HTTP, and gRPC when a port is given) and carries what it receives to the server, which forwards it to the collector it already exports its own spans to. Anything next to the client exports with `OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:4318`: one environment variable, no SDK change, no credential at the edge. The client chooses the transport: `tunnel` sends exports as frames on the WebSocket it already holds, which is what preserves the "exactly one outbound connection" property the feature exists for, and `https` posts them to the server's endpoint instead, for telemetry bursty enough that it should stay off a socket shared with proxied traffic. Attribution is the server's and never the client's: every export is stamped with `aperio.token` and `aperio.org` as resource attributes, because telemetry filed under the wrong tenant is worse than none, being believed. It never blocks what it measures, a full queue drops the newest export and counts it rather than making the exporter wait, since an exporter that cannot hand off its batch blocks the application it is instrumenting. And it never decodes the payload beyond its outermost level, so a field from an OTLP version newer than the server is copied through rather than dropped.

- **TCP and UDP relays produce an access log.** Every proxied HTTP request produced a structured line; a relay connection produced nothing, so a database reached through a tunnel left no record of who connected, for how long, or how much moved. That is the one surface where the question tends to be asked after the fact, by somebody working out what a compromised credential could have reached. Relays now emit one line per **connection** (`event: relay_closed`) with the transport, whether it arrived on a public `expose:` port or from a peer client dialling a tunnel, the peer address, the serving client, the tunnel name, the token, the duration and the bytes each way. Per connection and never per packet: a per-packet line would be one entry per datagram of a video stream, which is not a log anybody reads. It goes to the same `aperio_access` event and the same access-log file as a request line, in the same shape, so one pipeline ingests both, and it honours `access_log_sample_rate` with its own accumulator so a busy HTTP surface cannot starve it of its share. A public `expose:` port authorizes nobody, so its lines carry no token rather than an invented one.

- **A TCP tunnel can tell its backend the visitor's real address (`proxy_protocol:`).** A tunnel delivers bytes to the backend over a fresh local connection, so the backend saw a connection from the client process and the visitor's address was lost at the last hop: every postgres log line said localhost. With `proxy_protocol: true` on a tunnel, the server now carries the address it observed in the stream-open frame and the client writes a PROXY protocol v2 header before any payload byte. Off by default and per tunnel, because this is a statement about the backend rather than a preference: nginx, HAProxy and MySQL read the header, postgres and redis do not, and a backend that is not expecting it reads it as protocol garbage and drops the connection. It never invents an address, an older server that reports none, or an address that does not parse, means the connection is relayed with no header rather than with a fabricated one, since a receiver acts on what the header says. Mixed address families (an IPv6 visitor reaching an IPv4 backend) cannot be expressed in the format and are treated the same way. The header's destination fields carry the backend's own address, the one this side can state truthfully.

- **Autoscaling can now ask for less, not only for more.** Scale-in was left entirely to a client noticing it was idle, which only ever solves 1 to 0: `idle_timeout` retires a whole client process, so a pool that scaled out to six stayed at six until traffic stopped completely. The scaling loop now emits a `scale_in` reason with a *lower* desired capacity to the same endpoint, so it still kills nothing and Aperio stays the sensor and the policy rather than the orchestrator. Two asymmetries with scale-out are deliberate: utilization has to stay below **half** the target rather than merely below it, which is the hysteresis that stops a pool hovering at its target from scaling out and in on alternating samples, and it has to stay there for **four** windows rather than one, because being an instance short costs latency on live traffic while being one over costs money. It never asks for the last instance to go; 1 to 0 remains the client's own decision, since the client knows about requests in flight that the server does not. (The other half of the backlog entry, a global cooldown, turned out to be already per-bind.)

- **Config authoring help: template variables, a suggestion for a typo'd key, and a warning for a literal secret.** `${NAME}` and `${NAME:-default}` in a client config file are expanded from the environment before the yaml is parsed, so one file can serve several environments instead of being copied per environment, which is how two files drift. Only that spelling is expanded: a bare `$NAME` is left exactly as written, because `$` appears in generated passwords, regular expressions and the shell snippets inside `run:`, and rewriting those to make templating prettier would corrupt files that work today. A variable that is unset with no default is an error naming it, not an empty string, since substituting nothing produces a file that still parses and means something else. Separately, a key nothing recognizes used to be ignored in silence, which is the most expensive kind of typo, the file says the setting is configured and the behavior says it is not; unknown keys now warn and name the key they were probably meant to be, at the top level and inside `services:` entries, checked against the same generated schema editors complete from, and only when the guess is close enough to be worth acting on. It stays a warning, so a file carrying keys for a newer client than the one running still starts. Finally, `aperio-client check` warns when a credential is written into the file literally rather than as `${VAR}`.

- **Three client lifecycle knobs: `pid_file`, `startup_delay` and `depends_on`.** Small operational sugar, and worth naming what it is: a process supervisor does all three better, which is why these are conveniences rather than mechanisms. `pid_file` writes the process id where an init system can find it and removes it on a clean exit, but not after a crash, since a stale pid file would have an init system signalling whatever process now holds that number; a file it cannot write is a warning, not a refusal to start. `startup_delay` holds a service back for a backend that starts alongside the client, and only the first connection of a parallel pool waits, so a stagger does not become a per-connection delay. `depends_on` waits for other services in the same file to have a live tunnel and then **proceeds anyway** after sixty seconds, because a dependency that never arrives must not keep a service that could be serving traffic off the air. What makes that bound safe is that the three ways it can be wrong, a name that is not in the file, a service depending on itself, and a cycle, are all refused at startup: at runtime each of them ends with everybody waiting out the grace period and then starting, which looks exactly like working.

- **Split probe endpoints for container runtimes: `/aperio/healthz` and `/aperio/readyz`.** `/aperio/health` builds a JSON document with counters and takes two locks to do it, which is more than a `HEALTHCHECK` every five seconds needs, and under contention a probe that waits on a lock reports a busy process as a dead one, at the worst possible moment to restart it. `/aperio/healthz` answers the only question liveness actually asks, is the process still serving HTTP, with `200` and an empty body and no locks. `/aperio/readyz` answers the different question a load balancer asks, and answers `503` from the moment a shutdown signal arrives while the process is still serving: that is the other half of `shutdown_drain`, readiness turns off so no new requests are routed here, and the drain gives the ones already in flight time to finish. Restarting on readiness would kill the very drain it protects, which is exactly why the two are separate endpoints. Both need no credential, like `/aperio/health`.

- **Two backend settings became per-service: `connect_timeout` and `min_tls_version`.** Both were global, which meant a client with a loopback backend and a backend across a VPN had to pick one number for both: either slow failure detection everywhere or spurious failures for the far one. `connect_timeout` is the TCP-connection budget, separate from `timeout`, which covers the whole request; unset, nothing changes and the one budget still covers both. `min_tls_version` (`1.2` or `1.3`) is the floor for an `https://` backend, per service so a fleet with one legacy backend does not have to lower the floor for all of them; a value that is not a TLS version is refused at startup rather than ignored, because a typo that quietly leaves the floor where it was is what makes a security setting worse than none. Both take the usual per-entry-over-top-level layering and have `APERIO_CONNECT_TIMEOUT` / `APERIO_MIN_TLS_VERSION`. The three other knobs the backlog grouped with these (pooled-connection idle timeout, the buffered/streamed threshold, the heartbeat interval) stay global: no deployment we can name is hurt by sharing one number for them, and five new keys across four config surfaces for two real cases is the wrong trade.

- **Captured bodies are syntax-highlighted, and the activity chart has a middle window.** The inspector showed JSON, XML and HTML as raw text, which is exactly where a body is hardest to read. Bodies are now tokenized and coloured, and a minified JSON body is re-indented as well. The highlighter is written here rather than pulled in: the inspector shows three shapes and a general-purpose library is hundreds of kilobytes of grammars for languages that never appear. Anything that does not parse, a truncated capture above all, and anything large enough that tokenizing would be felt, is shown exactly as before, because a highlighter that stalls the dialog has made the body harder to read, not easier. Separately, the activity chart jumped from a 60-second live window to a fifteen-minute one with nothing in between, so an incident that started four minutes ago was squeezed into the right-hand quarter of the chart where its shape could not be read; there is now a five-minute view, cut from the ring the server already sends rather than fetched again.

- **The topology graph shows client-to-client dependencies.** `--bind-tunnels` lets one client dial another client's exposed tunnel, so a database bound locally by three machines is three services that stop working when the declaring client goes away, and the graph knew nothing about it. Those edges are now drawn, and the API returns them as `consumers` on `/api/topology`. A consumer is identified by the address it dialed from, not by a client id, because it has none: it opens a fresh WebSocket per connection, so counted naively every `--bind-tunnels` invocation and every reconnect would be a new node and the graph would fill with ghosts of the same machine. Several processes behind one address therefore collapse into one node, which is the right grain for the question being asked and is honest, an address is something the server observed rather than something a caller claimed. An edge survives its connections by fifteen minutes, since a consumer that has just finished a query is idle rather than gone, and an idle edge is drawn dashed so it cannot be mistaken for a live one. Organizations see only dependencies pointing at their own clients.

- **`aperio-client api` reaches every admin endpoint the dashboard does.** Most admin operations had a subcommand, and the ones that did not sent automation back to hand-written `curl` with a bearer header. Eleven gaps are closed: `client config`, `webhook test`, `org custom-name`, `org oidc`, `publish`, `subscribers`, `explain`, `schema`, `activity`, `audit-csv`, and `edge-traefik` / `edge-ask`. What keeps it closed is a test rather than a habit: it scans the server's own route declarations and fails when one has no subcommand, so an endpoint added without its CLI counterpart is a failing build. Four routes are exempt with the reason written next to them, the SSE stream and the browser-bound WebAuthn and TOTP enrolment ceremonies, which a one-shot call cannot perform.

- **The shutdown drain is configurable, and can size itself from its clients.** Shutdown broadcast `ServerShutdown`, waited 200 ms for those frames to flush, and then ended long-lived connections so axum's graceful shutdown could complete. What it never did was wait for requests that were already in flight, which behind a load balancer is the difference between an invisible deploy and a handful of 502s: the balancer needs long enough to take the instance out of rotation, and the requests it already sent need long enough to answer. `shutdown_drain` (`APERIO_SHUTDOWN_DRAIN`) is that wait, in seconds. Written as `auto` it takes the longest drain budget the connected clients announce, the longest rather than the average, because the drain is over when the slowest client has finished; a client is not the operator, so `auto` is capped at 30 seconds, which is the orchestrator grace period it is really racing. The default is unchanged, `0`, so no deploy starts waiting because of a version bump. The forced-exit fallback, a fixed ten seconds until now, is `shutdown_timeout` (`APERIO_SHUTDOWN_TIMEOUT`).

- **A client can label its own metrics (`metrics_labels:`).** One Prometheus scraping one Aperio server saw every client's series under the same name, distinguished only by `client_id`, so telling `prod` from `staging` meant writing relabelling rules against ids the client already knew the answer for. A client can now announce `metrics_labels: {env: prod, region: eu-west}` (or `APERIO_METRICS_LABELS=env=prod,region=eu-west`), and those labels are attached to its own `aperio_client_requests_total` series. Because these come from clients and label cardinality is how a metrics backend dies, the server validates and caps them on arrival rather than on the way out: at most 8 labels, names must be Prometheus-legal and may not be ones the server writes itself (`client_id`, `job`, `instance`, …), values are bounded and escaped. An invalid label is dropped and the client's remaining labels are kept, since a typo is not a reason to lose the metrics of a client that is otherwise fine.

- **The access log can be sampled instead of switched off.** At high volume the choice was between a line for every request and no request log at all, and operators facing a log bill picked the second. `access_log_sample_rate` (`APERIO_ACCESS_LOG_SAMPLE_RATE`) keeps a fraction of successful requests, thinning out both the `aperio_access` event and the access-log file. Sampling is deterministic rather than random: `0.1` is exactly one line in ten, where a coin flip would give ten in a hundred only on average, and the whole point of turning the volume down is knowing what the volume now is. A response of `500` or worse is always logged whatever the rate says, and so is every refused or failed request, because the line somebody goes looking for is precisely the one that went wrong. The dashboard's counters, the latency histogram and the rate charts are fed before the sampling decision and stay exact.

- **`connections:` can be a range, and the pool sizes itself.** A service that wanted headroom for its busy hour had to hold that many connections around the clock, because `connections: 8` meant eight sockets, eight reader tasks and eight writer tasks from the moment the client started until it stopped. Written as `connections: {min: 1, max: 8}`, the client opens the floor and grows towards the ceiling while requests pile up, then gives connections back when they stop. Growth is driven by requests **in flight** rather than by a request rate, which is what tells a thousand fast requests (one connection is plenty) apart from ten slow uploads (they need room to run in parallel); the pool opens one connection at a time and waits to see whether it helped, and it is far slower to shrink than to grow, because being one connection short costs latency on live traffic while being one over costs a little memory. `min` connections are never retired, so the service answers the moment the client starts, which is the thing a "connect on first request" scheme would have given up. A plain `connections: N` is unchanged, exactly N connections opened at startup and kept: elasticity is opt-in because more connections is not automatically faster, and on a host where client and server share CPU the throughput curve has a peak. The bandwidth share is divided by `max`, so a growing pool cannot exceed the budget the file declares, the server's `max_connections_per_service` still wins over the ceiling, and the dashboard reports the connections a service actually has open rather than the number it might reach. Also settable as `APERIO_CONNECTIONS_MIN` / `APERIO_CONNECTIONS_MAX`.

- **`serve:` emits an `ETag`, so an unchanged file is not sent twice.** The static file server already did the hard part of HTTP file serving, single-range `206` responses for video scrubbing and resumable downloads, but it had no validator, so every reload of an unchanged file shipped the whole body again. Responses now carry a strong `ETag` derived from the file's size and modification time (the shape nginx uses, and for the same reason: there is no content hash to hand and computing one per request would cost more than the transfer it saves). A request carrying a matching `If-None-Match` gets `304` with no body, on `GET` and `HEAD` alike, and the comparison is weak as the RFC asks, so `W/"x"` and `"x"` are the same entity. Because the validator is strong, `If-Range` is now honoured rather than declined: a resumed download whose file has not changed continues, and one whose file has changed gets the whole new file instead of a splice of two versions.

- **Alert rules you write yourself (`alert_rules:`).** Two threshold rules were built in, error rate and client-down, and everything else an operator might want to be told about needed another pair of environment variables and another branch in the alert loop. A rule now names a quantity the server already measures (`connected_clients`, `pending_requests`, `store_bytes`, or `rss_bytes` on Linux), a bound (`above` or `below`), and optionally how long the condition must hold (`for`). The sustain window applies in both directions, to firing and to resolving, so a value resting on its threshold cannot alert and resolve on alternating ticks. Rules emit the same `alert_triggered` / `alert_resolved` events as the built-in ones with `kind` set to the rule's name, so existing webhook receivers need no changes, and they are evaluated by the same ticker, which now starts when either kind of rule exists. A rule watching something this platform cannot read is reported at startup as one that will never fire, rather than firing on a fabricated zero, and a malformed rule refuses startup naming the rule.

- **The backend can be told which client, organization and token served a request.** A multi-tenant backend behind one tunnel had to infer who it was answering for. With `identity_headers` on, a proxied request carries `x-aperio-client-id`, `x-aperio-org` (absent for the master organization) and `x-aperio-token`, added per dispatch attempt so that after a failover they name the client that actually served it. Off by default, because they are new trust surface and a backend should start believing them deliberately. Independently of the setting, **inbound `x-aperio-*` headers are now stripped from every proxied request**: the namespace belongs to the server, so a visitor cannot forge one, and a backend that trusts these headers can do so without also having to check whether the announcement happens to be enabled.

- **`include:` splits a client config across files.** One `aperio.yaml` stops scaling at twenty services, or when different teams own different entries. An `include:` list reads other files first, with one rule: an included file's keys are used unless the including file sets them, and sequences of mappings (`services:`, `subscribe:`, `expose:`) concatenate, so a fragment adds services rather than replacing them. Includes merge in the order written, later over earlier, and the including file wins over all of them. Paths resolve relative to the file that wrote them, so a fragment means the same thing whichever directory the client starts from. Chains nest up to five deep, and a cycle, a missing file or a malformed `include:` is an error naming the file rather than a silently partial configuration. Hot-reload follows includes too: it watches every file that contributed and re-reads the set on each change, so adding or removing an include is picked up rather than leaving the watcher looking at the wrong files.

- **A webhook can be test-fired from the dashboard.** A webhook configured wrong was discovered the next time something actually happened, which is the worst moment to find out. Each webhook now has a *Test* button (`POST /aperio/api/webhooks/{id}/test`) that sends one synthetic `webhook_test` event through the real delivery path, the outbound policy check, the signature, the same client and timeout, and reports what the receiver answered: its status and how long it took, or the reason it failed. The delivery is recorded in the log like any other. It is sent once with no retries, because the caller is waiting for the answer and a success on the fourth attempt shown as a success would hide the very failure being tested for, and it carries its own event name so a receiver that switches on `event` can ignore it rather than acting on a deploy that never happened.

- **A client reports on itself, not just on its backend.** Everything the server knew about a client was whether it was pinging and whether its backend answered, so a host at its CPU limit, a machine swapping, and a link whose round trip has quietly gone from 8 ms to 400 ms all looked identical from the other end. Each heartbeat now carries the round-trip time of that tunnel connection as the client measures it (from its own ping to the matching pong), the jitter between consecutive round trips, how many times the connection has been re-established since the client started, and the client process's CPU percentage and resident memory. They are shown in the dashboard's clients table and carried by `/aperio/api/stats`. The round trip is the figure that separates "the backend is slow" from "the tunnel is slow", which the server could not tell apart before. The two process figures are read from `/proc`, so they are Linux only and are absent elsewhere rather than approximated; inside a container they describe the process rather than the cgroup. Everything is optional and additive, so an older client is unaffected, and a client that stops reporting a figure shows nothing rather than its last value, which would age silently while looking current.

- **A `subscribe:` entry's `run:` command takes its own environment.** The client already set `APERIO_MESSAGE_TOPIC` and `APERIO_MESSAGE_ID` for every run, but there was no way to give a subscription's command the values that belong to it (which environment it deploys, which channel it posts to), so they had to come from the client process's own environment and could not differ per subscription. An `env:` map on the entry adds them. They are applied *before* the two variables the client sets, so a declaration cannot shadow them: a command reading `APERIO_MESSAGE_TOPIC` must be able to trust that it describes the message it is handling.

- **Health probes speak gRPC against gRPC backends.** `h2c://` and `h2://` are documented targets for gRPC services, but the health probe sent a plain HTTP GET, which a server speaking HTTP/2 with prior knowledge and routing by method name cannot answer, so the documentation ended up advising an explicit URL somewhere else entirely. Against an h2 target the probe now calls the standard `grpc.health.v1.Health/Check`, and `health.endpoint` names the gRPC service to ask about, with `/` meaning the server as a whole. Healthy requires all three of a `200`, a `grpc-status` of `0` (accepted from the headers or the trailers, since a gRPC error may arrive either way) and a `SERVING` status in the message; anything unparsable counts as unhealthy rather than being guessed at. An absolute `http(s)://` URL still means an ordinary HTTP probe, for a backend exposing health on a separate port, and a target with no probe configured is unaffected: nothing starts probing that was not probing before. The two protobuf messages involved have one field each and are encoded by hand, so this adds no dependency.

- **Scheduled maintenance windows (`maintenance_windows:`).** Maintenance mode was a switch somebody flipped, with an optional TTL, which covers the unplanned outage and nothing else: a window at 02:00 every Sunday meant an operator setting an alarm. A recurring window is standing configuration rather than a runtime action, so it is written in `aperio-server.yaml` next to the other structured sections, which is also what makes it survive a restart (the runtime flags are in-memory and do not) and reload without one. Each entry takes a `hostname` in the same shapes a flag accepts, `from`/`to` as local `HH:MM`, an optional `days` list, an optional `reason`, and an IANA `tz` defaulting to UTC. While a window runs, matching hostnames answer exactly as a flag would, with `Retry-After` pointing at the end of the window. A `to` earlier than `from` wraps past midnight, and `days` then names the day the window *starts*, so `22:00` to `02:00` on `[sat]` is Saturday night into Sunday morning rather than two half-windows. The zone is a named one rather than a fixed offset, which is the point: 02:00 stays 02:00 across a daylight-saving change. A malformed entry refuses startup instead of being skipped, since a window that silently never fires is a deploy nobody stopped.

- **`GET /aperio/api/logs` takes filters.** The recent-request window could only be fetched whole, so anything selective had to pull all of it and re-implement the matching the dashboard already does in the browser. It now accepts `status` (an exact code like `404`, or a class like `4xx`/`5xx`, where a failed request with no status counts as `5xx`, matching how the dashboard buckets it), `method`, `path` (a case-insensitive substring of the URI) and `limit` (newest first). The predicates combine with AND, an empty parameter is not a filter (so a form submitting `?method=` does not mean "match nothing"), and the caller's organization fence is applied before any of them. The unfiltered call is unchanged, including its oldest-first order, which the live view relies on.

- **One request id joins the visitor, the server and the backend.** The server has always minted an id per proxied request and used it internally, but it neither read an inbound `X-Request-Id` nor told anyone what the id was, so a visitor's trace ended at the edge and a backend log line could not be joined to the server's own. The id is now sent to the backend and echoed on the response, under `request_id.header` (default `x-request-id`). Adopting the visitor's own value is opt-in through `request_id.trust_inbound`, off by default because the header is attacker-supplied: trusting it lets any visitor decide what lands in your logs, or repeat someone else's id. An adopted value must be at most 128 characters of `A-Za-z0-9-_.:/+`, so it cannot forge a log line or look like two header values, and anything else falls back to the server's own id. The internal id that keys in-flight requests stays server-minted whatever happens, since a visitor able to choose it could collide with another request and be handed its answer. Any inbound copy of the header is dropped before dispatch and the backend's own echo is dropped on the way back, so exactly one value travels in each direction. Set `request_id.enabled: false` (or `APERIO_REQUEST_ID=0`) to restore the previous behavior of setting no header at all.

- **Backend retry and a circuit breaker, on the client's own hop.** The server could already fail a request over to another client (`failover`, `retry_on_5xx`) and eject one that keeps misbehaving (`outlier_ejection`), but the client's hop to its own backend had nothing: one refused connection was the visitor's answer, and a backend that was simply down got dialed once per request for as long as the traffic lasted. Two new per-service blocks, `retry: {attempts, backoff, all_methods}` and `circuit_breaker: {failures, open_for}`, both also settable at the top level as the default for every entry and through `APERIO_RETRY_*` / `APERIO_BREAKER_*`. Both are off by default. Retrying covers only failures that happen before a response head arrives, and only requests that can be replayed, since a streamed upload is consumed by its first attempt; non-idempotent methods are excluded unless `all_methods` opts in, the same trade the server's `failover.all_methods` names. While the breaker is open the backend is not dialed at all and the visitor gets its `502` immediately, and after the window one request is let through to probe recovery. A response head of any status counts as a success: a `500` is a backend that is up and answering, and refusing to dial it would turn an application error into an outage.

- **The audit log is searchable and exportable.** `GET /aperio/api/audit` took no parameters at all: it returned the most recent 200 events and nothing else, so a log that is deliberately hash-chained, retention-governed and organization-isolated could not answer the question it exists for, what a given user did on a given day. It now takes `event`, `actor`, `q` (a case-insensitive substring of the details, kind or actor), `from`/`to` (unix seconds or `YYYY-MM-DD` in UTC, both inclusive) and `limit`. Any filter switches it from the in-memory ring to a search of the durable log itself, the active file plus every rotated generation, newest first; with no parameters it answers from the ring exactly as before, so the dashboard's polling view costs nothing extra. `GET /aperio/api/export/audit.csv` answers the same query as CSV for an auditor who wants the rows in a spreadsheet. The organization fence is applied around the search rather than inside it, so a filter can only narrow what a caller may already see. The dashboard's *Audit Log* section gained the matching filter fields and an export button that carries the current filter; a filtered view pauses live polling, since it is a deliberate query over files rather than a live tail.

- **`denied_ips:`, a source-IP deny list, the inverse of the allowlists.** `allowed_ips` says who may in and `admin_allowed_ips` fences the admin surface, but until now there was no way to say "this address never gets in": blocking one scanner meant turning on an allowlist that locks out everyone the operator did not think to name, or reaching for the fronting proxy. A denied address is refused everything the server answers, checked at the outermost layer before any other rule, so it covers proxied traffic, the dashboard and its API and the tunnel endpoints alike, and a blocked request cannot spend a rate-limit bucket, occupy a request slot or reach a backend. The client IP is resolved with the same proxy-trust rules as everything else, so a deployment behind a trusted proxy blocks the visitor rather than the proxy, and one without `trust_proxy` cannot be talked out of a block by a forged header. Blocked requests get `403` rather than a stealth answer, because unlike a per-service `allowed_ips` rejection this is an explicit server-wide block and an operator who has locked themselves out needs to be able to see that. Written as a yaml list it is hot-reloadable, so an address can be blocked mid-incident without a restart; an invalid entry refuses startup rather than applying a partial deny list.

- **A `routes:` entry can now carry policy, not just a static answer.** An entry with neither `redirect` nor `respond` no longer fails to start: it becomes a policy rule that annotates the proxied traffic matching its hostname and path, so per-route settings are written next to the route they govern instead of scattered across the file. Three fields to start with: `timeout` (seconds to wait for the serving client on that route, winning over the client's per-service `response_timeout` and the global one, since it is the operator's own configuration), `headers` (`request:`/`response:` edits in the same shape as the server-wide `headers:` section, applied after it so the narrower rule gets the last word, which is also how a per-route `cache-control` is set), and `rate_limit` (the same token bucket as a `rate_limits:` rule without repeating the hostname and path, and winning over one that matches the same request). Answer rules and policy rules are matched independently, each first-match in file order, so a redirect after a policy entry still fires; combining both kinds on one entry is refused at startup, because a static answer never reaches a backend and so cannot carry backend policy. `--check-config` reports the same problem before a deploy, and its shadowing lint now compares each kind only against its own.

- **`rate_limits:` rules take an optional `methods:` list.** A rule can be scoped to the verbs that matter, so a write path is throttled while reads of the same route are not. Rules that differ only by method own separate buckets, and a rule without `methods:` still covers every verb, so existing files behave exactly as before.

- **`scripts/profile-request.sh`: the cost of one request, stage by stage.** Sends a single request through the tunnel, finds its capture on the server, and renders the inspector's microsecond timeline as a waterfall (queueing, routing, tunnel transit each way, backend time, delivery), next to what curl saw from the visitor's chair. One request instead of a load test: it answers "where does the time go" without heating the machine or needing a benchmark window. Needs the master token and the inspector left on; streamed responses show the round trip to the response head, with the body accounted in the visitor delivery gap.


- **An organization's hostname allowlist takes a partial leftmost label.** `*-pi.robogon.com` (or `dev-*.robogon.com`) matches one label around the placeholder, so a tenant whose fleet is named by convention can be fenced to exactly the names it owns. Until now the only wildcard was `*.robogon.com`, which is the whole domain and rather more than such a tenant owns, and the refusal message offered nothing else. One placeholder, in the leftmost label only, the same shape `random_subdomain` already accepted; two placeholders are refused rather than silently honouring the first. The fence, the maintenance ownership check and the per-request matching all understand the new shape, and where the maintenance check cannot prove which of two partial patterns owns a name it now refuses rather than guesses. The maintenance pane's hostname field names the shape alongside the other two.

### Changed

- **`GET /aperio/api/explain` says every step twice, once as English and once as data.** The report was built out of finished sentences, which is right for the CLI and wrong for the dashboard: the screen has eight languages and there is nothing to be done with `no connected client serves this hostname and path, though 2 could: c-drain (draining), c-sick (its backend health probe is failing)` except show it in English, which is what it did. Each step now also carries a `code` naming the sentence (`routing.none_ineligible`, `ineligible.draining`, `maintenance.flagged_reason_until`) and a `params` object holding the values it interpolates, with `summary_code` and `summary_params` doing the same for the one-line answer; the dashboard renders those and is translated in all eight. `detail` is unchanged and still a finished English sentence, so a script or an API consumer reading it needs to do nothing. There is one code per *sentence shape* rather than per stage, a maintenance flag with a reason and a lifting time is a separate code from one with neither, so a translation is a whole sentence instead of fragments glued in an order the language may not use. A code the dashboard does not know, from a server newer than it, falls back to the server's `detail`. Clients in the report are also named rather than identified: the same label the clients table uses, the `custom_name` an operator set or the `name` of the `services:` entry, with the connection id carried alongside for anything that acts on it and shown only where two connections of one service would otherwise read identically. A report that said `028258c2-a035-45a2-b31a-39df3ef7b8d1 (draining)` now says `master@payments (draining)`, and connections answering to the same name are counted rather than repeated, so a service with `connections: 2` reads `axum ×2` instead of the word twice with two uuids to tell it apart.

- **The client's tunnel library is current, and its receive path stopped copying.** The client was pinned to tokio-tungstenite 0.23 while the server's axum already pulled 0.29, so the build compiled two copies of the WebSocket stack; the client is now on the same 0.29 and the duplicate is gone. The upgrade is also what unblocked the other half: a binary frame arrives as refcounted `Bytes` rather than `Vec<u8>`, so a relayed TCP chunk, a UDP datagram, a proxied WebSocket frame and a streamed request-body chunk are now slices of the frame that arrived instead of copies of it, the same change the server's receive path got earlier. Outgoing frames are built as `Bytes` too, so they are no longer copied again into the write buffer. Note where this does and does not help: it is the *upload* and *relay* direction, since downloads were already covered.

- **The server batches its writes to a client, as the client already did.** Each outgoing tunnel frame paid its own flush, which is a syscall per frame, and this is the busier side under fan-out. The writer now feeds everything already queued behind a message and flushes once per batch, the same change the client's writer got. No latency is traded for it: a message is never held waiting for company, only joined by what was already waiting. Bandwidth pacing still spends per frame rather than per batch, since its whole purpose is to stop the server pushing faster than the client's link can drain, and a paced connection flushes what it has before sleeping out its debt rather than holding finished frames. Unmeasured, reasoned from the code; the technique is the one measured on the other side.

- **Every setting with a default now states it in the yaml schemas.** The JSON Schema descriptions for `aperio.yaml` and `aperio-server.yaml` (what an editor shows on hover and completion) gained a trailing "Default: `value`." sentence on 127 fields, sourced from the code's actual fallbacks, so an operator no longer has to cross-reference the docs table to learn what leaving a key unset means. Three stale descriptions found on the way were corrected: `token_expiry_warning` is seconds, not days; `alert.client_down` is the seconds a service may stay down, not a connected-client floor; `backup.dir` has no default and is required to enable backups.

- **The client sends streamed bodies as full frames, flushed in batches.** Once a response switches to streaming, the client used to forward each piece exactly as the backend handed it over, typically well under the 128 KB frame size, and every frame paid its own allocation, WebSocket mask pass and flush. Backend chunks now accumulate into full frames, and the tunnel writer flushes everything queued behind a message in one go instead of once per message. A backend that goes quiet gets its bytes flushed immediately, so trickling streams (server-sent events, long polling) see no added latency; only streams with more data already waiting are batched. Applies to all three backend paths (HTTP/1, HTTP/2, Unix socket). Unmeasured, reasoned from the code.

- **A streamed response body stopped paying per chunk for the whole server.** Every chunk of a streamed (over 256 KB) response used to take the global stream-registry lock to find its consumer, copy its payload out of the WebSocket message, and take three more shared locks to account its bytes; all of it once per 16-128 KB chunk, across every connection at once. The registry is now consulted once per stream and cached on the connection, the payload is a refcounted slice of the message that arrived, and the byte accounting (server totals, organization bytes, token daily quota) is charged in 1 MiB batches with the remainder settled when the stream ends, so quotas see the same totals no later than the stream's end. The TCP, UDP and relayed-WebSocket frames lose the same per-chunk copy. Unmeasured, reasoned from the code: a 2 MB-body benchmark held the same throughput while connection count and flow-control watermarks changed, which is the signature of exactly these shared per-byte costs.

- **Tunnel protocol v7: the relay payloads stop being base64.** A TCP chunk, a UDP datagram and a binary WebSocket frame now travel as raw bytes in a tagged binary frame, where they used to be base64-encoded inside a JSON message: a third more bytes on the wire plus an encode, a JSON parse and a decode on every 16 KB chunk, in both directions. This is the throughput ceiling for anything moving bulk over `expose:` or an emergency TCP tunnel, and the last base64 leg of the tunnel; HTTP bodies went binary in v5/v6. Negotiated per stream and per direction, so a peer below v7 keeps receiving exactly what it received before, and text WebSocket frames are unchanged since they were never encoded.

  One trade to know before upgrading, if and only if you run with `tunnel_compression` on: these payloads used to ride inside a text frame, which the writer deflated whole, and a binary frame skips that path. Tunnelling a *compressible* protocol (a plain-text or uncompressed database wire protocol) over TCP or a raw expose port therefore sends more bytes than before, while spending less CPU per byte. Nothing breaks and no setting changes; for already-encrypted or already-compressed streams, which is what the relay path is usually carrying, v7 is a straight win in both.

- **A cache hit stops copying the body under the lock.** The response cache held its bodies as `Vec<u8>` and cloned the whole vector while holding the cache lock on every hit, so a hot large response serialized every other cacheable request behind a full memcpy. The body is `Bytes` now; the clone is a refcount bump, and the lock is held only that long. The cache's own recency and hit accounting still need a write lock (turning that into a read lock is a separate, larger rework of the cache internals, recorded rather than rushed). Unmeasured, reasoned from the code.

- **The live-clients map is a read/write lock.** Routing, statistics, pub/sub fan-out and the maps all read the connected-client set on every request, while only a connect, a disconnect, or a heartbeat's announcement mutates it; under the previous mutex those readers serialized with each other and with every heartbeat on one queue. They take a shared read lock now, so concurrent requests read it at once; the mutating paths take the write lock, unchanged in behavior. Unmeasured, reasoned from the code.

- **Per-request bookkeeping moved off the request's back.** Recording a request for the dashboard (the slowest-endpoints report, the sparkline trends, the activity ring, the recent-traffic list) took four sequential global locks on the serving worker. The request now queues one event and a collector task does the writes; when the queue is full or absent the write happens inline exactly as before, so nothing is lost either way. Unmeasured, reasoned from the code: this removes cross-request lock contention, not work.

- **The access log stopped blocking requests.** The per-request line used to be written synchronously, under a process-wide lock, from whichever worker served the request: a slow disk stalled that worker and the lock serialized every request in the process on one file descriptor. One writer task owns the file now; the request path queues the line and moves on, and a queue the disk cannot drain drops lines and says how many rather than slowing traffic. Retention pruning and the right-to-erasure purge rewrite the file through the same task, so a rewrite can never race an append. Unmeasured, reasoned from the code.

- **The routine sweeps left the request path.** The per-IP and per-route rate-bucket cleanups and the expired-session sweep used to run inline, under their lock, on the back of whichever request happened to draw the five-minute tick; with a large map that request, and everyone queued behind the lock, paid for the whole retain. They run on a background beat now. The inline size failsafes stay, and an expired session is still refused on lookup regardless of the sweep. Unmeasured, reasoned from the code: the change removes a periodic tail-latency spike, not average cost.

### Removed

- **A config file no longer describes a service at the top level.** `target:`, `serve:`, `hostname:`, `path:`, `tcp_target:` and `target_health:` (or `health.endpoint`) written at the top of `aperio.yaml` only ever did anything in a file *without* a `services:` list, so a reader had to work out which of two shapes they were looking at before they could read anything else. Deprecated since 0.6.0, warned about at every startup since, and removed here as announced. A file that still writes one is **refused**, with the keys named and the edit spelled out, rather than being ignored: a client running while its own file says `target:` and it is serving nothing is the one outcome an operator cannot debug from what they are looking at. Migrating is mechanical, indent them under one `services:` entry. Single-service mode is unchanged where it belongs, on the command line and in the environment (`--target`, `APERIO_TARGET`, the positional target), and a top-level `health:` block without an `endpoint:` is still the defaults every entry inherits. A file declaring `version:` gets the same notice through the upgrade report before it upgrades.

What went wrong is stored now, and the sentence is built at render, where the language applies.

- **The dump carries the activity rings.** `GET /aperio/api/export` already offers the statistics and the uptime history for a migration, on the stated principle that refusing to carry history only means someone copies `aperio.db` instead. The two-hour and one-day activity rings became persistent state in this release and were left out, so a restored server had every other number and a blank long-range chart. `?include=activity` carries them, opt-in like the other history sections, with the same organization gate: without `organizations`, only master's rings travel. On import anything that has aged out of the ring is dropped, as it is when they are read back from the store. The fine ring is deliberately not carried, for the same reason it is not persisted: fifteen minutes of five-second slices is the view of *right now*, which a dump cannot hold.

- **Switching the activity chart's range showed the previous range's data under the new labels.** The poll kept its last answer until the next one arrived, and nothing discarded a slow reply to the range that had just been left, so a day of traffic could sit under a "last 15 minutes" heading, and an out-of-order reply could put it back there until the next poll, up to a minute later on the day view. The poll now takes a key naming what it is asking for: changing it clears the data and discards anything still in flight from before the change.

- **The OTel bridge's `https` transport kept posting to the server it started with.** It captured the server URL and the tunnel token when it started, so a reload that moved the server or rotated the token left telemetry going to the old address, or refused by a credential that no longer existed, while the tunnel itself had already followed the change. Worse, the warning added for the parts of the bridge that genuinely cannot be rebuilt did not fire here, because it only watched the `otel_bridge:` block, so an operator had every reason to think the change had been applied. Both are read per export now and follow a reload; the warning is narrowed to what really needs a restart, the listeners, the queue and the transport.

- **A reload could drop a message that should have run a subscription command.** The dispatcher took its broadcast subscription inside its own task, so it heard nothing until the runtime first polled it, and a reload stops the previous dispatcher before starting the replacement. Anything delivered in that window reached neither: the command simply did not run, with nothing said. The subscription is taken before the task is spawned, and the replacement is subscribed before the incumbent is stopped, so the two overlap rather than leaving a gap. The overlap is the safe direction, since a message the old dispatcher is already handling is not re-delivered to the new one.

- **A reload silently dropped a local subscriber's hold on a filter.** A filter the new configuration still named was rebuilt from scratch with no holders, so an SSE connection or MQTT session that had asked for it lost its claim while everything still appeared to work. The failure showed up only at a later reload, when the filter left the file and was given back with that subscriber still attached and still expecting messages. Holds are carried across a reload now, whether the filter stays in the file or leaves it.

- **A reload that could not bind a moved message face left the process with no face at all.** The running face was stopped first and the new address bound second, so a port that was already taken meant both were gone, under a log line that said the previous configuration had been kept. The new address is bound first now and the old face stopped only once that succeeded, which is also what makes that log line true.

- **Stopping a message face left the sessions it had already accepted running.** Each accepted connection is its own task, so ending the acceptor did not reach them: a face removed from the configuration went on serving every SSE stream and MQTT session it had already taken, for as long as the client cared to hold it open. The switch that stops a face now reaches its sessions too.

- **A hot-reload changed only the services, while the documentation promised every setting.** The local message faces (`messages_listen`, `messages_mqtt_listen`), the `subscribe:` filters and their `run:` commands, and `idle_timeout` were read once at startup and never again: a face removed from the file kept listening, one whose address moved kept the old port, and an edited subscription needed a restart. A reload now re-applies all of them, after the new configuration has been validated so a reload that is going to be rejected cannot move a listener on its way to being rejected. A face whose address did not change is left alone rather than rebound, since rebinding would drop the connections it is serving. A filter a local subscriber is still holding survives a reload that dropped it from the file, because that subscriber is still there. `otel_bridge:` is the one exception, its queue is held by whichever tunnel connection is live, and a reload that changes it now says a restart is needed instead of ignoring the edit in silence.

- **A stalled `h2://` or `unix://` backend was not retried.** The two paths gained `retry:` in the same release, but a timeout on the response head answered `504` immediately instead of going round the retry loop it was standing in. `retry.attempts` is documented to cover a failure before any response arrives, in so many words including a timeout on the head, and the HTTP/1 path has always done so; a backend that has stalled is also the case an operator most expects a retry to cover, and it was the one case that skipped it. A timeout is now an attempt like any other and still ends as a `504` when the attempts run out.

- **`retry:` and `circuit_breaker:` did nothing for `h2c://`, `h2://` and `unix://` backends.** Both are consulted in the HTTP/1 path, and the dispatch to the HTTP/2 and unix-socket paths happens before either of them, so a service on one of those schemes carried resilience settings in its config that were never read: a dead backend was dialed once per request for as long as the traffic lasted, and a failure that a retry would have absorbed reached the visitor. Both paths now check the breaker before dialing, record the outcome, and retry under the same two fences the HTTP/1 path uses (an idempotent method unless the operator opted in, and a body that can be replayed, which a streamed upload cannot). The HTTP/2 path also re-dials once for a connection the backend had already closed, since it pools connections just the same.

- **A subscription command that never read its stdin hung forever, and a timed-out one left its pipeline running.** The message payload was written to the command's stdin *before* the timeout was set up. A command that does not read stdin does not necessarily close it, it may simply be busy, and once the pipe buffer fills, which an ordinary 64 KB message does, the write blocks with no deadline over it: the runner hung for the life of the process, holding one of the `max_concurrent` slots the operator configured. The write is inside the budget now. Separately, killing the command killed only the `sh -c` and left whatever it had started running past the deadline; on Unix the command is given its own process group and the whole group is ended.

- **A configuration reload could drop a response it had just waited for.** The reload path announces a drain, waits for in-flight requests to finish, and then ended the connection by aborting its writer task, which discards whatever is still in that task's queue. A response reaches the queue *before* the request task decrements the in-flight counter the drain waits on, so the drain could pass while a response was still queued, and then the abort threw it away: the visitor saw a failure caused by a change that was meant to be invisible to them, which is the exact outcome the drain was added to prevent. The writer is asked to finish now, meaning "send what is queued, then stop", with a two-second bound so a connection that is genuinely gone cannot hold a shutdown open.

- **A visitor that hung up mid-request left an entry behind on the server.** A proxied request registers itself in `pending_requests` (a WebSocket upgrade in `pending_upgrades`), dispatches, and awaits the answer. If the visitor's connection drops, the handler future is dropped mid-await, taking its timeout with it, and every removal in the code is on a path that is no longer running. The only sweep that reached those entries ran when the *serving client* disconnected, so under a long-lived client the maps grew with every abandoned request, and `pending_requests` is an alert metric, so the leak reported itself as load. Both registrations now hold a guard that takes the entry back out when the handler stops existing.

- **An elastic pool counted connections that were never running.** The server announces a per-service connection ceiling and a connection above it stands down by returning, but the pool kept its handle and went on counting it: the dashboard and the Ping reported connections that had never opened, and the growth arithmetic divided the in-flight peak by a connection count that was too high, so a pool at its real ceiling could believe it had room. The pool drops finished entries on every tick and says so once. Connection numbers are now carried with the handle instead of derived from the pool's length, which stopped being the same thing the moment an entry could leave from the middle: a pool holding connections 1 and 3 would have been told to open "3" again, putting two clients with one id in front of the server.

- **Parallel connections of one service shared a single message writer, and deleted each other's.** The message bus keyed a connection's writer by the service label, and a service with `connections: N` gives all N connections the same label. So the second connection to come up evicted the first, the bus held exactly one writer no matter how many were live, and whichever connection dropped first took that writer with it: publishing then failed with "no tunnel connection is up" while connections were up and serving. Writers are keyed by the connection's own id now. Replacing an entry with the same id still happens and is still right, that is one connection reconnecting.

- **A connection the backend had already closed reached the visitor as a `502`.** The client keeps backend connections alive and reuses them, and a backend closes idle ones on its own schedule, so there is an unavoidable window where a request is written onto a socket the backend has just finished with. hyper reports that as `IncompleteMessage`, or as a reset, with no response head, and it was passed on as a gateway failure although nothing was wrong with the backend. Under load that window is hit constantly, which is why the same backend behind any mainstream proxy does not produce these. The client now re-dials once, silently and without backoff, for a request the existing fences already allow to be replayed. It is deliberately not governed by `retry.attempts`, which is off by default: that setting is about a backend that failed, this is the client's own connection pool racing the backend's idle timeout. A second such failure on the same request is a backend genuinely closing on the client and still reaches the visitor.

- **A connection's config view showed a stale connection count for an elastic pool.** The number a connection announces is how many the pool has open, but it was read once when that connection came up and then repeated in every heartbeat for the life of the connection. A pool that had since grown showed, say, `connections: 3` beside four live connections in the clients table, which reads as a discrepancy rather than as a pool doing its job. It is re-read on every heartbeat now.

- **A client announces its pool's floor and ceiling, so the dashboard can say the count is expected to move.** A pool sitting at its floor was indistinguishable from a fixed `connections: N` of the same size. The config view writes an elastic pool as the range the file wrote with the current size beside it (`connections: { min: 1, max: 5 }  # 4 open right now`); a fixed pool is unchanged. The `docs/configuration.md` section now also states the growth rule in numbers, the thresholds, the cooldowns and why they are asymmetric, rather than describing it in prose only.

- **Ending a connection on purpose was logged as a heartbeat failure.** The channel that ends a connection's socket loop carried no reason, and the receiving end logged every wake-up as `Liveness timeout triggered`, followed by `Connection to server lost`. So an elastic pool giving a connection back because the load had dropped, a configuration reload, and a shutdown all reported a link failure that had not happened, as a warning. The reason travels with the signal now: a deliberate close says so and the pool says why it retired the connection, while a genuine liveness timeout reads exactly as it did. For the same reason the drain line no longer claims "applying the configuration change" when the cause may have been a pool retirement; whichever of the three it was has already logged its own reason.

- **A server that accepted the connection and then said nothing held the client's dial open forever.** Only the TCP connect was bounded, so a peer that completed the handshake never left the reconnect loop nothing to do: no error, no retry, no move to the next candidate server, and the service simply stayed down without saying why. The TLS and WebSocket handshakes now share a 20-second budget, which any peer that is not hung finishes well inside.

- **`max_response_body` was enforced from the second chunk onwards.** The size check lived only in the arm that runs once a response is already streaming, so the chunk that starts the stream was never measured: a backend that delivered a body in one piece larger than the cap had it buffered, turned into the head of a stream and sent in full, and the visitor received a successful response several times the size the operator allowed. The three backend paths, HTTP/1, HTTP/2 and unix socket, all had the same shape and all now check before the chunk is used for anything. Passing the cap before anything has been sent is a clean `502` rather than a stream aborted halfway, since there is nothing in flight to truncate.

- **The OTel bridge buffered an export in full before checking its size.** The 8 MB fence was applied after the body had already been collected, which made it a description of what was in memory rather than a limit on it: a sender shipping something enormous was read to the end and only then refused, and several at once multiplied that. The fence is applied while reading now, so an oversized export is cut off at the fence.

- **A gRPC health probe could hang forever on a backend that sent headers and nothing else.** The timeout covered reaching the backend and receiving the response head; reading the body and trailers, which is where `grpc-status` and the `SERVING` value actually come from, sat outside it. A backend that answered `200` and then went quiet held the probe for the life of the process, and a probe that cannot finish cannot fail, so the backend kept whatever verdict it last had. The body is under the same budget as the head now.

- **A `min_tls_version` this build cannot honour no longer takes the whole client down on a reload.** The value was parsed inside the running service task, which had nowhere to return an error to and so called `process::exit(1)`: one typo in a hot-reloaded file ended every service in it, when the contract for a bad reload is a warning and the previous configuration kept. It is validated on the config path now, before any service is spawned, so a bad value is refused the same way every other invalid setting is, and `--check-config` reports it too, which it could not before because nothing on the validation path ever parsed the field.

- **The activity chart covers two hours and a day, at a resolution that scales with the span.** The ranges are now 60 s, 15 min, 2 h and 1 d; the 5-minute view is gone, it was the same fifteen-minute ring cut short in the browser and sat too close to its neighbour to be worth a button. The server keeps three rings side by side, 5-second slices over a quarter hour, 2-minute slices over two hours and 15-minute slices over a day, so every range is about sixty cells whatever it covers: a day at five-second resolution would be seventeen thousand points per organization, drawn into a few hundred pixels. `GET /aperio/api/activity` takes a `range=15m|2h|1d` parameter and still answers with the quarter hour when it is absent or unrecognized, so a caller that predates it keeps exactly what it had.

- **The two long activity ranges survive a restart.** They are written to the store on the same flush as the persistent stats and read back on boot, with anything that has aged out of the ring dropped, because a view covering a day that empties on every deploy answers "what happened overnight" with a shrug. The fine ring is deliberately not restored: fifteen minutes of five-second slices is the view of *right now*, and a restart is exactly the moment when right now changed.

- **A streamed response now reports where its time went.** The client attached its stage durations only to a buffered response, so anything over the streaming threshold, 32 KB on a modern client, told the server nothing at all about itself and the inspector showed a single tunnel round-trip row. That is exactly backwards: the large responses are the ones worth profiling. The stages now ride on the `ResponseStart` head as well, which is the same milestone a buffered response reports at and has the same two backend stages behind it. One row is genuinely missing there, the end of the backend body, because at the head the body is still arriving; the inspector and `scripts/profile-request.sh` show a single span from the backend's first byte to the head reaching the tunnel instead of inventing an end for it. The protocol change is additive in both directions: an older client sends no timings on the head and an older server ignores the field.

- **The request inspector showed one row where the server had measured four.** Everything before the request left the server was drawn as a single "queued & routed" span, although the server records three marks inside it: when a connected client became available, when the request was admitted past the concurrency limit, and when routing picked a client. `scripts/profile-request.sh` printed all four stages from the same capture, so the dashboard was the narrower view of identical data. It now tells them apart, which is what makes a slow request readable: waiting for a client, queueing behind the concurrency limit, and routing are three different problems with three different fixes. They are the server's own clock, so they are present even for a streamed response, where every later stage collapses into the one round-trip row.

- **The request inspector drew `+null µs` for a streamed response.** The waterfall has a detailed branch, six rows from the client's own stage timings, and a coarse one, a single tunnel round-trip row, for captures that do not carry them; a streamed response never does. The check that chose between them read `!== undefined`, and the server sends an absent stage as the JSON value `null` with the key present, so `null !== undefined` was true and every streamed response took the detailed branch and rendered its six rows as `+null µs → +null µs`. The comparison matches the wire now, and the type it is written against does too: those fields were declared optional in TypeScript while the server sends `null`, which is what let the compiler agree with the mistake. Making the type honest turned this into six compile errors, which is where a wire-format disagreement belongs. The stage calculation moved into `lib/timeline.ts` with tests, including one that asserts nothing rendered can be non-finite.

- **Two more places shipped English, and the i18n check now catches the whole class.** A name-validation message ("organization name is longer than 64 characters") and two sidebar strings, one of them read aloud by a screen reader, were never routed through the translator. They are now, and so is the rule that finds them: the check gained a third pass that flags prose in JSX text, in the attributes a browser renders or speaks, and in strings returned from a function. The predicate is narrow on purpose, since most English literals here are `aperio.yaml`, `5xx`, `ms` and `app.example.com`, which stay in English deliberately, and a check that flagged those would be turned off within a week. Verified against the bug that prompted it: putting `"5m ago"` back fails the build.

- **Relative times were never translated.** "5m ago", "just now", "never" and the rest are produced in `lib/format.ts`, which is not a component and so never had a translator to call; they shipped in English whatever language the dashboard was set to. The time helpers take the translator as a parameter now and every caller passes it, so a Turkish dashboard says "5 dk önce". The dates inside them are still left to the browser's locale, which knows the visitor's conventions better than a dictionary would. This is the class of gap the i18n check cannot see: it verifies that everything routed through `t()` is translated, not that everything visible is routed through `t()`.

- **The audit log's event filter could not be typed correctly.** The field was free text and the API matches `event` **exactly**, so `login` returned nothing at all while `login_success` and `login_failed` both sat in the log, and an empty result on an audit screen reads as "that never happened". It is a grouped list of the seventy event kinds the server records. Partial matching still lives in the search box, which does look inside the event name. A test checks the list against the server's own sources, so an event added without its filter entry fails the build: a hand-kept list would be right on the day it was written and wrong at the next release, and the missing name would be the newest one, which is exactly the one somebody is looking for.

- **The OTel bridge ignored a token's source-IP fence.** Its endpoint never read the caller's address and passed a placeholder of `127.0.0.1` to the token check, which is the value the token's `allowed_ips` list is judged against. A token allow-listing loopback, a plausible entry for a client on the same host, was therefore usable from anywhere on the internet, and one fenced to a private range was refused from the host it was issued for. It resolves the peer exactly as every other endpoint does now, honouring `trust_proxy` the same way. Only the OTLP endpoint was affected; every other credentialed path already did this correctly.

- **A config file included by two others was reported as a cycle.** `include:` tracked visited files in one list and used it both to detect cycles and to tell the hot-reload watcher what to watch. Those want different things: a cycle is a file that includes itself along the current chain, and the watcher wants every file that contributed. A root including two per-environment fragments that both include a shared one, which is the most ordinary layout there is, was refused as a cycle. The chain is now tracked separately from the watch set. Real cycles are still refused, and every contributing file is still watched.

- **`adaptive_concurrency` could raise a client's limiter above the configured `max_concurrent`.** Shrinking asks the semaphore to forget permits, and it forgets *at most* what is available; with every permit in flight, which is exactly the moment the backend is behind and the pool shrinks, it could take none. Giving back the difference later then handed the limiter more permits than the operator set, and it drifted upward with every cycle. Both directions now move by what the limiter actually did, so a shrink that could not finish simply finishes next window, the announced number never claims a ceiling that is not being enforced, and the limiter never exceeds the configured one.

- **A `--bind-tunnels` connection whose handshake never completed left a permanent dependency on the topology graph.** The edge was recorded before the WebSocket upgrade, and the upgrade's callback, which is what removes it, does not run when the handshake fails. Since an edge holding a live connection is deliberately never expired, the stale one stayed for the life of the process. It is recorded inside the upgrade now: a dependency begins when bytes can flow.

- **A `canary:` on a route that also answers named the wrong settings.** The startup error listed `timeout`, `headers` and `rate_limit`, so an operator who had written `canary:` was sent to look at three fields they had not used. A `weight` above 100 was also read as "everybody" rather than refused, and an empty `service` made the split silently do nothing; both are errors now.

- **Inspector eviction broke ties by hash order.** Fair-share eviction picks the organization holding the most captures, and its comment promised that ties go to whichever of them has the oldest capture. It did not: the winner came out of a `HashMap`, whose iteration order is arbitrary, so two equally busy tenants took turns at random. The tie is resolved by age now, as documented.


- **A configuration reload no longer drops requests that are still in flight.** When a reload stopped a service, its tunnel connection was torn down the moment the change was noticed, so whatever was being served through it failed: a visitor saw an error caused by an edit that was meant to be invisible to them. The client now announces `Draining` first, which stops the server dispatching anything new to that connection, waits for the in-flight requests to finish, and only then drops it. The wait is bounded by `reload_drain` (default 10 seconds, `0` restores the old immediate drop), so one stalled request cannot hold a configuration change hostage.

- **The `dashboard:` block's schema example no longer refuses to start the server.** The example still showed an `auth` key inside the block, the separate dashboard password whose removal was 0.6.0's security note, and the block rejects unknown keys, so pasting the example produced a file the server could not parse, written on the schema's own advice. The example is fixed and a test now parses every example in both schemas, so an editor completion can no longer suggest a configuration the parser refuses.

- **A maintenance flag set with a partial-label pattern now serves its 503.** The maintenance endpoint takes every shape the allowlist takes, and the partial one (`*-pi.robogon.com`) was accepted, stored and listed, and then matched no request at all: the read path only knew `*.domain`. An operator who flagged a fleet by its naming convention was told the flag was on while every device kept serving. The matcher now understands all three shapes, same as the fence that authorized the flag in the first place.

- **The explain view names which visitor gate would stop a request.** It only ever reported a password a *client* declared for its own service, so a server-wide `server_auth` or an OIDC configuration read as "no visitor gate" on a hostname that very much has one. All three are reported now, and the step names which of them applies, since a client's password and the server's live in different places and are changed by different people.

## [0.8.0] - 2026-07-31

### Security

- **The admin namespace is not proxied.** A path under `/aperio/` matching no route fell through to the proxy, so a typo in an API path, or a probe for an endpoint that does not exist, was answered with whatever a tunnel client happened to serve, under the URL the documentation calls the admin surface. Unmatched paths there are `404` now. The registered endpoints, including `/aperio/health`, `/aperio/ws` and the auth routes, are unaffected.

- **The dashboard's live stream now notices that the session it was opened with is gone.** The session check ran once, when the stream was opened, and the connection then lives for as long as the tab stays open: signing out, "sign out everywhere", an expiry or a disabled user all left it emitting live traffic and statistics to a caller who no longer had a session. It re-runs the same check on every two-second tick and closes as soon as it comes back empty, so a revoked session sees at most one more tick. It needs an already-authenticated session to reach, which is why this was a leak rather than a way in.

### Added

- **Tunnel protocol v5: a buffered response body travels as bytes, not as base64 inside JSON.** The envelope and the body go out in one binary frame, so a response no longer costs a base64 encode on the client, a decode on the server, a third more bytes on the wire, and a string the size of the response held on both sides. Negotiated, not breaking: the frame is only sent to a server that announced v5, an older one still receives base64 in JSON, and a v5 server still understands it. Streamed bodies were already bytes since v2; this closes the buffered case.

- **A group of server settings says how many of them were changed, without opening it.** The settings pane marks an overridden setting once you are looking at it, which is no help for the group you did not think to open: a value changed once from the dashboard is invisible until something it does surprises you. Each accordion header now carries the count of settings inside it that differ from what the server started with.

- **Traces can be sampled.** `otel.sample_rate` (env `APERIO_OTEL_SAMPLE_RATE`) is the fraction of requests traced, and it defaults to `1.0`, which is what tracing did before the setting existed: every request builds a span tree and hands it to the exporter. `0.01` samples one request in a hundred, which answers the same questions about latency and error shape for a hundredth of the cost. The decision is made once at the root of a request and every span of that request follows it, so a sampled trace is whole rather than a `proxy.request` missing five of its eight phases; a request that is not sampled skips the phase-span assembly entirely. An unparseable or out-of-range value traces everything and says so, rather than silently turning observability off.

- **The comfort features have switches now, and one of them is per service.** The request inspector records every transaction and the access event logs every request, because that is what makes the dashboard worth opening; on a server running flat out they are also the first per-request costs worth reclaiming. `inspector` (env `APERIO_INSPECTOR`) and `access_events` (env `APERIO_ACCESS_EVENTS`) turn them off server-wide, the second without lowering `log_level` and losing warnings with it. A client can opt one service out with `capture: false` (or `--no-capture`) and leave the rest inspectable. The dashboard marks such a client **no capture**, marks every client **inspector off** when the server's switch is the reason, and the inspector's "no detail" message now names both possibilities instead of blaming age.

- **The activity chart has a fifteen-minute view.** The minute-long one is built in the browser from the deltas between stats polls, which is right for "is it moving right now" and cannot answer "what did the last quarter hour look like": it starts empty on every reload and only knows what the tab has seen. The server now keeps its own ring of five-second slices per organization, `GET /aperio/api/activity`, and the chart toggles between the two. Five seconds rather than one because a per-second line over fifteen minutes is noise, and hovering a slice gives the request count behind the rate. Refusals are counted too, so the chart does not show a quiet server at the moment it is turning everything away.

- **Tunnel protocol v6: a buffered request body travels as bytes too.** v5 did this for responses and left the other direction alone, so an upload under the streaming threshold was still base64 inside the `Request` JSON: a third more bytes on the wire, an encode on the server and a decode on the client, per POST. The envelope and the body now go out in one binary frame, negotiated exactly like v5, so a client that announced v6 gets bytes and anything older still gets base64. Both directions now also compress: the sending side's writer deflates a full frame when the connection negotiated tunnel compression and only when deflating actually made it smaller, which is what keeps a binary frame from bypassing compression the way v5's first cut did.

- **The dashboard can say why a request would be answered the way it is.** The proxy makes a dozen decisions before a byte reaches a backend, and until now the only record was a log line saying what happened, so "why is this hostname 503ing" cost a reproduction, a log grep and a guess. The Topology page (and `GET /aperio/api/explain`) walks the same decisions in the same order for a request nobody sends, and marks the one that decides: maintenance, `routes:`, the preview `robots.txt`, `waf:`, `rate_limits:`, the visitor gate, client selection, then `fallbacks:` or the 504. Every stage reports, not only the deciding one, and when nothing serves the route it names the clients that could have and why they did not (draining, disabled, failing their backend probe, missed heartbeats, a path bind that does not match). It is a strict dry run: no rate-limit token is spent, no round-robin cursor moves, no scaled-to-zero service is woken. Operator role and up, and an organization may only ask about hostnames its own fence admits.

- **A maintenance flag says why, and can lift by itself.** `reason` reaches the visitor on the 503 page (a custom page opts in with `{reason}` and `{until}`, an existing one is unchanged) and the dashboard list, so the person asking and the person who set it read the same sentence. `ttl_seconds` (the dropdown, or `--ttl`) makes the flag expire on its own and makes `Retry-After` the real window instead of a fixed 300: the flag that causes an outage is the one switched on for twenty minutes of work and forgotten. Without a window nothing changes, it stays until turned off. The list now says who set each flag and when, and `GET /aperio/api/maintenance` returns objects rather than bare hostnames.

- **Maintenance mode takes a subdomain wildcard, so a whole domain goes down with one switch.** `robogon.com` covered exactly `robogon.com`, and `test.robogon.com` kept serving, which left "put everything under robogon into maintenance" to be done one service at a time, missing the ones that connect while the flag is on. `*.robogon.com` now covers every subdomain at any depth, not the apex, the same subdomain-wildcard meaning an organization's hostname allowlist already has, so list `robogon.com` too when you want both. `*` still covers the server and stays master-only. A wildcard is a claim over a whole subtree, so it takes an organization whose fence owns that subtree: an org allowed only `robogon.com` cannot set `*.robogon.com`, and master cannot set it while a tenant is fenced to anything inside it.

- **The export chooses what it carries, and the store's history can come too.** `GET /aperio/api/export?include=` names the sections, and `aperio-client api export --include` does the same from the CLI. Omitted, it writes what this endpoint always wrote: tokens, webhooks, users, organizations, autoscaling and settings overrides. What the store also holds is now available for the asking, `statistics`, `uptime`, `inbox` and `admin_keys`, so a migration can carry its history instead of someone copying `aperio.db` and losing the schema tolerance that is the point of a logical dump. The dashboard's Export & Import pane is a checkbox per section. Leaving `organizations` out keeps only the master organization's rows, its statistics slice included, because a row whose organization does not exist on the target server is an orphan; the pane names what that drops before you download it. A misspelled section is a `400` rather than a quietly missing one. Sessions and the audit log are still never exported.

- **The parallel-connection ceiling is the server's, and a token can lower it.** `connections:` was capped at 16 by the client itself, a number the server had no say in and no way to enforce: raising it meant editing the client, and a client that ignored it was not stopped by anything. The server now owns it as `max_connections_per_service` (env `APERIO_MAX_CONNECTIONS_PER_SERVICE`, default 16, so nothing changes for an existing deployment), announces it on the handshake so a client opens what it may rather than finding out by being closed, and enforces it. A dynamic token carries an optional `max_connections` that can lower the number for its holder and never raise it: the effective ceiling is the smaller of the two.

- **A `429` now says which limit produced it.** Six different ceilings answer `429`, and to the visitor they were one status code and a sentence: the response carries `x-aperio-limit: <kind>; setting=<where the number lives>` (plus `Retry-After` on the limits that refill, and deliberately not on the quotas measured in days or months). Because a load test does not read headers, the same thing is a counter: `aperio_rate_limited_total{limit=...}`, one series per ceiling, emitted even at zero. [Performance Tuning](docs/performance-tuning.md) has the table mapping each kind to the setting to raise.

### Changed

- **The upgrade report names the keys your file writes, not every key the entry covers.** An entry can span thirty settings and reach a file through one of them, and printing all thirty is how a warning stops being read: the question an operator asks is which of *theirs* is affected. A `WhenSet` entry now lists the intersection with the file; a changed-default entry, whose whole point is the people who never wrote the key, still names what it is about.

- **The single-service shape in `aperio.yaml` is now removed in 0.9.0, not 0.7.0.** The deprecation was announced for a removal in 0.7.0, that release came and went with the shape still accepted, and every warning, doc line and upgrade-report entry went on naming a version that had already shipped. Nothing about the file changes: a top-level `target:`/`serve:`/`hostname:`/`path:`/`tcp_target:`/`target_health:` still works exactly as before, the notice now names a version that is still ahead. Found by this release's configuration audit.

- **Breaking for scripts: `GET /aperio/api/maintenance` returns objects, not bare hostnames.** Each entry is now `{hostname, reason, until, since, actor}`, which is what carries the reason and the window this release adds. `aperio-client api maintenance list` prints the new shape; anything parsing the old array of strings wants the `hostname` field. The `POST` side is unchanged and its two new fields are optional.

- **A response body is copied twice less on its way through the tunnel.** The client built the frame in two allocations, copying the body into the payload and then again into the frame around it; it is one pass now. The server copied the body out of the WebSocket message it had just received; it takes a refcounted slice of it instead. The wire format is unchanged, and so is everything a visitor sees.

- **Breaking, and reported on upgrade: `aperio-server.yaml` wins over a dashboard override for the same key.** It used to be the other way round: the file said one thing, a value changed once from the dashboard said another, the dashboard won, and nothing anywhere reported the difference. That is a file that lies, and finding out costs an afternoon of wondering why a benchmark will not go faster. A stored override the file contradicts is now dropped at startup (named in the log and written to the audit trail as `settings_override_dropped`), the dashboard refuses to create one for a key the file writes, and the settings pane marks those fields **from file** so nobody types into them first. A key the file leaves alone is still the dashboard's to set, live, which is what the feature is for. A file declaring `version:` hears about this as a `Breaking` entry in the upgrade report, naming the affected keys it writes; a file that mentions none of the live-editable keys cannot be affected at all.

- **The server is on axum 0.8.** No behavior changes on any endpoint: route parameters are spelled `{id}` instead of `:id` internally and WebSocket text frames carry `Utf8Bytes` rather than `String`, neither of which is visible from outside. The upgrade is what makes the accepted-socket fix below possible.

- **A response body over 32 KB now travels as binary frames instead of base64 inside a JSON message.** The switch existed at 256 KB, where it was there to bound memory; below that a body was base64-encoded, which is a third more bytes on the wire and a pass over every one of them. The threshold moves to 32 KB against a server that takes binary frames and stays at 256 KB against one that does not, where streaming would buy nothing. On loopback this measures as break-even at 32 KB and a few percent above; the third fewer bytes is the part that matters on a real link, and it is the part a loopback benchmark cannot show.

- **The settings pane says what a stored override is, and offers the yaml that replaces it.** Editing a server setting from the dashboard is a live change that also outlives a restart, but it is stored in the server's own store rather than in `aperio-server.yaml`, so the file an operator reads describes a different server than the one running. When any setting carries an override, the pane now says so, and shows the exact yaml lines that would make them the deployment's, with the consequence stated: the file wins, so writing a key there drops the override behind it at the next start.

- **Large counts in the dashboard are grouped, and an empty cell says so.** `6652646` is a number nobody reads, so the overview, the clients table and the traffic breakdown now write `6,652,646`, grouped the way the dashboard's own language does rather than the browser's. A cell with nothing in it shows an en dash again: a repository-wide sweep had replaced the placeholder with a lone comma, so a client with no hostname bind showed `,`.

- **The words an operator types are no longer translated.** `hostname`, `path`, `header`, `endpoint`, `payload`, `token`, `webhook`, `proxy` and `subdomain` name things that appear verbatim in `aperio.yaml`, in a URL or on the wire, and a column headed "Alan Adı" over a list of `hostname:` values breaks the link between the screen and the file. They stay in English in all seven languages now, in prose as well as in labels: a column headed one way and a sentence under it worded another is worse than either choice made consistently. Everything around them is still translated, including the words that only sound technical (tunnel, client, cache, request).

- **`--serve` no longer does its filesystem work on the thread it is answering from.** Resolving a request path ran a blocking `canonicalize` and up to two `stat` calls directly on the Tokio worker polling that request, so a slow filesystem (a network mount, a cold disk) stalled every other task on that worker rather than just the one response. It goes through `tokio::fs` now. The SPA fallback took the same route *and* read the whole `index.html` into memory on every navigation; it is served from an open file like anything else, and a `HEAD` for it now reports the length it would have sent.

- **The client no longer carries the server's feature set.** The release built both crates in one `cargo` invocation, so Cargo unified features across them and every option the server enables in a shared dependency was compiled into the client as well: 776 KB of code it never calls. They are built separately now, and `aperio-client` drops from 6.17 MB to 5.51 MB on top of the link-time optimization below.

- **The release binaries are a third smaller, and slightly faster.** Link-time optimization across crates, with a single codegen unit: `aperio-client` goes from 9.26 MB to 6.17 MB and `aperio-server` from 18.93 MB to 13.82 MB, while throughput through the tunnel measured ~11% higher, since the inlining that removes duplicated code across crate boundaries is the inlining a proxy hot path wants. Release builds take about three times as long.

### Fixed

- **A proxied WebSocket or TCP relay whose backend is merely slow is no longer dropped.** Protecting the tunnel's read loop from a stalled consumer had been done with a non-blocking send that gave up the instant a stream's buffer filled, which turned *transient* backpressure into stream death: WebSockets and TCP relays are lossless, so a large transfer whose peer applies flow control could be killed by a burst its backend would have absorbed a moment later. Both arms now take the same bounded hand-off the upload path uses, two seconds of patience before that one stream is dropped with a log line naming it. A consumer that has genuinely stopped reading still loses its own stream rather than the connection's heartbeat. UDP relays keep dropping on a full channel, which is what a datagram relay is for.

- **One slow backend can no longer take a whole tunnel down.** A chunk of a streamed upload was handed to its backend request with the stream map locked and no time limit, on the loop every request, every stream and the heartbeat of that connection share. A backend that stopped reading its body therefore stopped the tunnel: no Pong went out, and fifteen seconds later the liveness check tore the connection down and every in-flight request with it, which reads as "the server died" and is one slow upload. The map is released before the hand-off now, the wait is bounded at two seconds, and a consumer that misses that window loses *its* upload with an explicit error rather than silently truncating it. The WebSocket relay already worked this way; the request-body path did not.

- **A retried request no longer reaches the second client in a frame it cannot read.** Whether a buffered body travels as bytes (v6) or as base64 in the JSON was decided once, before the dispatch loop, and that loop re-enters with a *different* client after an in-flight failover or a 5xx retry. A v6 frame handed to a client speaking an older protocol is a message it drops, so the request hung until the gateway timeout with nothing saying why. The choice is made per attempt now, from the client actually being dispatched to.

- **A maintenance flag can no longer outlive the organization that set it.** A flag is cleared by the organization that set it, so deleting that organization left the hostname answering 503 with nothing anywhere to switch it off: the maintenance list is org-scoped, so master could not even see the flag, and its disable request answered `200` while doing nothing. Deleting an organization now clears the flags it owned, and master may clear any flag, which is the same authority it already has over the server.

- **The settings pane's yaml snippet uses the key the file actually reads.** The two names disagree more often than not, `gateway_timeout_secs` is `gateway_timeout:` in `aperio-server.yaml`, `cache_enabled` is `cache:`, `auth_credentials` is `server_auth:`, and the snippet was spelling them the dashboard's way, which produces a file that looks right, materializes an environment variable nobody reads, and changes nothing. The mapping now comes from the server, with a test that every setting is in it. The two settings the file has no spelling for (its `503_page`/`504_page` take a path where the override holds the HTML) are named instead of silently emitted, and the one key read only at startup says it needs a restart.

- **A new organization appears in the sidebar's picker immediately.** The picker and the Organizations screen poll separately, so an organization created on one was missing from the other for up to thirty seconds, which is where you go straight after creating it. Creating, renaming and deleting now tell the picker to reload.

- **An organization can put its own hostname into maintenance, and mint a share link for it, before any client is connected.** Both asked whether one of the org's clients was serving that hostname *at that moment*, so an organization fenced to `x.com` was told `x.com` is not served by your organization until a client for it came up, which is the opposite of when a maintenance page is wanted. A fenced organization is now judged by its hostname allowlist, which is what says which sites are its own; an organization with no fence has no allowlist to read and keeps the old rule. Master is fenced by the other organizations and by nothing else: whatever no tenant claims is master's, so it can still flag a host with nothing behind it, and still cannot 503 a tenant's site.

- **A visitor's WebSocket upgrade that hits the per-visitor rate limit now names the limit, like every other refusal.** That path answered a bare `429` while its HTTP sibling carried `x-aperio-limit` and counted itself, so a WebSocket-heavy service could be throttled without showing up in `aperio_rate_limited_total`.

- **An HTTP/2 visitor's request reaches the backend at the path it asked for.** Such a request arrives with its URI rebuilt from `:scheme` and `:authority`, and the client turned `http://host/echo` into the path `/host/echo` rather than `/echo`, because it read the path by prefixing `http://localhost` to whatever it was given. HTTP/1.1 visitors, whose URI is a bare path, were never affected.

- **A compressible response body is compressed again when `tunnel_compression` is on.** The v5 full-response frame is a binary frame, and binary frames bypass the tunnel's compression, which only ever applied to text: 32 KB of HTML that used to travel as a few hundred bytes was travelling whole. The frame deflates its own payload now, and only when deflating makes it smaller, so a body that is already compressed or genuinely random is sent as it is rather than paying to grow. Nothing changes for a deployment with compression off, which is the default and the right setting for anyone chasing throughput.

- **Every socket the server accepts sets `TCP_NODELAY` too.** The client's two hops got it in the same release; the server's could not, because `axum::serve` in 0.7 owned the accept loop and offered no hook. The upgrade to axum 0.8 provides one, so the whole path is now free of Nagle: visitor to server, server to client, client to backend.

- **The tunnel socket and the client's connections to its backend set `TCP_NODELAY`.** Neither did before. Both carry request and response messages that somebody is waiting on, not a bulk stream, and Nagle holds a small write back for an acknowledgement that has nothing to do with it.

- **The server asks for the randomness it uses.** Password salts and TOTP secrets come from `OsRng`, which `rand_core` only exposes with its `getrandom` feature, and the server never declared it: the feature arrived through unification, from some other crate in the tree that happened to want it. Nothing was ever wrong at runtime, but nothing said so either, and the axum upgrade rearranged the graph enough to turn it off, which is how it was found. It is a direct dependency now.

- **Three things every proxied request paid for and nobody used.** The structured access-log line was built on every request, ten fields and a timestamp assembled into a JSON tree, and then dropped inside the writer when no access log file was configured; the timestamp behind it was read twice per request, once for the dashboard's live entry and once for that line; and the inspector re-encoded the response body to base64 having just decoded it from the base64 it arrived in. None of this changes what anything shows.

- **The throughput figure in the README was measuring refusals.** It said ~12k requests/second; the benchmark behind it ran with the default per-IP rate limit, so 1,900 of every 2,000 requests were answered with an instant `429` that never touched the tunnel. Measured again with the limiter out of the way, the number is ~4,200 requests/second, and it is now labelled with what it does and does not include.
## [0.7.0] - 2026-07-29

### Security

- **`/aperio/` is the dashboard, not somebody's site.** The trailing slash matched no dashboard route and fell through to the proxy: a visitor who typed it got a 504, or, with a client connected and no hostname match, whatever that client serves, under the URL people are told is the admin surface. It redirects to `/aperio` now, query string kept.


- **An OIDC token exchange no longer re-derives its callback URL from the request that carries the code.** The `redirect_uri` presented at the exchange must be the one the authorization request sent; it is now remembered with the login's state entry and read back, so the `Host` header of the callback request cannot decide what the exchange claims. And when `APERIO_OIDC_REDIRECT_URL` is unset, the server says so at startup: deriving the callback from `Host` means the hostname a login *starts* on decides where the provider returns the code, which is worth knowing before it matters.

- **The session cookie carries the `__Host-` prefix wherever it can.** This server also serves other people's sites, which makes the usual cookie rules too weak for it: a tenant on `evil.tunnel.example.com` can set a cookie for `.tunnel.example.com`, and the dashboard would read it as its own, an operator walked into a session someone else chose. `__Host-` is a promise the browser enforces (host-only, https, `Path=/`), so a neighbour's cookie can never be the prefixed one, and the prefixed one is what the server reads first. The plain name is still accepted on its own, so sessions issued before this and every deployment that cannot set `Secure` keep working; logging out clears both.


- **The parameterless TCP tunnel endpoint is fenced like every other one.** `GET /aperio/tcp` with no `?tunnel=` and no `?client=` picks "any TCP-capable client", and picked it without asking whether the caller was allowed to reach it: any valid tunnel token got a raw socket into whichever client answered first, including one belonging to another organization. Every other way into that handler goes through the same permission check that governs `--bind-tunnels`; this one now does too, so a caller reaches only what it could have reached by naming it.

### Added

- **A runnable messaging example.** [`messaging`](docs/examples/messaging/) is the pair: a reacting side that subscribes, runs a command on `deploy/web` and opens both local faces, and a publishing side that exposes nothing at all. It states the two things worth knowing before using `run:` in anger, that it is a remote-execution primitive and how to scope the publishing token to one subtree, and what the delivery does not promise.

- **Clients of an organization can send each other messages.** They could be reached from outside and could reach a private service through a peer, but had no way to signal each other; the workaround was running an MQTT broker behind a tunnel and binding it everywhere. A client now subscribes to topic filters over the tunnel connection it already holds, and `POST /aperio/api/publish` (or a publish from another client) fans the message out to every subscriber in the same organization. MQTT's filter syntax, since it is the one people know: `+` is one level, `#` is the rest. Full documentation in [Messages Between Clients](docs/messaging.md).

  Two properties are worth knowing up front. **Delivery is per client process, not per connection**: a client with a `services:` list holds one connection per service, and it receives one copy, not one per service. And **nothing is stored** for a client that is away: a message reaches whoever is connected when it is published, because the case this serves is reacting to something happening now, and replaying an hour-old event to a machine that just came back is a bug rather than a service.

  **A client subscribes with `subscribe:` and receives through a local face.** `subscribe:` (or `APERIO_SUBSCRIBE`) is a list of topic filters, process-wide rather than per service. `messages_listen: 127.0.0.1:1888` opens a plain-HTTP listener an application on the same machine talks to: `GET /subscribe?topic=<filter>` streams server-sent events, `POST /publish?topic=<topic>` sends the body. No dependency and no codec, so `curl -N` is a working subscriber and every language's standard library can do both halves; the filter does not have to be in the config file, attaching is enough. See [Messages Between Clients](docs/messaging.md).

  **Messaging is a token capability.** A dynamic token carries a list of topic filters, and one rule covers both directions: a token that may subscribe to `deploy/#` may publish on it, and a token with an empty list, the default, and what every token minted before this carries, can do neither. A granted filter has to *cover* what is asked for, so subscribing to `#` is not a way around a scope that named one subtree. The master token is unrestricted; an ephemeral tunnel token gets nothing, being a guest of the organization for one hostname.

  **`qos: 1` is at-least-once.** The default still sends once and forgets, which is right for most signals. At QoS 1 the server holds the message until each subscriber acknowledges it and resends meanwhile, giving up after 30 seconds; the subscriber recognizes a redelivery and does not hand it to the application twice. The window is the whole promise and is short on purpose: it covers a connection that died between the write and the acknowledgement, not a subscriber that is away, and nothing is stored for a client that is offline at any QoS. A client that stops acknowledging holds at most 256 messages before the oldest are dropped. `qos: 2` is treated as 1.

  **A QoS 1 publish through the MQTT face is answered with PUBACK.** It was not before, so a well-behaved MQTT library held the message and retried it forever.

  **A subscription can run a command.** `subscribe:` takes an object as well as a bare filter, so `- {topic: deploy/api, run: ./deploy.sh}` runs that command whenever a message arrives, without an application attached. This is a remote-execution primitive by design and is shaped accordingly: the payload reaches the command on **stdin** and never on the command line, so a message cannot become part of the command however it is written; the topic and message id arrive in the environment; runs are capped (1 at a time by default) and the excess is dropped rather than queued; each run is timed (60s by default) and logged with its exit status. `run:` cannot be set from the environment, what may execute on a machine belongs in a file an operator wrote.

  **The dashboard has a Messages pane.** It lists the client processes currently subscribed and the topic filters they asked for, which is the one thing about messaging that cannot be worked out from outside, a publish that reached nobody looks exactly like one that reached everybody. It also publishes, with the reply naming how many processes were reached, and says so plainly when that is zero. `GET /aperio/api/subscribers` is the same list.

  **The messaging path is on the metrics endpoint.** `aperio_messages_published_total`, `_delivered_total`, `_dropped_total`, `_resent_total` and `_abandoned_total`, plus the gauges `aperio_message_subscribers`, `aperio_message_subscriptions` and `aperio_messages_awaiting_ack`. Subscribers and subscriptions are counted per client process and deduplicated, so a client running three services with two filters reads as one subscriber with two subscriptions. `dropped` is the one to alert on: it means a subscriber was not keeping up and silently missed a message, which nothing else in the system reports.

  **A refused subscription is reported to the client**, not only in the server's log: a filter the token does not carry comes back with the reason, so it reads as a missing permission rather than as a topic nobody publishes on.

  **An MQTT face, for an application that would rather use the client library it already has.** `messages_mqtt_listen: 127.0.0.1:1883` and a Node, Python or Go MQTT client connects, subscribes and publishes as it would to any broker. MQTT exists only between that application and the client: nothing on the wire to the server speaks it. It is a translator rather than a broker, so a message always goes up and comes back down, and the compatibility answer is stated rather than discovered, QoS 1 and 2 granted as 0, no retained messages, no persistent sessions, no will. Both faces can run at once and share one subscription set.

  **`$aperio/` is the server's own namespace**, closed to clients so an infrastructure event always means what it says. Every server event already feeding webhooks is published there too, `client_draining` becomes `$aperio/client/draining`, so a client can react to a peer connecting, a bind happening or a request failing without standing up an HTTP receiver for it. A bare `#` deliberately does not match the namespace, so subscribing to everything while debugging does not enroll you in it.

- **A runnable MQTT example.** Reaching a broker from every machine in an organization, without the broker being on the public internet: it stays bound to loopback on one host, a tunnel carries it, and each publisher or subscriber binds it back to local `1883` so the application's own configuration does not change. Nothing in it is MQTT-specific, which is the point, it is the shape any single-endpoint protocol takes here. It also states the cost honestly: a message crosses the tunnel once to the broker and once more to each subscriber, so a large fan-out is the thing to measure first.

- **A tunnel can declare `protocol: tcp/udp` and be one tunnel on both transports.** A service that is genuinely both, DNS being the obvious one, had to be written as two declarations, which meant two names, two entries in every binder and two local ports for something an operator thinks of as one thing. A combined declaration keeps it as one: one name, one entry, one local port, with a listener opened on each transport (they are separate port spaces, so the number is shared without conflict). `udp/tcp` is accepted and normalized. Declaring the same target twice, once per protocol, still works and is the way to bind them to different local ports. `encrypt: true` is refused on a combined tunnel, since the handshake is TCP-only and accepting it would leave the datagram half in the clear under a flag that says otherwise.

- **Tunnels have names, and a name is the only handle you need.** Reaching a declared tunnel meant knowing the declaring client's id, which is the one thing a configuration file cannot keep: the server-side connection id is a fresh UUID per connection, and a client with a `services:` list suffixes its own id per service, so `client_id: <uuid>` in one file had to be written as `<uuid>-0` in the other, with the index nowhere an operator could see it. A `tunnels:` entry now takes a `name:`, unique within the organization, and that is what `bind-tunnels:` and `expose:` address. Leaving it out derives a name from the target and protocol, so files that never opt in still get a stable handle, and a name shaped like a UUID is refused so names can never be confused with client ids. Addressing a peer by client id still works and now also accepts the raw `client_id` from the file, not only the suffixed form.

- **`GET /aperio/tunnels` lists what a token may bind, and the dashboard has a Tunnels page.** There was no way to ask what existed: discovery required already knowing a client id, so the only way to learn what you could reach was to be told out of band. The listing reports each tunnel's name, protocol, target, declaring client, how many connections can serve it and whether any of them can right now, scoped to what the caller may actually bind. The dashboard shows the same list beside Clients, with a copy button that hands you a ready `bind-tunnels:` block.

- **Binding is a token capability (`allow_bind`) instead of possession of the declaring client's own credential.** The rule was byte equality: to bind a client's tunnel you presented the exact token that client connected with, which is also the token that publishes services as that client. Letting a colleague reach a database for ten minutes meant handing over the ability to serve as that deployment. A token can now carry `allow_bind` and reach the tunnels of *other* clients in its organization while publishing nothing. It is off by default, never crosses an organization, and the two old ways in (the master token, the same token) are unchanged, so no existing setup is affected.

- **The login page has a language picker and a theme toggle.** Both were only reachable after signing in, which is backwards for the language one: somebody who cannot read the form cannot get far enough to find the control that would fix it. The theme follows: the login page was the one page that ignored a dark-theme preference and flashed white. Both controls are the same component the dashboard header uses, not a second copy of it.

- **Creating an organization asks for its limits, including the monthly traffic allowance.** The form only took a name and a hostname fence, so every organization started uncapped and stayed that way until someone remembered to go back and set the caps, which is the wrong default for the one thing an organization is meant to bound. Client, token, user and MB-per-month limits are now part of creating it; each is still optional, and an empty field still means no limit. If the caps fail to save after the organization is created, the form says so and leaves it open rather than reporting a failure for an organization that already exists.

- **A name is an identifier: `a-z`, `0-9` and `_`.** Organizations, services and tunnels are all addressed by name, in `payments@postgres`, in a `bind-tunnels:` key, in a server's `expose:` rule, and a name that can be written more than one way is a way to reach the wrong thing: `Postgres` and `postgres`, `pg-main` and `pg_main`, an `i` that is actually `ı`. One rule now covers all of them, checked by the client at startup, by `check`, and by the server when an organization is created. What is left out is left out on purpose: `-`, `.`, `*` and `@` carry no meaning inside a name, which is what keeps them available as syntax *around* one (`@` already separates an organization from a tunnel).

  **This is breaking, and deliberately so:** a file that named a service or a tunnel anything else no longer starts, and the message names the fix (`pg-main` → `pg_main`). The derived handle of an unnamed tunnel changed spelling with it: `127-0-0-1-5432-tcp` is now `127_0_0_1_5432_tcp`. Recorded in `CONFIG_CHANGES`, so an upgrade says so rather than failing obscurely.

- **`custom_name:` is where the label goes.** Free text, any language, any punctuation, and changeable at any time, because nothing addresses it: services and tunnels take it in `aperio.yaml` (`APERIO_CUSTOM_NAME` for a service named on the command line), and an organization takes it when created. The dashboard shows the label and keeps the handle beside it, an organization row, a tunnel row and a client's service badge all read the same way, so the thing you recognize and the thing you paste are both on screen.

- **An organization can be renamed.** Only what it is *called*: the handle is fixed at creation, because an `expose:` rule and a binder's config on another machine point at it and cannot be updated from a dashboard. That separation is the reason a display name exists at all. The create form proposes the handle from the label as you type it, and stops the moment you edit the handle yourself.


- **An exposed public port is claimed by organization, not by token name.** An `expose:` entry says `org: payments` (or folds it into the name, `tunnel: payments@postgres`); omitting it means the master organization. The old `token:` still works and still matches exactly what it matched, but it cannot be unambiguous: nothing stops two organizations from each having a token called `ci`, and a rule naming one could match a client of either, with the winner decided by hash-map order, a public port quietly relaying into the wrong organization's tunnel. An organization is the boundary the rest of the system already enforces, and its name is unique by construction. A name that does not exist now matches nothing at all, rather than falling back to whoever answers first.

- **`<org>@<name>` addresses a tunnel everywhere.** A tunnel name is unique inside an organization and nowhere else, so the bare name is an address only by accident, and a binder holding the master token sees every organization at once. The qualified spelling works as a `bind-tunnels:` key, as `?tunnel=` on the bind endpoints and in `expose:`, and it is how the dashboard's Tunnels page shows them, so one form reads everywhere. A bare name still resolves as it always did. Organization names may no longer contain `@`, which is what keeps the split unambiguous.


- **Every key in both JSON Schemas carries a concrete example.** The schemas are the only documentation an editor can reach, point the YAML extension at `aperio-client.schema.json` and the hover shows the description and the examples, and nothing else, and 148 of 328 keys had neither an example nor a default, `bind-tunnels:` among them. So the keys whose *shape* cannot be guessed from their type, exactly the ones you would look up, were the ones that sent you to the website. All of them now show a real fragment: a `bind-tunnels:` map with both spellings of an entry, a `tunnels:` list, a `waf:` rule set, a whole `oidc:` block. Two tests keep it that way, one refusing a key with nothing concrete to show, one building a document out of every example and parsing it back, which is what caught three examples that were wrong when they were first written.

- **A load-balancing or failover choice says what it will do.** The two pickers offered a list of identifiers, `sticky`, `retry-wait`, and a one-line hint about the setting, not about the option. Nothing on the screen said what actually happens to a request under each, which is the thing being decided. The chosen option now carries a sentence of its own under the picker: who receives traffic under each strategy, and what becomes of a request whose client dies mid-flight.

- **Export & Import is its own settings pane.** It sat in the server-settings form as one more collapsible group, next to gateway timeouts and rate limits, which is not what it is: it is not a setting, it moves every token, webhook, user and settings override at once, and importing overwrites all of them. It has its own entry in the settings dialog now, beside Server Settings rather than inside it.


- **A config file describes services under `services:`, even when there is one.** Naming a single backend at the top level of `aperio.yaml`, `target:`, `serve:`, `hostname:`, `path:`, `tcp_target:`, and the probe path `target_health:` / `health.endpoint`, is deprecated and **will be removed in 0.7.0**. Those keys only ever did anything in a file *without* a `services:` list, so a reader had to work out which of two shapes they were looking at before they could read anything else, and a key written into the wrong shape did nothing at all. Nothing changes yet: a file written that way still starts and behaves identically. A client that finds one says so at startup, naming the keys, and a file declaring `version:` gets the same notice through the upgrade report on the next upgrade. The rest of the `health:` block is unaffected: `interval`, `timeout`, `threshold` and `wait_for_backend` are genuine defaults every entry inherits, while a probe path belongs to the backend it probes. Migrating is mechanical, indent them under one `services:` entry.

  **Single-service mode itself is not going away.** It moves to where a one-liner belongs: the positional CLI target and `--serve`/`--hostname`/`--path`, and the `APERIO_TARGET` family in the environment. Those are unchanged and will stay.

- **The examples are one folder per scenario, all written the recommended way.** The `s_`/`m_` split named the shape a file happened to use, single-service or a `services:` list, which stopped being a distinction worth a folder the moment there was one shape. The nine pairs that existed (`s_cache` and `m_cache`, `s_headers` and `m_headers`, …) are merged into one example that shows the feature with several services, since one entry is the same thing with less of it, and the prefixes are gone: `simple`, `cache`, `headers`, `emergency_tunnels`. Two folders that only had a number to tell them apart are named for what they show, `sticky_sessions` and `encrypted_tunnels`. Every client file now describes its backends under `services:`, and every link in the documentation was moved with them.

- **The config builder writes one shape.** The *Single service* / *Services list* choice is gone, since there is no longer a choice to make. The single-service keys are marked deprecated in the emitted schema, so a blank form does not offer them, and an imported file that uses them still shows them, which is what someone migrating such a file needs.


- **The dashboard docs say what the settings screen can actually do.** They described it in one paragraph of "almost every runtime setting", which is true and useless: it does not say which ones, and it does not say what is deliberately absent. [The dashboard guide](docs/dashboard.md) now lists every group with the settings behind it and the environment names they correspond to, states the two that reach connected clients immediately, and names the security- and startup-critical flags that never become dashboard overrides and why. The book carries the same material. The Tools dialog and the palette's settings search are documented alongside.

- **`APERIO_SCALING_ALLOW_PRIVATE` is documented.** The flag existed and was enforced, an autoscaling endpoint resolving to a private, loopback or link-local address is refused without it, but appeared in neither reference table, so the only way to learn about it was to hit the error.

- **The command palette searches the settings, and shows what each one is set to.** It listed the pages of the sidebar and nothing else, so everything that had moved into a dialog, organizations, users, the audit log, became unreachable by search at the moment it stopped being a sidebar row. Every pane is listed now, along with shortcuts that go straight to a form ("Add User", "New Organization") and every server setting by name. A setting matches on its English name, its translated one, its environment key and its group, and carries its current value on the right, marked when it is an override rather than the environment default, half the reason to look a setting up is to check it, which should not cost opening a dialog and a group to read one number. Picking one opens the settings pane, expands the group holding it and scrolls to it. Only the super-admin sees the values, since only they may read them.

- **The audit log, API explorer and config builder open as a "Tools" dialog.** None of them is where the work happens: you check the audit log because something changed and want to know who, you open the explorer because a call is not doing what you expected, you open the builder because a file needs writing. They are instruments, so they now sit together behind one sidebar entry instead of taking four rows next to Settings. The dialog is wider than the settings one, a request/response pair and a generated YAML file are wide by nature, and shares its shell with it, including the overlay behaviour and the unsaved-changes guard.

- **The organization row's action is "Edit" rather than "Quota".** It opens the hostname fence, the limits and the OIDC override as well as this month's usage, so naming it after one of the four sent people looking elsewhere for the other three.

- **The configuration pages open as a settings dialog instead of taking over the window.** Server settings, organizations, users, webhooks and the webhook inbox are things you open, act on and leave, so they now share one dialog with their own nav down the side, reached from a single "Settings" entry where the sidebar used to list them as separate destinations. The pages that are *read* rather than operated keep the whole window: the audit log, the API explorer and the config builder.

- **The settings dialog opens over the page you were on, and leaves the URL alone.** It was addressed as `?tab=settings` like any other page, which made it *replace* the view underneath instead of covering it: whatever you were watching was gone when you closed it, the back button stepped through settings panes, and a reload came back into a settings screen nobody had navigated to. The dialog is now pure overlay, the page beneath keeps the URL and is still there when the dialog closes, and a reload returns to that page with the dialog shut. Links written against the old form still open the pane once, then drop the parameter. Because a reload now discards an open dialog, a settings form with unsaved edits asks before it is thrown away, both on closing or switching panes and on the browser's own reload.

- **Organizations, users, sessions, admin keys, webhooks and the webhook inbox are lists rather than tables.** Six or seven columns never fit the dialog: every cell was squeezed by the widest value in its column, so a hostname list or a user agent decided how unreadable the rest were. Each record now gets the full width one line at a time, what it is, then what is true about it, with its actions on the right. They are also unfilled, so the dialog reads as one glass panel instead of a stack of opaque cards over it.

- **The users pane says which organization it is listing.** The list is filtered to the session's organization, so without naming it a short list reads as "there are only two users" rather than "in this organization there are two".

- **Server settings are one column of collapsed groups, not two columns of open cards.** Nine groups of switches side by side read as an undifferentiated wall, and finding a setting meant scanning both columns. They are an accordion now, so the group headings are the index and only the group being changed is open. Export/import and the read-only environment flags join them as sections of the same list rather than trailing cards. The fields inside an open group follow the width they actually have rather than the window's, so they stop splitting into two columns too narrow to hold a label.

- **The sidebar footer is one user entry instead of three loose buttons.** Two-factor auth, passkeys and signing out sat in the footer as menu items with the same weight as the navigation above them, though none of them is a place you go. They are now behind the signed-in identity, which the footer shows with its role, in the shape the sidebar's own composition describes for a footer. The remaining session time moves into that menu. The sidebar also gains its edge rail, so it can be collapsed by dragging the border rather than only from the one button in the page header.

- **The dashboard wears the Aperio mark instead of a generic globe.** The sidebar tile and the login card carried a stock icon, and the login tab had no icon at all. The mark now stands in both places, drawn with `currentColor` so it takes the colour of whatever it sits in and needs no separate light and dark artwork. It stands on the surface behind it with no tile, taking the foreground colour, so it is near-black on the light theme and near-white on the dark one. On the login card the wordmark sits beside the mark instead of under it, so the card opens with one lockup rather than two stacked headings. The favicon keeps the signal it always had, tinting by connection state, and is now the mark rather than a bare dot, so a backgrounded tab says both which product it is and whether the tunnel is up. The wordmark beside it is set in Michroma, uppercased, and marked `lang="en"`: `text-transform` is locale-aware, so on a dashboard running in Turkish the `i` would otherwise uppercase to a dotted `İ` and the brand would read APERİO. The font is self-hosted alongside the body font rather than fetched from Google, since the dashboard is served under a `default-src 'self'` policy and an air-gapped install has nothing to fetch from. Everything that is not the wordmark is now set in Roboto, self-hosted the same way, replacing Noto Sans; it covers every script the UI ships translations for except Chinese and Japanese, which the previous face did not carry either and which continue to fall through to the system sans. The login page also carries the mark as an oversized, near-invisible watermark, and the card above it is glass: no fill of its own, blurring what shows through, with the ring and shadow it already had drawing its edge. Every floating surface is glass with it: dialogs (including the two-factor prompt), confirmation dialogs, the command palette, dropdown menus and select panels. They share one recipe with the login card: no fill of their own and a 15px blur, the surface being the blur. Where `backdrop-filter` is unsupported they fall back to no background at all. A standalone copy in the brand green ships at `docs/assets/aperio-mark.svg`, for the contexts that cannot inherit a colour, and heads the README.

- **A public `expose:` port names the tunnel and the token that owns it, instead of a shared secret.** The secret sat in plaintext in two files, named no owner, could not be revoked, and left the port to whichever client presented it first. An entry now reads `tunnel: ssh` + `token: bastion-host`: the port accepts that named tunnel only from a client authenticated with that token, so revoking the token closes the port's source, the audit trail names an owner, and another client in the same organization cannot claim the name and receive the traffic. Omitting `token:` accepts only tunnels declared with the master token. The `key:` form still works. Public expose is no longer marked experimental; its limits (one serving client, TCP only, no encrypted tunnels) are deliberate rather than provisional.

- **A tunnel bind picks a connection that can actually serve it.** Every connection of a client process announces the same `tunnels:` list, and resolution stopped at the first match, then checked whether it was draining or unhealthy. A process with several connections could therefore be told "not available" while a healthy sibling sat next to it. Resolution now walks them and takes an available one.

- **The binder verifies at startup and says which gate closed.** It opened its listeners and only discovered the truth per connection, reporting every rejection as "failed to reach server" even when the real answer was a token that may not bind, or a client that is draining. It now resolves everything against the server's listing before listening: an entry that cannot be bound is named at startup alongside the names that can be, and the entries that did resolve still come up, because getting three of four tunnels during an incident beats getting none.

- **A `bind-tunnels:` entry can be just a port, and a privileged local port no longer means no listener.** `pg-main: 15432` is the whole entry for most bindings. The local port still defaults to the declared target's port; when that port is privileged (below 1024) or the target has none to parse, which used to skip the tunnel outright, a port derived from the tunnel name is used instead, stable across restarts so whatever connects to it never needs reconfiguring. A listener can be moved off loopback with `address:`, which warns, since it puts a deliberately unexposed service on the network.

### Fixed

- **`referrer_policy:` is sent as one of the values a browser acts on**, like `frame_options:` before it: anything else falls back to `strict-origin-when-cross-origin` instead of going out as written, so a typo is a policy rather than a header that quietly does nothing.

- **The settings pane says when it failed to load**, instead of rendering as an empty screen; a webhook inbox entry that cannot be deleted says so, instead of reappearing on the next refresh as though the button had not worked. The webhook URL field is a URL field, so a malformed address is caught before the round trip.


- **A handful of small things a code read turned up.** Deleting an organization now clears it from the sessions that had it selected, instead of leaving an admin on screens that are empty for a reason nothing states. An `expose:` entry with `port: 0` is refused rather than binding whatever the OS hands out, which nothing could then reach. `frame_options:` is sent as `SAMEORIGIN` or `DENY` and nothing else, since a browser acts on those two and silently ignores a typo, a header that looks like protection and is not. A binary tunnel frame whose id will not fit its one-byte length prefix is refused instead of wrapping the length and putting every frame after it out of step. The idle-retire check re-reads its counters after deciding, so a request that starts in the microseconds between two atomic loads cannot be retired out from under. In the dashboard, the OIDC client secret field opts out of password-manager autofill, a corrupt sparkline entry in local storage is discarded rather than spreading `NaN`, and `1,500 MB` is refused rather than read as 1.5 MB, a thousandfold difference nobody should have guessed at.


- **The rate-limit refill rate can no longer be set to zero from the dashboard.** The environment variable has always refused a non-positive value; the settings screen accepted `0`, and a bucket that never refills is not "no limiting", once the burst is spent, every visitor of every proxied site gets a 429, for as long as nobody notices. Now refused the same way, keeping the previous value.

- **The `routes:` schema example named a key that does not exist.** It said `status: 301` where the field is `permanent: true`, so an editor offered it, the file accepted it (the key was simply ignored), and the redirect went out as a 302, a temporary redirect for someone who asked for a permanent one. Every example in both schemas is now checked against the keys its type actually has, which is what would have caught this.

- **`.env.example` named three variables the code never reads.** `APERIO_SERVER_GATEWAY_TIMEOUT` and `APERIO_SERVER_GATEWAY_RESPONSE_TIMEOUT` carry a `SERVER_` the reader does not (they are `APERIO_GATEWAY_TIMEOUT` / `APERIO_GATEWAY_RESPONSE_TIMEOUT`), and a comment advertised `APERIO_CLIENT_TARGET` as a legacy alias for `APERIO_TARGET`, which it never was. Copying any of the three set a variable nothing looked at.

- **The share-link API said its lifetime was capped at 30 days.** The cap is 10 years (and `0` never expires); the doc comment is what the OpenAPI schema publishes, so the API documented a limit the server does not enforce.

- **The webhook inbox freezes silently when a session expires.** Its five calls went out through a bare `fetch` rather than the shared client, so they missed the redirect-to-login every other screen gets: the pane simply stopped showing anything, with no way to tell that the answer was "log in again".


- **A `bind-tunnels:` key that names a tunnel in more than one organization is refused.** A name is unique inside an organization and nowhere else, so a token that can see two of them saw `postgres` twice and bound whichever came back first, a local port onto someone else's database, with nothing said about it. The entry is now reported with the qualified names to choose between (`payments@postgres`, `billing@postgres`), and skipped, like every other entry that cannot be resolved.

- **Every page's subtitle was in English, in all seven languages.** The line under a page title comes from the sidebar's own table, and its strings reach the translator through a variable, which the i18n check could not see. It reads those tables now, the same way it already reads the settings catalogue, and the strings it turned up are translated.

- **A deprecation warning naming one key said "`hostname` describe a single service".** Singular now, which is the case an operator actually reads.


- **`aperio_messages_resent_total` counted nothing.** The counter was rendered on the metrics endpoint and never incremented, so a QoS 1 subscriber that was not acknowledging looked exactly like one that was: the resends were happening, the graph said zero. The other messaging counters were unaffected.

- **A message published on a topic the token does not carry now says so.** The refusal was only in the server's log, while the local face had already answered `202` to the application that sent it, so the publishing side had no way to learn its message went nowhere. It comes back as `PublishRefused` with the reason, matching what a refused *subscription* has always reported.

- **A local subscriber's topic filter is given back when it leaves.** Attaching to either local face added a filter for the life of the process, so sixty-five runs of `curl -N` on different topics walked a long-running client into the server's per-client filter limit and the next subscription was refused for no reason the operator could see. A filter is now held for as long as something holds it, and released when the last local subscriber goes; one from `subscribe:` is still the client's for as long as it runs. An idle subscriber that disconnects is also noticed immediately rather than at the next message, which on a quiet topic never came.

- **An MQTT SUBSCRIBE sent together with the CONNECT is answered.** Everything that arrived in the same read as the CONNECT was left in the buffer and not looked at again until more bytes turned up, so a client that writes both at once, or two writes the kernel coalesced, sat unsubscribed until its keep-alive ping happened to wake the parser.

- **A client that only sends and receives messages can start.** `subscribe:` or a local message face with no `services:`, `target:` or `tunnels:` was refused with "the target is required", so a publish-only client had to invent a service it does not have. A connection that carries messages is as good a reason to exist as one that carries a peer's tunnels, which was already allowed; `check` agrees, and the log line for such a connection no longer calls it "tunnels only" when it has none.

- **`aperio-client check` accepts a binder as a complete configuration.** A file made only of `bind-tunnels:` opens local listeners onto tunnels another client declared and exposes nothing of its own, which is exactly what a binder is for; the check called it a missing target, and the message it printed did not even name the section the file is made of.

- **A backend that had just passed its first probe could be reported as "still checking".** The client announced the healthy verdict and recorded that a probe had completed as two separate steps, so a heartbeat sent in between carried "up, and nobody has looked", a pair that describes nothing, and the one the dashboard draws as CHECKING rather than routable. The next heartbeat corrected it, which is why it took a one-in-many end-to-end run to see it at all. The two are read together in one place now, and being healthy is itself taken as evidence a probe completed, so the contradictory pair can no longer be constructed.

- **`aperio-client check` reported on the backend the client was about to ignore.** In a file that named one service at the top level *and* carried a `services:` list, the check named the top-level target and probed it, while the runtime does the opposite, the list wins. So the one command whose job is "will this configuration work" answered for the wrong machine and never touched the one that would serve traffic. It now mirrors the runtime exactly (a positional CLI target still overrides the list, as it always did) and warns, naming the keys that are being ignored.

- **The client says when top-level service keys are ignored.** With a `services:` list present, `target:`, `serve:`, `hostname:`, `path:`, `tcp_target:` and `target_health:` above it are read by nothing; they were dropped without a word. A file that says something the client will not do should say so out loud, and the config builder now refuses to stay quiet about it too.

- **A settings pane a role may not open no longer renders an empty dialog.** Following a link to one, `?tab=settings` as a viewer, say, highlighted the pane the reader *could* open in the nav while the body was still asked for the refused one, so the panel came up blank. It now shows the pane it selected.

- **The command palette's setting values follow the server.** They were read once when the tab loaded, so changing a setting in the dialog next door left the palette quoting the old value until a reload, worse than showing none, since checking a value without opening anything was the point. They are re-read every time the palette opens.

- **Eleven server settings, the browser tab title and the request inspector's body markers were shipping in English.** Three groups of settings, stream flow control, the serve-stale window and the noindex switch, had no translation in any language, and the tab read "Aperio · Connected" whatever the dashboard was set to. The translation check could not see any of it: those settings reach `t()` through a variable, and it only reads literal arguments, so it had been reporting a clean sheet over a whole screen. It now reads the settings catalogue the same way it reads the config builder's, which is what turned the gap up, and all seven languages carry them.

- **A closed dropdown shows the label it was picked by, not the raw value underneath.** The role field read "viewer" over a list offering "İzleyici", the share-link expiry read "3600" instead of "1 hour", and the traffic range read "30d", each menu was translated and each closed field then contradicted it. The four affected pickers now name their options, so the selected one reads the same closed as it did open.

- **Enter submits the user, organization and password forms.** They are built from labelled inputs and a footer button rather than a real `<form>`, so the one thing every filled-in form does, type the last value, press Enter, did nothing, and the organization form only honoured it from its first field. Textareas keep Enter for newlines.

- **The user forms enforce the eight-character password minimum before submitting.** The label said it and the server refused it, but only after the round-trip. Create stays disabled until there is a username and a long enough password; on edit, blank still means "keep the current one".

- **The config builder's section headings are translated.** Every heading and blurb in the builder rendered in English on a dashboard running in any other language, while the rest of the page around them was translated. They reach `t()` through a variable, and the build-time translation check only sees literal arguments, so it had been reporting a clean sheet over twenty-two headings and their descriptions. The check now reads that table too, which is what turned the gap up, and all seven languages carry them.

- **A config builder section with nothing to lead with no longer hides everything behind "More settings".** Sections whose keys are all secondary, Access control and five others, opened onto a single nested accordion and nothing else: an accordion whose only child is another accordion. Those sections now list their fields directly. The nesting stays where it earns its place, on a section with a short head and a long tail.

- **The config builder shows every accepted value of a setting, not the first.** A key whose schema examples enumerate its choices, like a tunnel's `tcp` / `udp` / `tcp/udp`, was advertising one of them as a placeholder and leaving the rest undiscoverable from the only screen an operator would look at.

- **Enter in a login field signs you in.** The form had a submit button and no handler in the way, so the browser's implicit submission should have covered it, and did not: a real Enter in the password field raised no submit event at all, leaving the button the only way in. The form now asks for the submit itself when Enter is pressed in one of its fields, through `requestSubmit`, so the browser's own validation still runs and an empty field is still reported rather than posted.

- **The sidebar logo is the size it is set to.** `SidebarMenuButton` carries `[&_svg]:size-4` in its base classes, and a descendant selector outranks a plain size utility, so every size given to the mark there was silently discarded and it rendered at 16px throughout.

- **The Tunnels table sits flush in its card and no longer counts paths at you.** The card kept its own vertical padding around a table that *is* the card, leaving a band above the header row and below the last one that read as a broken table rather than as spacing; it now matches the other table sections. The "Paths" column is gone: the number of connections announcing a tunnel is an implementation detail of how a client opens its connections, and naming it in an operator-facing table invited reading it as something about the tunnel. Whether anything can serve it is what matters, and that is already the dot next to its name.

- **Tunnel discovery names the declaring process, not one of its connections.** The listing reported a per-connection instance id, which carries a service index the operator never wrote (`<uuid>-1`) and, worse, was whichever connection happened to be visited first: a tunnel served by two connections could report a different id on two calls that described the same thing. It now reports the process's own `client_id`, exactly as written in its config file, falling back to the per-connection id for a client too old to announce one. A `bind-tunnels:` key naming a connection (`<uuid>-0`) still selects that peer, so configurations written before tunnels had names keep working.

- **A dialog whose content grows no longer pushes its own buttons off the screen.** Dialogs are centred on the viewport, so one taller than the window loses both ends at once, and with nothing to scroll the confirm and cancel buttons simply could not be reached. The text areas made this easy to hit: they size themselves to their content, so pasting a configuration into the config builder's import dialog grew the box until OK was somewhere below the bottom of the screen. Two caps, both on the shared components rather than on the dialogs that happened to notice: a dialog is now at most the height of the viewport and scrolls past that, and a text area stops growing at half the viewport and scrolls internally instead. The two dialogs that had worked around this individually drop their local caps.

## [0.6.0] - 2026-07-28

### Security

- **Disabling a dashboard user no longer hands that user master super-admin rights.** Deleting an account ended its live sessions, but disabling one did not, so the session stayed valid for up to a day after the operator had decided the account could no longer be trusted. That alone would have been a lapse; the interaction with organization scoping turned it into an escalation. A session's organization is resolved by looking the username up in the user store, and that lookup skips disabled rows, so a freshly disabled user resolved to "no organization", which the authorization layer reads as the master organization. An administrator of a child organization therefore *gained* privilege at the moment of being disabled, and their open session could reach the master-only endpoints: the full store export (password hashes, TOTP secrets, webhook secrets), import, purge, and admin-key management. Disabling an account now drops its sessions immediately, exactly as deleting one does, and, as a second line of defence, any session whose user is disabled is rejected by the authorization layer itself rather than being silently reinterpreted as a master session. Sessions from an OIDC identity, which has no user row, are unaffected.

### Added

- **Settings that share a prefix are now written as a block.** `health_interval` / `health_timeout` / `health_threshold` / `target_health` / `wait_for_backend` read as a flat list of run-on names when they are one subject, so `aperio.yaml` takes a `health:` block instead (`endpoint`, `interval`, `timeout`, `threshold`, `wait_for_backend`), at the top level and per `services:` entry. `aperio-server.yaml` gains the same treatment for fifteen groups: `alert`, `audit`, `cache`, `dashboard`, `edge`, `failover`, `gateway`, `ip_limit`, `login_lockout`, `metrics`, `oidc`, `otel`, `retention`, `scaling`, and `server` (`server_token` / `server_auth` becoming `server: { token, auth }`, matching the client's long-standing `server:` block). Where the group's own key is also a setting, the child carrying it is `enabled` (`cache: { enabled: true, max_bytes: … }`) or `mode` for `failover`, and the bare scalar (`cache: true`) is still accepted. Environment variables are unchanged, since the environment has no nesting: the mapping is mechanical in both directions, `<group>.<child>` to `APERIO_<GROUP>_<CHILD>`. **Every flat key still works exactly as before**, so no existing file needs changing; a file may mix both spellings, with the block winning per field, and the client prints a one-line deprecation notice naming the block to move each flat key to. The `aperio.yaml` / `aperio-server.yaml` JSON Schemas describe both forms, so editors complete the blocks, and the shipped examples now use them.

- **The flat `health_*` keys and a top-level `token` are documented as the deprecated spellings they already were.** `fold_groups` has always folded `health_interval` / `health_timeout` / `health_threshold` / `wait_for_backend` into the `health:` block and reported them as deprecated, but only `target_health` said so in its own documentation, so the JSON Schema told editors the other four were current. The same for a `token:` written at the top level instead of under `server:`. Behaviour is unchanged, all of them still work, but the schema, the editor tooltips and the config builder now agree with the parser.

- **The config builder grew into something usable for a real file.** With every setting on one flat list the page was a wall; the settings now sit in collapsible sections, each showing how many of its fields are set, with `services:` and `tunnels:` first because they are what a file is usually about. The page is two columns: the form on the left, the document it produces on the right, updating as you type, with copy and export beside it. A client file starts in its multi-service shape rather than the single-service CLI shorthand, the two are mutually exclusive, so whichever you pick hides the other's keys instead of offering a file that cannot start. Deprecated spellings no longer appear in a blank file and show up only when an imported one uses them, so the builder never suggests the key we want retired. `bind-tunnels:`, a map of peers, previously the one thing the form could not touch, is edited in a dialog, and both schemas are now free of fields the builder cannot configure. The `version:` key that drives upgrade checking is offered like any other setting.

- **Four live-editable server settings were missing from the dashboard.** `cache_max_stale` and the three stream flow-control watermarks (`stream_pause_bytes`, `stream_resume_bytes`, `stream_backlog_limit`) were editable through the API and the config file but had no input on the Server Settings page, so the only way to tune them at runtime was a raw API call. They now appear, the watermarks under a new *Stream Flow Control* group, and a size field can carry a minimum so the three that reject zero say so in place instead of failing the save.

- **A forgotten translation now fails the dashboard build.** The i18n check compared the languages against each other, which cannot catch the case that actually happens: when *every* language misses a newly added string they agree with each other perfectly and the dashboard quietly ships English. It now extracts the literal arguments of every `t('…')` call and requires each language to carry them, and it runs as part of `npm run build` rather than only on demand. Turning it on surfaced 142 strings that had been rendering in English in all seven languages, the autoscaling, admin-key, quota, cache and self-health screens among them, and those are now translated. The key reader was also missing dictionary entries written without quotes, which is how it could report a key the file already had.

- **Configuration files can declare the version they were written for, and upgrades check it.** `version: 0.5.0` at the top of `aperio.yaml` or `aperio-server.yaml` turns a blind upgrade into a checked one: on startup the binary compares that against its own build and looks up every recorded change to the configuration format that landed in between. An upgrade that cannot affect the file says nothing at all, so silence is meaningful. One that can prints each change, the keys it touched and what to do, then asks you to bump `version:` once you have reviewed it. A change whose consequences are security-relevant, a default that opens something previously closed, an enforcement that quietly stopped applying, makes the binary **refuse to start** rather than run under a configuration whose meaning shifted. A file declaring a version newer than the binary (a rollback nobody rolled the config back for) is called out too, and `aperio-server --check-config` reports the same verdict. Leaving `version:` out keeps today's behaviour exactly, with one line noting the check is off. The recorded history starts here on purpose: entries for older releases could only be guesses, so nothing is claimed about them.

- **A config builder in the dashboard writes `aperio.yaml` and `aperio-server.yaml` for you.** A new System page assembles either file from a form: pick the side at the top, start fresh or **Import YAML** by pasting a document or opening a file, edit, then **Export YAML** to copy the result or save it under the right filename. The form is generated from the JSON Schema the server serves (new `GET /aperio/api/config/schema/{client|server}`), itself derived from the Rust types that parse these files, so the page offers exactly the settings the running binary understands and each field carries that setting's own documentation. Where the schema knows enough it helps: fixed values become a select, byte sizes are entered as an amount plus a unit, lists of scalars take a comma-separated line, and `services:`/`tunnels:` and the other object lists get add-and-remove entry cards. Empty fields are omitted from the file rather than written as blanks, and a section too structured to render is preserved exactly as imported, so opening an existing file loses nothing.

- **Every setting is now reachable from `aperio.yaml` / `aperio-server.yaml`.** A handful of settings existed only as environment variables, which meant they were absent from the JSON Schemas, uncompleted and unvalidated by editors, and invisible to anyone reading the config file to understand a deployment. On the client, `serve_spa`, `serve_404`, `device_key`, `device_key_file`, `log_level`, `log_format` and `server.urls` (cross-server failover, previously only `APERIO_SERVER_URLS`) gained yaml keys. On the server, twenty-one settings that the docs already described as yaml keys were missing from the schema and are now declared, among them `admin_allowed_ips`, `max_ws_connections`, `token_pinning`, `retry_on_5xx` / `retry_statuses`, the four `outlier_*` keys, `inspector_redact`, `webauthn_rp_id`, `webhook_retry_schedule`, `uptime_tick_secs`, `config_hot_reload` and `reuseport`, plus `cache.negative_ttl`, `scaling.allow_private`, `oidc.client_secret` and a new `backup:` block (`interval`, `dir`, `keep`). The `rate_limits:`, `fallbacks:` and `waf:` sections are described by the schema too, so editors now complete them like `headers:` and `routes:`.

- **The autoscaling and security-header settings can be set from the environment.** `scaling:` and `security_headers:` were yaml-only, so a deployment that injects configuration through the environment could not use them at all, and a scaling secret had to live in a file on disk. Both now have the `APERIO_*` spellings the naming standard implies (`APERIO_SCALING_URL`, `APERIO_SCALING_SECRET`, `APERIO_SCALING_MIN` …, `APERIO_SECURITY_HEADERS` and the six `APERIO_SECURITY_HEADERS_*` variants), layered per field, so a file can carry the shape while the environment injects only the secret.

- **The stream flow-control watermarks are now settings.** The per-stream pause/resume thresholds introduced with tunnel protocol v3 were fixed values; they can now be tuned on the server as `APERIO_STREAM_PAUSE_BYTES` (default 2 MiB), `APERIO_STREAM_RESUME_BYTES` (default 512 KiB) and `APERIO_STREAM_BACKLOG_LIMIT` (default 16 MiB), or in `aperio-server.yaml` as a `stream:` block (`pause_bytes`, `resume_bytes`, `backlog_limit`), editable live like the other scalar settings and applied to streams started after the change. An inconsistent trio is repaired rather than obeyed: the resume mark is kept below the pause mark and the hard cap above it, so the mechanism cannot be configured into dropping every stream or flapping.

- **An optional policy over where the server may send webhooks and autoscaling hooks.** Both features take a URL from a lower-trust party (an Operator creating a webhook, a client declaring `scaling.url`) and have the server call it, and the delivery log reports how the destination answered, which together let a tenant use the server as a blind probe into its private network. Two new server settings fence this in without breaking the normal deployment, where receivers legitimately live on the internal network: `outbound.allowlist` (`APERIO_OUTBOUND_ALLOWLIST`) names the host/CIDR patterns the server may call, refusing everything else, at webhook creation with a clear error and again at every delivery, so webhooks stored before the policy also comply; `outbound.block_private` (`APERIO_OUTBOUND_BLOCK_PRIVATE`) instead refuses destinations that are, or resolve to, internal addresses (loopback, RFC 1918, link-local and the cloud metadata services, CGNAT, unique-local). Both default to off, which keeps today's behaviour exactly; autoscaling hooks keep their own stricter https-and-public default, with the new policy applied on top. A refused delivery is recorded in the delivery log with the reason, without the destination ever being contacted.

- **Static-file mode streams files and answers `Range` requests.** Serving a directory (`--serve` / `serve:`) used to read every requested file fully into memory for the life of the request, so peak usage was file size times concurrent visitors; a large download now streams from disk in chunks and memory use no longer scales with file size. Responses advertise `Accept-Ranges: bytes` and a single-range `Range` header is answered with `206 Partial Content` and a `Content-Range` (a range beyond the file gets `416`), so video scrubbing and resumable downloads work straight out of a served directory. Multi-range requests and requests carrying `If-Range` are served as the full `200`, which the HTTP spec permits.

- **The OTLP startup check now proves the collector speaks OTLP/HTTP, instead of only that something is listening.** It opened a TCP socket and logged "endpoint is reachable" on success, which is true of any process on that port, including a collector's gRPC listener. Pointing `otel.endpoint` at 4317 therefore produced a reassuring startup line followed by silence, with every span dropped and the only clue an `ExportError` from the SDK. The check now posts an empty export (a valid `ExportTraceServiceRequest` carrying zero spans, so a working collector accepts it and records nothing) over the exporter's own HTTP client, and reports what actually happened. An endpoint on port 4317 additionally gets told why: Aperio exports over OTLP/HTTP, so it wants the HTTP port, 4318 by convention.

- **Traces can now be exported over OTLP/gRPC, not only OTLP/HTTP.** Collectors are routinely deployed with only the gRPC listener open, and until now that meant Aperio could not reach them at all. Both transports are built into every binary and chosen with `otel.protocol` (`http` or `grpc`; the spec spelling `http/protobuf` is accepted, as is the standard `OTEL_EXPORTER_OTLP_PROTOCOL` variable). Left unset, the endpoint's port decides, 4317 is gRPC by convention and everything else is HTTP, so the two ordinary collector layouts need no setting at all, and an endpoint that used to fail silently on 4317 now simply works. The endpoint is adjusted to match the transport rather than being taken literally: the `/v1/traces` signal path is appended for HTTP and stripped for gRPC, so switching protocols does not require editing the URL. Pin `protocol` explicitly when the collector listens on a non-standard port; if it is pinned against the other transport's conventional port, startup says so. The gRPC transport reuses the server's existing rustls/ring TLS stack, so nothing new is compiled in beyond tonic itself.

- **The startup probe tests whichever OTLP transport is in use.** The empty-export check is HTTP-specific, so a gRPC endpoint is instead checked by completing an HTTP/2 connection preface, which is the transport gRPC is defined on and which an OTLP/HTTP or HTTP/1 listener will not complete. That is weaker evidence than an accepted export and the log line says as much rather than claiming a successful export; TLS endpoints are reported and left unprobed instead of being quietly downgraded to a bare TCP connect, which is the kind of reassuring non-check this probe exists to avoid. Pointing a gRPC endpoint at port 4318 is named outright, the mirror image of the existing 4317 hint.

### Removed

- **The separate dashboard password (`dashboard_auth` / `APERIO_DASHBOARD_AUTH`) is gone.** It predated organizations and named dashboard users, and by now it was a third way to reach the same place: a single server-wide secret that signs in as the built-in `aperio` admin with no role, no organization, and nothing to revoke short of changing it for everyone. The dashboard is entered as `aperio:<master token>`, and anyone else gets a named user (Users page) or their own organization, which is what the rest of the product already assumes. **A server whose configuration still sets it refuses to start**, naming the key and what to do instead, a removed credential that is merely ignored would leave the file claiming an authentication path the server no longer honours, and nobody would find out until someone tried to sign in. The startup warning that used to fire when the dashboard was enabled without it is gone with it.

### Fixed

- **Exported traces contain the whole request breakdown again, not just a single root span.** Aperio synthesizes a phase span per stage of a proxied request, `queue & routing` with its four measured sub-phases, `tunnel round-trip` with the client and backend estimates nested under it, and `server → visitor`, but every one of them was being discarded on the way out. They are built through the global tracer, and while the tracing layer was given the real exporter the *global* tracer provider was never installed, so it stayed the default noop: a sink that accepts spans and drops them without an error anywhere. A collector therefore received one `proxy.request` span per request with none of the timeline that the dashboard's own inspector has always shown. The provider is now installed globally as well, and a test asserts that a span built through the global tracer after startup carries a valid span context, which is exactly what a noop provider cannot produce.

- **A visitor downloading slower than the backend sends no longer loses the transfer.** Unblocking the tunnel from stalled visitors had left streamed data with nowhere to wait: each stream's buffer held about sixty-four chunks, and the moment a backend ran that far ahead of its visitor the stream was declared stalled and cut, even though the visitor was reading steadily. Any sizeable download to a home connection from a fast backend, or a WebSocket or TCP session with a burst of server-side output, could be severed mid-transfer, and with chunked responses the truncation could even arrive looking like a clean end of body. The tunnel protocol (now v3) gained per-stream flow control: when a stream's server-side backlog passes a byte watermark, the client is told to pause and stops reading that one stream's source, so ordinary TCP backpressure reaches the backend, and a resume follows once the visitor catches up. Nothing else on the tunnel is affected, a consumer that accepts nothing for the whole response timeout still ends its stream as before, and UDP keeps its drop-when-congested contract. Older clients (protocol v2) cannot be paused; against them the server allows a much larger backlog (16 MiB per stream) before giving up.

- **`services:`, `tunnels:` and `bind-tunnels:` in `~/.aperio.yaml` are no longer ignored.** The user-level config file layers under the project's for every setting, and is the natural place for defaults shared across projects, except that these three sections were read from the project file only. Declaring them in `~/.aperio.yaml` did exactly nothing, silently, while every key beside them was honoured. They now layer like the rest: a project file that declares one replaces the user-level version wholesale (rather than merging entry by entry, which would make it impossible to drop an inherited service), and a section the project file does not mention is inherited.

- **Grouped configuration blocks now survive a hot-reload.** The new block spellings worked at startup but not on a live config edit, on either side. The client's reload path parsed `aperio.yaml` without folding the blocks into the settings they stand for, so saving a file that uses `health:` silently turned health probing off until a restart. The server's hot-reload layer read `aperio-server.yaml` expecting only the flat spellings, so the presence of a `cache:` or `failover:` block, as the shipped examples now write them, made it discard *every* live-editable file setting without a trace: even editing an unrelated flat key like `max_body_size:` in such a file did nothing until a restart. Both paths now apply the same folding as startup. The server also honors the documented per-field precedence when a file mixes both spellings of a setting, the block now wins regardless of which one comes later in the file, and `--print-config` attributes block-derived values to the file instead of to the environment.

- **Failed deletions in the dashboard now say so instead of appearing to succeed.** Deleting a webhook or a user, resetting someone's two-factor auth, removing a passkey, ending a session or lifting maintenance mode each reported success and refreshed the list without ever checking whether the server had accepted the request. A rejected or failed call therefore looked exactly like a successful one, and the item silently reappeared on the next refresh. All of them now surface the server's error, as the other actions in the same screens already did.

- **Clearing a numeric field in Settings restores the default instead of saving zero.** Emptying the box was read as the number zero, so the setting was saved with an explicit `0` override, which for values like a timeout or a limit means something quite different from "unset". An empty field now removes the override and lets the server's own default apply.

- **The requests-per-second chart no longer overstates the rate when the live stream is down.** The rate was worked out by dividing the request count between two snapshots by a fixed two seconds, but the fallback used while the live stream is unavailable delivers snapshots every three seconds, inflating the reading by half. The chart now measures the actual time between snapshots, so it reads correctly in both modes.

- **A visitor's first WebSocket frames are no longer dropped by the client.** The client registered the stream only after telling the server the backend had accepted the upgrade, but the server completes the visitor's handshake the moment it sees that answer and can forward frames straight away. Anything arriving in that gap belonged to a stream the client did not yet know about and was discarded, so a visitor that sends immediately on connect, which client libraries routinely do, could lose its opening message. Registration now happens before the acceptance is announced, matching what the raw TCP path already did.

- **UDP tunnels honour `ip_family` and retry across every resolved server address.** The UDP bind path dialled the server directly instead of going through the shared connection logic used by the tunnel and TCP paths, so it ignored the configured address family and gave up after the first address it happened to pick. On a host where only one family reaches the server, a common IPv6-only or IPv4-only network, UDP binds failed while everything else connected normally.

- **A `HEAD` request in static-file mode no longer reads the whole file.** Serving a directory answered `HEAD` by loading the file's entire contents into memory and then discarding them, which made a HEAD as expensive as a GET. It now reads only the file's metadata, and reports the `Content-Length` a GET would have returned instead of `0`.

- **The published `aperio.yaml` schema described the wrong default for `connections`.** It documented a default of two parallel tunnel connections per service; the actual default has always been one. Editors and anyone reading the schema were told to expect redundancy that was not configured.

- **Changing an organization's hostname allowlist now takes effect on connections that are already open.** The endpoint's documentation stated that a hostname falling outside a tightened fence stops being served at once, but each client copies the allowlist when it connects, so in practice the old list stayed in force until that client happened to reconnect, which for a stable tunnel can be days. A hostname an operator had just revoked therefore kept being served. The new list is now pushed onto that organization's live connections, and any connection serving a hostname the fence no longer permits is dropped, with the number dropped recorded in the audit entry.

- **A webhook to an unresponsive receiver can no longer hang forever.** Webhook delivery builds its HTTP client with a ten-second timeout, but fell back to a default client if construction failed, and that default has no timeout at all, so a receiver that accepted the connection and then went silent would hold the delivery task open indefinitely. Construction failure is now reported as a failed delivery, matching how the OIDC and autoscaling call sites already handled it.

- **`GET /api/audit/verify` is restricted to the master administrator, as it always documented.** The endpoint verifies the tamper-evident hash chain across the audit files, which span every organization and so cannot be scoped to a tenant. It was nonetheless reachable by any signed-in user of any role, including a viewer in a child organization, who could use it to learn whether the server-wide audit log had been tampered with.

- **A raw TCP visitor that finishes sending no longer loses the response.** When a visitor closed its upload direction, which for many protocols simply means "request sent, now waiting for the answer", the server treated it as the end of the whole connection and cut off the download in progress, discarding data the backend had already sent. The download is now allowed to drain, bounded by the gateway response timeout so a client that never closes its side cannot hold the stream open.

- **A bogus stream id from one client can no longer make another client's response lose data.** Frames that end a stream were handled by removing it first and putting it back if the sender turned out not to own it. For the moment in between, the stream was missing, and the rightful owner's frames arriving in that window found nothing to deliver to and were dropped silently. Ownership is now checked and the stream removed in a single step, so a frame carrying someone else's stream id is simply ignored.

- **The dashboard's sessions list shows when each session actually started.** The "Signed in" column read "just now" for every row, including sessions opened days earlier, because the timestamp was converted from seconds to milliseconds twice over, once by the column and once again by the formatter, which already expects seconds. The doubly-scaled value lands tens of thousands of years in the future, and the formatter reports anything not yet in the past as "just now", so the column was uniformly useless for spotting an unexpected or stale session.

- **Opening one item in the dashboard no longer shows another one's data.** The request inspector, the webhook inbox and the traffic history chart each loaded their detail without checking, when the answer came back, that it was still the one being asked for. Moving between two items quickly, browser back and forward across `?inspect=` links, or switching the chart's date range twice, left two requests in flight, and whichever finished last won, even when it was the older one. The panel then showed a different item's details than the one selected, with nothing to indicate the mismatch. Each of these now discards a reply that arrives after the selection has moved on, matching what the client configuration dialog already did.

- **`idle_timeout` now counts every kind of traffic, not just ordinary HTTP requests.** The idle clock was only ever reset when a complete, buffered request arrived. Streamed uploads, WebSocket upgrades and raw TCP or UDP sessions never touched it, so a client kept busy exclusively by those, a file-upload endpoint, a chat or terminal backend, a database tunnel, concluded it had been idle the whole time and shut itself down while traffic was flowing, cutting live streams mid-connection. Every kind of inbound work now marks the client as in use, and the frames flowing through a long-lived WebSocket, TCP or UDP session keep marking it, in both directions, stamping only the frame that *opens* a stream still let a session outlasting the window be cut mid-traffic. A request that is still being answered also holds retirement back, however long the backend takes or the response streams. `idle_timeout` now retires a client only when it is genuinely doing nothing.

- **A rejected config reload no longer leaves static-file serving broken.** When a reload changed which directories are served, the client shut down the little loopback servers behind the directories that had been dropped, and it did so before checking whether the new configuration was usable at all. If the check then failed, the client reported that it was keeping the previous configuration and carried on, but that configuration now pointed at servers it had just closed, so every visitor request for a served directory came back as `502`. The client looked healthy and logged nothing further, while the reload it had explicitly refused to apply had already broken it. Serving is only retired once the new configuration has actually been adopted; a reload that fails validation now leaves the running one genuinely untouched.

- **A typo in `idle_timeout` no longer kills a running client on config reload.** Every other unusable value in `aperio.yaml` is handled the way a hot-reload should handle one: the client complains, keeps the configuration it already had, and carries on serving. `idle_timeout` alone was resolved by code that exited the process outright, because it was written for startup, where refusing to run is the right answer, and then reused unchanged on the reload path. Saving a mistyped duration into a config file while traffic was flowing therefore shut the client down completely, turning a correctable typo into an outage. The value is now reported like any other invalid setting: fatal at startup, and on reload merely logged, with the previous configuration left running.

- **A backend that speaks first over WebSocket no longer loses its opening message.** Once the tunnelled backend answered `101`, its connection was live and it could start sending immediately, and many protocols do exactly that, among them Socket.IO's open packet, MQTT over WebSocket, and most chat protocols, all of which greet the client before the client says anything. The server, however, only registered the relay for that stream after finishing the *visitor's* side of the handshake, and any frame arriving in between belonged to a stream it did not yet know about, so it was discarded without a trace. The result was a connection that looked established but where the first message simply never arrived, leaving clients waiting for a handshake reply that had already been thrown away. The relay is now registered before the upgrade request is even sent to the client, so it is already in place however fast the backend answers; frames arriving while the visitor's handshake finishes are buffered and delivered the moment the relay starts.

- **An organization's token quota now also covers tunnels provisioned through the API.** `max_tokens` caps how many credentials a child organization may hold, and the dynamic-token endpoint enforced it carefully, counting under the same lock as the insert so that two simultaneous requests could not both slip past the cap. `POST /aperio/api/tunnels` mints credentials into that very same store, but never consulted the quota at all, and it is open to the Operator role rather than admins only. A tenant limited to a handful of tokens could therefore hold as many live credentials as it liked simply by asking for tunnels instead, leaving the cap enforced on paper only. Both endpoints now share one check, applied the same way and under the same lock.

- **Round-robin load balancing spreads requests across the pool again when autoscaling is enabled.** With `APERIO_SCALING` on, every request first checks whether anything currently serves its route, so that a route with no client can be cold-started instead of answered with a gateway error. That check was made by asking the load balancer to pick a client and discarding the answer, but picking is not a free question: it advances the route's rotation cursor. Each request therefore took two steps around the pool instead of one, and a pool of two clients landed on the same one every single time, leaving its partner completely idle while the other took all the traffic. Every pool with an even number of clients was skewed the same way, and odd-sized pools rotated in an uneven order. The check is now a separate, side-effect-free lookup, so the rotation advances exactly once per request. Only the round-robin strategy was affected; sticky and primary/standby routing chose correctly throughout.

- **One visitor who stops reading no longer freezes every other visitor on the same tunnel.** A tunnel connection has a single loop reading the client's frames, and that loop handed each response chunk straight to the visitor waiting for it, waiting for room in that visitor's buffer before reading anything else. A visitor who stalls, a paused download, a browser tab in the background, a connection dropped without a close, fills that buffer, and the loop then sat there for up to the gateway response timeout of 30 seconds. Nothing else on the tunnel moved in the meantime: other visitors' responses, raw TCP and UDP data, and even the client's keepalive Ping all queued behind the one stuck stream, and a stall long enough to cross the client-down threshold dropped the client from routing entirely, so unrelated visitors received `504` errors. A single visitor could therefore take a tunnel down deliberately and repeatedly. Each stream now has its own forwarder that does the waiting, so the shared loop never blocks; the raw TCP path, which waited without any timeout at all, is covered too. Backpressure is unchanged, a stream whose buffers fill is still dropped after the same timeout, but now only that stream is affected.

- **A WebSocket handshake that dies before it completes no longer costs the server a tunnel slot forever.** The active-tunnel counter is raised while the upgrade request is still being processed, so that concurrent connections cannot race past `max_tunnels`, but it was only ever lowered again at the end of the connection handler. That handler runs from a callback the web framework simply discards, without calling it, when the connection is lost during the handshake, a client that goes away mid-upgrade, a proxy that times out, a dropped network. Every one of those left the counter one higher than the number of tunnels actually open, with no path back down, so a server seeing occasional handshake failures drifted upward until it hit its limit and began refusing every new tunnel with `503 Maximum active tunnels limit reached` while serving none, recoverable only by a restart. The reservation is now held by a guard that returns the slot if the connection handler never takes ownership of it.

- **Ctrl-C now stops a client that is between connection attempts.** A client whose server was unreachable sat in its reconnect backoff, which grows to over half a minute, and the shutdown signal did not interrupt that sleep: the client kept waiting, woke up, dialed the server anyway, and then hung indefinitely instead of exiting. The signal was lost outright in that window, because it is delivered only to whoever is already waiting for it, so the freshly connected client went on waiting for a notification that had already happened, and only a second, harder kill ended it. A shutdown request is now a state the client checks as well as a wake-up it waits for, so it is seen whether it arrives before, during, or after any of those steps: the backoff ends the moment the signal lands, no new connection is opened while shutting down, and a disconnected client exits immediately rather than draining nothing for the length of its retry delay. It still waits for whatever another service of the same process has in flight, so one service exiting no longer cuts short a sibling's drain.

- **The edge endpoints answer 404 instead of a 504 gateway error when the feature is off.** `/aperio/api/edge/ask` and `/aperio/api/edge/traefik` were registered only when `APERIO_EDGE_TOKEN` was set. Without it the paths matched no route, fell through to the visitor proxy, and came back as `504 Gateway Timeout - No client connected in time`, which reads as a broken tunnel rather than a server that was never configured for the integration, and the documented `404` could never actually be produced. Both paths are now always reserved and the handlers answer `404 edge integration is not enabled` when there is no token, so a Caddy `ask` or a Traefik provider poll against an unconfigured server gets a straight answer. Reserving the paths also means a request for them is never forwarded to a client's backend, and the token can now be turned on by config reload without restarting the server.

### Added

- **Clicking a connection in the clients table shows its effective configuration.** A dashboard that only shows binds and badges cannot answer "what is this client actually running", and the announced value is often not the configured one: a client with `bandwidth: 10mbit` and `connections: 10` announces 1mbit per connection, and nothing in the UI said so. The new dialog renders the connection's configuration as a YAML document, what the client announces over its heartbeat plus what the server applies on top, with every hostname labeled by where it came from (declared by the client, granted by the token, random subdomain, dashboard overrule). Any setting whose effective value differs from what was configured is highlighted in place with a `# declared` comment and listed underneath with both values, the reason, and who resolved it: a bandwidth budget divided across parallel connections or scaled to fit, a `connections` count clamped to the ceiling of 16, an unparseable rate that was ignored, a `cache: true` the server's disabled cache makes a no-op, a `public` or `auth` declaration the token does not permit, or an active overrule. Settings a client never announces (its target, request timeouts, header rules, health probes) are not knowable server-side and are left out rather than guessed at, which the document's own header states. Clients now announce their `connections` count and the settings they resolved differently in their heartbeat (additive, so an older client simply reports fewer notes). Raw data: the new `GET /aperio/api/clients/{id}/config`, org-scoped like every other client endpoint.

### Changed

- **A connection's effective-configuration view now speaks the config file's own vocabulary.** The document is meant to read like the `aperio.yaml` that would produce the connection, but it labelled the service with a `service:` key, which no config file has, the `services:` entries call it `name:`. It now renders `name:`, so the block can be compared against a real config without translating a key that exists nowhere else. Each hostname's origin comment reads "requested by the client" rather than "declared by the client", which no longer collides with the `# declared <value>` comments in the same document, where "declared" means the value the configuration asked for. The five-line header has been cut to the one caveat a reader actually needs, that settings the client never announces cannot appear.

- **Overrule targets the hostname the client configured, and no longer takes the random subdomain down with it.** The dialog pre-filled the first bind in the list, which for a client with a server-assigned subdomain was that random name rather than the hostname the operator had configured, and applying replaced *every* bind with the single value typed in. It now opens with one row per hostname the connection answers on, the client's own declared names first, then the random subdomain on its own row, each labeled with where it came from. Editing one row moves only that name and leaves the others routing untouched; emptying them all clears the override. `POST /aperio/api/clients/{id}/override` accepts the new `hostname_binds` list (each entry validated and org-fenced as before, blanks dropped, an empty list clearing the override) and still accepts the single `hostname_bind`, so `aperio-client api client override` is unaffected. `GET /aperio/api/stats` now reports `override_hostname_binds` in place of `override_hostname_bind`.
- **The clients table shows one hostname, the client's own.** A connection bound to several names filled the *Hostname* column with a badge per name, mixing the hostname the operator configured with the token-granted and randomly assigned ones in whatever order they happened to be in. The column now leads with a name the client declared for itself and folds the rest into a `+N` badge that lists them on hover. `GET /aperio/api/stats` reports the same ordering and gained `declared_hostnames` and `random_hostname` per client, so the distinction is available to API consumers too. This also fixes a client with several `hostname:` binds reporting only the first of them.

- **`bandwidth` is now a budget the client divides, instead of a rate it repeats on every connection.** The server shapes each tunnel connection with a token bucket of its own, so a service with `connections: 10` announcing `10mbit` was really allowed 100mbit, and a top-level `bandwidth` was copied into every `services:` entry, multiplying again by the number of services. The client now settles the whole thing before connecting: a service's share is divided across its `connections`, and the top-level value is a budget the entries are settled against rather than a per-entry default. Services that named a rate keep it and the remaining budget is split equally among those that did not; if the named rates would leave the others nothing, they are all dropped and the budget is split equally; if every service named a rate and together they overshoot, the rates are scaled down proportionally. The last two cases log a warning at startup, and every service logs the rate one of its connections announces. With no top-level budget the behavior is unchanged for services that name their own rate, and services that do not stay unlimited. Existing configs that set only a top-level `bandwidth` will now see the announced total match what they configured, which is a real reduction where several services or connections were multiplying it. See [Sharing the bandwidth budget](docs/configuration.md#sharing-the-bandwidth-budget).

## [0.5.0] - 2026-07-25

### Added

- **The dashboard now has an Autoscaling page.** Under *Access*, it lists every autoscaling record clients have armed for the current organization with the live state of its pool: connected instances against the ceiling, a utilization bar that turns amber once the scale-out target is crossed, the endpoint the server calls (with a badge when the call is signed, never the secret itself), and whether the breaker has disarmed the record. A `scale to zero` badge marks the binds a request can cold start, and an operator can disarm a record from here; a client that is still running and still declares the block re-arms it on its next heartbeat. Records are only ever created by clients declaring a `scaling:` block, so the page is otherwise read-only.
- **Autoscaling: the server can now ask an endpoint you control for capacity.** Aperio is the only component that sees demand and supply at the same moment (requests arriving for a hostname, and the clients connected to serve them with the concurrency limits they announced), so it decides *when* capacity is needed and signals a desired capacity to a URL you own; starting anything stays the provider's job. Two triggers share one state machine: a **cold start** when a request arrives for a hostname no client serves (the request is held and re-dispatched instead of answering 504), and a **scale out** when the pool stays saturated for a full window. Scaling *in* is client-driven: the new `idle_timeout` retires an idle client with a graceful drain, so the server never kills anything. Declared per client in `aperio.yaml` under `scaling:` (`url`, `secret`, `min`, `max`, `cold_start`, `target_utilization`, `window`, `cooldown`), announced on every heartbeat and persisted server-side against the hostname so a scale-to-zero service can be woken when nothing is running. Off unless the operator sets `APERIO_SCALING=1`. New article: [Autoscaling](docs/autoscaling.md).
- **Saturation is measured from the concurrency limiters, not request counts.** Each client already queues on a limiter sized by its announced `max_concurrent`, so permits in use is exactly the work the pool is doing; utilization is `inflight / sum(max_concurrent)` over routable primary-tier clients, and a scale-out needs it to hold above `target_utilization` for the whole `window`. Standby tiers (`priority > 0`) never count as capacity, since counting them would mask saturation of the primaries. `GET /aperio/api/scaling` and `aperio-client api scaling list|disarm` surface every armed record with its live `instances`, `capacity`, `inflight`, `utilization`, and breaker state.
- **Cold starts are single-flight, bounded, and fenced.** A burst of a hundred requests against a sleeping service produces exactly one call; a failed call backs off exponentially and five consecutive failures disarm the record until it is re-announced; at most eight calls are ever in flight across all binds, so a restart cannot burst against a provider API. The held request releases its global concurrency slot first, so visitors waiting on one sleeping service cannot starve every healthy service on the server. Maintenance mode, a visitor the owning token's `allowed_ips` would reject, and a disarmed record never trigger a (billable) cold start. Because the request was never dispatched, holding it is safe for every method, so the `failover` idempotency rules deliberately do not apply. The outbound call is SSRF-fenced: https only unless `APERIO_SCALING_ALLOW_HTTP=1`, every resolved address checked against loopback/private/link-local (including the cloud metadata address) and their IPv6 forms, no redirects followed, and the secret never logged or returned.
- **Traefik and Caddy can now learn Aperio's runtime hostnames by themselves.** An edge proxy in front of Aperio cannot route or issue a certificate for a hostname that only appears when a client connects, and container labels cannot express it either (they are fixed at container creation). Two new read-only endpoints close that gap, both gated by the new `APERIO_EDGE_TOKEN` (unset = they are not registered at all, and answer `404`): `GET /aperio/api/edge/ask?domain=<host>` answers `200`/`404` by whether the hostname is currently served, which is exactly Caddy's on-demand TLS `ask` contract, so Caddy issues a certificate the moment a tunnel appears; and `GET /aperio/api/edge/traefik` returns a Traefik dynamic-configuration document with one router per served hostname for Traefik's HTTP provider. The token is accepted as `Authorization: Bearer` or `?token=`, since Caddy's `ask` cannot send headers. `APERIO_EDGE_SERVICE_URL`, `APERIO_EDGE_ENTRYPOINTS`, and `APERIO_EDGE_CERT_RESOLVER` shape the generated routers; `APERIO_EDGE_INCLUDE_OFFLINE` additionally publishes hostnames a token permits but nobody serves yet (off by default: it lets a tenant provoke an ACME request for any hostname its token covers). The inventory covers **connected** clients even when their backend health probe is failing, since withdrawing the route would turn a recoverable `504` into a TLS failure, and it is deterministically ordered so a repeated poll yields a byte-identical document and Traefik never churns routers. New article: [Behind a Dynamic Edge Proxy](docs/edge-proxy.md), which also covers the wildcard-domain setup that needs no integration at all.
- **Organizations can be fenced to their own hostnames.** A child organization now carries an optional hostname allowlist, set at creation or later (`hostnames` on `POST /aperio/api/orgs`, the new `PUT /aperio/api/orgs/{id}/hostnames`, `aperio-client api org create|hostnames --hostname ...`, or the dashboard's Organizations page), and every hostname bind made inside the organization must match it. Without a fence a token carrying `*` (or no hostname permission at all) may bind **any** hostname on the server, so an org admin minting a wildcard token for their own tenant could claim a hostname belonging to another one. Entries are an exact hostname (`acme.com`) or a subdomain wildcard (`*.acme.example.com`, any depth, not the parent itself). The fence is enforced at every point a hostname can be claimed, not only once: token create/edit refuse an out-of-fence permission (403), client connect re-checks every declared and token-granted bind (so a token minted before the fence cannot bind past it), ephemeral tunnel provisioning refuses an out-of-fence hostname, and the dashboard bind override refuses one too. A server-assigned random subdomain is exempt, since the tenant cannot influence which name it gets. An empty list (the default) means no restriction, so existing deployments are unchanged, and the master organization is never fenced.
- **`aperio-client api ...` brings the whole admin API to the command line.** Everything the dashboard does is an HTTP call, and the client can now make those calls directly, so share links, tokens, ephemeral tunnels, maintenance mode, the kill switch, cache purges, webhooks, the inbox, users, sessions, organizations, admin keys, settings, backup/restore, and every read-only report (stats, history, uptime, logs, topology, bandwidth, slow endpoints, route trends, audit, self-health, traffic CSV, OpenAPI) are scriptable without a browser session or a hand-written `curl`. One call per invocation: the server's JSON answer is pretty-printed on stdout and the exit code is 0, while an authentication failure, a non-2xx status, or a transport error prints to stderr and exits 1, so `set -e` scripts stop on an API error. Logs move to stderr for these commands, so piping into `jq` is safe. Example: `aperio-client api share --hostname app.example.com --path /test --expire 1d`. Lifetimes accept human durations (`45s`, `30m`, `2h`, `1d`, `2w`, `never`), and the host/path scope reuses the existing `--hostname` / `--path` flags. Passwords and JSON documents accept `-` to read from stdin, keeping secrets out of shell history. Documented in the new [Admin API from the CLI](docs/cli-api.md) article.
- **`APERIO_API_KEY` (CLI `--api-key`, yaml `server.api_key`) configures the admin key the `api` commands authenticate with.** It is a programmatic admin key with its own role and organization, presented as `Authorization: Bearer`, and is unrelated to the tunnel token. When no admin key is set, the tunnel token is sent instead, which the server accepts only where the master token is a valid credential (`api tunnel create` / `delete`), so a CI job that only provisions preview tunnels needs no admin key at all.
- **`APERIO_WEBAUTHN_RP_ID` makes one passkey work across every subdomain.** With passkeys enabled, the RP ID was fixed to the exact host of `APERIO_WEBAUTHN_ORIGIN`, so a credential registered on `aperio.robogon.com` failed on a sibling host like `test-aperio.robogon.com` (it is not a subdomain of the origin's host). Set `APERIO_WEBAUTHN_RP_ID` to the shared parent registrable domain (`robogon.com`) and one passkey covers the whole `*.robogon.com` tree: the RP ID becomes the parent and ceremonies from any of its subdomains are accepted. WebAuthn has no wildcard RP ID, so a parent-domain RP ID is the supported mechanism. The value must be the origin's host or a parent of it (never a public suffix like `com`); changing it invalidates passkeys enrolled under the previous RP ID, so users re-enroll. Default behavior (exact-host RP ID) is unchanged when the variable is unset.

### Changed

- **OTLP request traces now mirror the real flow, not an estimated waterfall.** The per-request child spans were six flat, split-transit *estimates* presented as the timeline, approximations that read like measurements. They are replaced by three **measured** server-clock spans that follow the request's actual path, `queue & routing` (arrival → dispatched), `tunnel round-trip` (dispatched → response: out over the tunnel to the client and back), and `server → visitor` (response → served), so a trace shows at a glance where a request spent its time. `queue & routing` further breaks into its own measured sub-spans, `await client` (waiting for a connected client), `admission` (server-wide concurrency slot), `routing` (WAF, route limit, client selection), and `dispatch prep` (token check, header/trace build, send), so a request blocked before it ever left the server is pinpointed. The client/backend breakdown (`tunnel → client`, `client → backend`, backend first-byte/body, `client → tunnel`) is still available on the buffered path but now **nests under** `tunnel round-trip` and stays flagged `aperio.estimated = true`, so estimated detail can no longer be mistaken for a measured boundary. Streamed responses, which report no client offsets, now get the three real spans too (previously a coarse collapsed set).

- **The Topology view now shows the routing the server owns, not just connected clients.** It was a second rendering of the Clients table, derived from the same live-client snapshot, so it only ever showed connected tunnel clients. It is now backed by a dedicated `GET /api/topology` endpoint and shows client-less routing too: static `routes:` (redirects and fixed responses, drawn as self-contained nodes with their action) and public `expose:` TCP ports (drawn reaching their serving client, or dangling red when none does). - **Topology also flags declared-but-offline routes.** A hostname or path a token is permitted to bind but which no live client currently serves is drawn as a dashed, faded node labelled with the granting token, so "the service that should be up but isn't" is visible at a glance, something the connected-clients table structurally cannot show (there is no row for an absent client). Scoped per organization like the client list.
- **Topology surfaces passive outlier ejection.** A client that crossed the outlier failure threshold (5xx / timeout / connection loss) is silently pulled from routing while its tunnel connection stays up, a state no dashboard screen showed. The routing map now colours such a client red and labels it `ejected` (alongside `draining`), and the new `ejected` flag rides on every client detail (also available to `/api/stats`).

The client-anchored stages are estimates (transit split evenly; client and server clocks are never mixed) and carry an `aperio.estimated` attribute. Synthesized entirely server-side from timings the client already reports, no client or protocol change, on the buffered (non-streamed) response path.

### Changed

- **Client services default to a single tunnel connection again (was 2).** `connections` now defaults to `1`, reverting the `2` default briefly shipped in 0.4.2. Opt into parallelism explicitly with `connections: N` (yaml) or `APERIO_CONNECTIONS=N` when you want a dropped connection covered by a sibling with no visitor-facing gap; the server still load-balances across the connections of a service.
- **A panic in a request handler now returns a clean 500 and is logged, instead of silently dropping the connection.** The HTTP stack gained an outermost catch-panic layer, so a panic while serving one request (proxy or dashboard) is contained to that request, the visitor gets a `500`, every other in-flight request and the process are unaffected. A process-wide panic hook additionally routes *every* panic (including those in spawned background tasks, which unwind silently by default) through the server's structured log with its message, source location, thread, and, when `RUST_BACKTRACE` is set, a backtrace, so contained panics are visible and alertable rather than vanishing. The server already builds with `panic = "unwind"`, so this hardens observability and the request edge without changing the crash model.
- **The backend health probe runs once per service, not once per parallel connection.** A service with `connections: N` spawned N independent `target_health`/`wait_for_backend` probes against the backend, N× the health-check load, and connections could briefly disagree during a blip. The probe is now a single per-service task writing a shared verdict that every connection reports in its heartbeat.
- **The Live Tail view is now a console toggle inside Live Traffic, not a separate page.** The dashboard had two sidebar entries, Live Traffic (table) and Live Tail (`tail -f` terminal), rendering the exact same request stream with only the presentation differing. They are merged: Live Traffic now has a **Table / Console** switch, so the search box, method/status filters and pause control are shared across both renderings. The standalone Live Tail page is gone; old `?tab=tail` links land on Live Traffic, and the console view honours host/status in the shared search.
- **The Clients / Uptime table is ordered by most-recent activity and hides long-dead services.** Rows were sorted alphabetically by name, so a live service and the leftover record of a one-off connection that errored and was closed sat side by side, and the dead ones lingered for their full 30-day retention. The table now sorts by the last successful ping (most-recently-active first, name as a tiebreak), and a service that has been continuously down for over 24 hours drops out of the view entirely, its record is still kept in the store until the existing GC removes it, so it reappears if it comes back up.

### Fixed

- **The delete-webhook confirmation no longer overflows its dialog.** A long webhook URL (e.g. a Discord endpoint) is a single unbreakable string, so it spilled past the dialog's edge; the URL now wraps within the dialog (`overflow-wrap: anywhere`).
- **A service that opts into caching while the server cache is off is now surfaced, not silently ignored.** `cache: true` only takes effect when the operator has also enabled the server-side response cache (`APERIO_CACHE`); previously a service that opted in against a disabled cache got nothing, with no signal either way. The server now logs a one-time warning per client (`… requested response caching … but the server cache is disabled …`) and the dashboard's Clients table shows a `cache off` badge on that connection, so the misconfiguration is visible to both the operator and the service owner. A new [Response Caching](docs/caching.md) doc page explains the two-key opt-in model.
- **Chat webhooks (Discord, Slack, Teams) now send a coloured card instead of a flat text dump.** The `discord` format only emitted a plain `content` message and the `slack` format a plain `text` line, both looked no different from the raw payload and carried no title or colour, so choosing them appeared to do nothing; the `teams` card was coloured but hard-coded green for *every* event (a disconnect looked as green as a connect). Each now renders a proper card titled with the event, one field per event datum, whose colour encodes the event's nature, green for good/recovered events, red for failures like `client_disconnected`/`alert_triggered`, amber for warnings, neutral otherwise: a Discord `embed`, a Slack `attachment`, and a Teams `MessageCard` with an event-driven `themeColor`.
- **Dashboard: the Organizations UI and the multi-connection tooltip are now translated in every language.** 15 strings, the organizations panel/dialogs and the `×N` parallel-connections tooltip, existed only in English and Turkish, so the German, Spanish, French, Russian, Chinese, and Japanese dashboards fell back to English for them. They are now translated in all six.
- **Static-serve listeners are stopped when a config reload drops their directory.** In `--serve` mode the client started a loopback HTTP listener per served directory but never tracked or cancelled it, so a config reload that changed or removed a `serve:` directory left the old listener running forever (a file-descriptor/memory leak). `serve::start` now returns the accept loop's handle, and a reload aborts the listeners for directories the new config no longer serves.
- **Proxied WebSocket handshakes no longer forward the visitor's `Sec-WebSocket-Key`/`Version`/`Accept` to the backend.** These are per-hop handshake mechanics that tokio-tungstenite generates and validates for the client→backend connection; copying the visitor's values overwrote the generated key, so a strict backend (e.g. Node.js `ws`, Gorilla) could reject the handshake with `400`. Only the end-to-end negotiation headers (`Sec-WebSocket-Protocol`/`Extensions`, `Origin`) are forwarded now.
- **Path-bind trimming now respects segment boundaries.** With `trim_bind` on, the client stripped the `path_bind` prefix with a raw string `starts_with`, so bind `/api` also matched and mis-stripped unrelated routes like `/apiv2/x` (forwarded to the backend as `/v2/x`). Trimming now applies only at a `/` segment boundary, exactly `/api` or `/api/…`, across the HTTP/1, HTTP/2, Unix-socket, and WebSocket-upgrade proxy paths.
- **A bad token for one `--bind-tunnels` peer no longer kills the whole process.** Tunnel discovery for a peer that got `401`/`403` (or whose discovery URL failed to build) called `process::exit(1)` from its per-peer background task, tearing down every other healthy peer's already-bound listener with it. It now logs the error and skips just that one binding, leaving the rest running.
- **A streamed response that hits the size limit, or whose backend errors mid-body, now aborts instead of silently truncating.** On exceeding `max_response_body_size` (or a mid-stream backend failure/read timeout), the client sent a clean `ResponseEnd`, so a chunked response with no `Content-Length` reached the visitor as a successful, complete-looking `200` that was actually cut short. The client now sends a new additive `ResponseAbort` frame; the server drops the visitor's body stream with an error, terminating the connection abnormally so the visitor detects the incomplete response. Covers the http/1, HTTP/2, and Unix-socket proxy paths; older servers ignore the frame and fall back to the existing stream timeout.
- **A slow tunneled WebSocket/TCP stream can no longer stall the whole connection.** Server→client `WsData`/`TcpData` frames were delivered with an awaited, timeout-bounded channel send *inside* the tunnel read loop, so one backend that stopped reading could block the loop for up to the request timeout, starving `Pong` processing and tripping the 15 s liveness watchdog, which reset the connection and dropped every stream on it. Delivery is now a non-blocking `try_send` (as UDP already did): a backed-up stream is dropped on its own, leaving the connection and every other stream healthy.

## [0.4.2] - 2026-07-22

### Security

- **Tunnel WebSocket upgrades are rate-limited before token verification.** The main `/aperio/ws` endpoint verified the connection token without first applying the per-IP rate limit that the sibling `/aperio/tcp` and `/aperio/udp` endpoints already enforce, leaving unbounded token brute-force and canary/`token_new_ip` webhook spam open from a single IP. It now applies the same rate-limit gate before authorization.
- **Hop-by-hop framing headers are stripped in the HTTP/1 and Unix-socket proxy paths.** The client's reqwest (`proxy/http.rs`) and hyper http/1 (`proxy/unix.rs`) request-forwarding paths did not drop `transfer-encoding`, so a visitor-supplied `transfer-encoding: chunked` could ride through and collide with the client's own body framing, an HTTP desync / request-smuggling surface against raw-socket backends. They now strip `transfer-encoding` (and the hop-by-hop `trailer`), leaving `content-length` as the single framing signal, matching the HTTP/2 path. `content-length` is deliberately kept so streamed uploads still frame without falling back to chunked.
- **`settings.json` is written owner-only (0600).** The dashboard settings file holds `auth_credentials` as plaintext `user:password` but was written with the default umask (typically 0644), readable by other local users. It is now created, and re-permissioned on every write, as mode 0600 on Unix, matching the client device-key file.

### Added

- **Client IP-family control when dialing the server.** A new `ip_family` setting (`auto` (default), `ipv4`, `ipv6`; CLI `--ip-family`, env `APERIO_IP_FAMILY`, yaml `ip_family`) chooses which address family the client uses to reach the tunnel server. The client now resolves every address itself and tries each in turn (IPv4-first, interleaved for `auto`) with a per-address connect timeout, so a hostname that resolves to an unreachable family, e.g. a Cloudflare-fronted server publishing AAAA the host cannot route to, no longer strands the connection; `ipv4` forces IPv4 deterministically. Applied to all three server-dial sites (main tunnel, `check`, and the TCP bridge).
- **OTLP endpoint reachability probe at startup.** With `APERIO_OTEL` enabled, the server now TCP-probes the configured OTLP endpoint on startup and logs the result ("OTLP endpoint … is reachable" / "… unreachable, trace spans will be dropped"), so a misconfigured or down collector is obvious immediately instead of silently dropping every span. Advisory only, it runs off-thread, never blocks, and never fails startup.
- **A client process's parallel connections are grouped into one dashboard entry.** A client opening multiple connections to a service (`connections: N`) previously appeared as N look-alike rows in *Active Tunnel Connections* and N nodes in *Topology*, each also minting its own random preview hostname. The client now announces its process identity via an `x-aperio-instance` handshake header; the dashboard collapses a process's connections to the same service into a single row/node with a `×N` connection count (request counts summed, enable/disable acting on all N), and the server derives one shared random hostname per process+service instead of a distinct one per connection.

### Changed

- **Client services now open 2 parallel connections by default (was 1).** `connections` defaults to `2` so a single dropped connection, e.g. a CDN recycling a long-lived WebSocket, is covered by the sibling connection with no visitor-facing gap; the server load-balances across them. Set `connections: 1` (yaml) or `APERIO_CONNECTIONS=1` to restore the previous single-connection behaviour.

### Fixed

- **OTLP trace export no longer panics its exporter thread.** The batch span processor drives the OTLP/HTTP exporter from a dedicated thread that has no Tokio runtime; with the async reqwest client it panicked (`there is no reactor running, must be called from the context of a Tokio 1.x runtime`) the moment a real span was exported, killing the exporter so, with OTel enabled, no span ever reached the collector. The exporter now uses the blocking reqwest client, which owns an internal runtime and exports correctly from that thread. TLS behaviour (rustls with the process-wide ring provider) is unchanged.
- **Shutdown aborts an in-progress server connection attempt.** The client's reconnect loop awaited the server dial (TCP connect + WebSocket handshake) without watching the cancel signal, so a half-open server that accepted the socket but stalled the handshake, which has no timeout, could keep a service alive past a requested shutdown. The dial now runs under the cancel signal and is torn down immediately when the client is told to stop.

## [0.4.1] - 2026-07-21

### Changed

- **OTLP trace export no longer pulls in the aws-lc-rs crypto backend.** The OpenTelemetry OTLP/HTTP exporter previously resolved (through reqwest 0.13) to the aws-lc-rs rustls provider, adding a second crypto backend and its `aws-lc-sys` C/asm build to the dependency graph. - **Environment-variable names standardized (breaking).** Every setting now has exactly one canonical `APERIO_*` spelling, with no aliases. The client's `APERIO_CLIENT_*` scoping aliases (`APERIO_CLIENT_TARGET`, `APERIO_CLIENT_SERVE`, `APERIO_CLIENT_TIMEOUT`, …) and the `APERIO_HOSTNAME_BIND` / `APERIO_PATH_BIND` spellings are dropped in favour of the short canonical forms (`APERIO_TARGET`, `APERIO_SERVE`, `APERIO_TIMEOUT`, `APERIO_HOSTNAME`, `APERIO_PATH`, …); `APERIO_CLIENT_ID` keeps its name because "client" is part of the concept, not a redundant prefix. On the server the gateway-timeout vars lose their redundant `SERVER_` prefix, `APERIO_SERVER_GATEWAY_TIMEOUT` → `APERIO_GATEWAY_TIMEOUT` and `APERIO_SERVER_GATEWAY_RESPONSE_TIMEOUT` → `APERIO_GATEWAY_RESPONSE_TIMEOUT`, and the matching `aperio-server.yaml` keys become `gateway_timeout` / `gateway_response_timeout` to preserve the mechanical yaml↔env mapping.

### Fixed

- **Streamed response bytes now count toward the token daily quota.** A response delivered as a stream (rather than buffered) was charged to org stats but escaped the serving token's daily byte quota that buffered responses are charged for; each streamed chunk is now attributed to the token too.
- **Rate-limit env vars reject nonsensical values.** `APERIO_IP_LIMIT_MAX` / `APERIO_IP_LIMIT_REFILL` now fall back to their defaults when set to `0`, a negative, `NaN`, or infinity (which would have wedged the limiter), matching the dashboard settings validation.
- **`security_headers` mappings reject unknown keys.** A mistyped granular security-header field (e.g. `frame_option`) is now a config error instead of being silently ignored.
- **Config schema:** the `failover` example lists the accepted values (`fail`/`retry`/`wait`/`retry-wait`); `off` was never valid. Additional secret-looking body/JSON field names (`totp`, `pin`, `passphrase`, `jwt`, `session_token`, `cvv`, …) are now redacted in the request inspector.

### Security

- **TOTP replay prevention.** A successful two-factor login now records the step counter the code matched and refuses any later code from the same or an earlier step, so a code intercepted in transit can no longer be replayed within its ~90-second validity window.
- **Proxied WebSocket cleanup + ownership.** When a tunnel client disconnects, the server now drains its live proxied public WebSockets (sending a close to each) instead of leaking the `ws_streams` entry and its relay tasks and leaving the public peer hung. Inbound `WsData`/`WsClose` frames are also honoured only when the sending client owns the target stream, matching every other tunnel stream type.

### Added

- **`aperio-server --print-schema`.** The server binary now emits the JSON Schema for `aperio-server.yaml` on demand (previously only produced as a build artifact of `aperio-client`), so a deployment can regenerate it without the source tree, point an editor's `yaml.schemas` at the output for completion and validation. Reinforces `aperio-server.yaml` as the primary, schema-checked configuration surface, with environment variables as the fallback.
- **`aperio-server --print-config`.** Prints the effective configuration and exits without starting the server: every `APERIO_*` value in effect, each attributed to its source (the environment or the `aperio-server.yaml` file), the structured file sections, and any persisted dashboard overrides (which win at runtime). Secret-looking values are masked and long ones summarized. Answers "what is actually set, and where did it come from?" without reading the process env by hand.
- **Live-WebSocket connection limit.** `APERIO_MAX_WS_CONNECTIONS` (default `10000`, `0` = no cap) caps the number of concurrently-live proxied public WebSockets. WebSockets are long-lived, so they get their own ceiling separate from the short-lived `APERIO_MAX_CONCURRENT_REQUESTS` request limit; an upgrade beyond the cap is rejected with `503`. Closes a gap where a flood of proxied WebSocket upgrades could exhaust server memory/FDs/tasks (per-IP rate limiting throttles the connection *rate*, not the live *count*, and does nothing against a distributed source).
- **Documentation deepening.** New architecture deep-dive (tunnel protocol, request lifecycle, concurrency, state), upgrade guide + client/server compatibility notes, and a performance-tuning guide.
- **Server self-health + CSV export.** `GET /aperio/api/self-health` reports process RSS (Linux), SQLite store size, cache occupancy, uptime and client count (dashboard card); `GET /aperio/api/export/traffic.csv` streams the per-period traffic history as CSV.
- **Benchmarks + load harness.** criterion micro-benchmarks for the cache hot paths (`cargo bench`, reported in CI) and a k6 soak test (`tests/soak.js`) with error-rate and p95 thresholds.

- **Dashboard tests.** A [vitest](https://vitest.dev) unit suite (run in CI alongside the i18n check) plus a [Playwright](https://playwright.dev) shell smoke test, the dashboard had zero tests before.
- **Dashboard polish.** Capture permalinks, the inspected request id lives in the URL (`?inspect=`), so an opened capture can be bookmarked, shared, and reopens on reload, and quick-fill token presets (CI preview / 30-day / long-lived) in the token create dialog.
- **Per-hostname fallback URLs.** A `fallbacks:` section redirects an unclaimed hostname (no connected client) to a configured origin/status URL (`302`, or `301` with `permanent`, optional `preserve_path`) instead of a `504`, with a `*` catch-all. Rejected visitors still get the stealth answer so a route's existence never leaks.
- **Cache depth package.** `GET /aperio/api/cache/stats` reports entry count, byte size, and hit/miss ratio (with a dashboard card on the Breakdown page). Tracking query parameters (`utm_*`, `gclid`, `fbclid`, …) are stripped from the cache key so ad-tagged URL variants share one entry. `APERIO_CACHE_NEGATIVE_TTL` negatively caches `404`/`410` responses for a short window to shield a backend from repeated misses. A backend `Surrogate-Key` response header tags cache entries, and `POST /aperio/api/cache/purge` with `surrogate_key` invalidates every entry carrying that tag (CDN-style tag purge).
- **Serve mode SPA fallback + custom 404.** `APERIO_SERVE_SPA=1` falls a navigation that resolves to no file back to the root `index.html` (status 200) so a client-side router owns the route; `APERIO_SERVE_404` serves a custom page for the remaining misses.

- **Canary tokens + token new-IP alerting.** A per-token `canary` flag turns a dynamic token into a decoy: any successful authentication with it emits a `canary_tripped` webhook + audit event, so a leaked `aperio.yaml`/dump surfaces as a clear breach signal. Independently, the server remembers the source IPs each token connects from (in-memory) and emits `token_new_ip` the first time a token appears from a previously unseen address.
- **Admin surface IP allowlist.** `APERIO_ADMIN_ALLOWED_IPS` (comma-separated IPs/CIDRs) fences the `/aperio` dashboard and `/aperio/api/*` endpoints to matching client IPs (`403` otherwise). The login page, auth endpoints, health and OIDC routes stay reachable from any address so `APERIO_SERVER_AUTH`-protected proxied sites keep working; proxy traffic and tunnels are never affected.
- **Route-shadowing lint.** `--check-config` now flags `routes:` entries that can never fire because an earlier rule's hostname + path bind always matches them first (first-match order), catching both exact duplicate binds and a broad rule hiding a narrower one.
- **Hot-reload audit diff.** The `config_reloaded` audit entry now records `key: old→new` for every changed live setting (secret-looking keys masked, long values summarized) instead of just "reloaded".
- **Audit chain verification.** `aperio-server --verify-audit` verifies the tamper-evident hash chain across the active audit log and every rotated generation (exit 0/1), and `GET /aperio/api/audit/verify` exposes the same check to the dashboard.
- **Scheduled physical DB backups.** `APERIO_BACKUP_INTERVAL` / `APERIO_BACKUP_DIR` / `APERIO_BACKUP_KEEP` periodically snapshot the SQLite store with `VACUUM INTO` (a self-contained `aperio-<epoch>.db`, no WAL/SHM), pruning old snapshots and recording a `db_backup` event.
- **i18n key coverage CI check.** `npm run check-i18n` parses the dashboard source with the TypeScript compiler and fails the build on duplicate or stale (no-longer-used) dictionary keys, reporting cross-language gaps.
- **Production hardening + threat-model docs.** A pre-flight hardening checklist and a formal trust-boundary threat model under `docs/`.
- **Transparent retry on buffered 5xx.** `APERIO_RETRY_ON_5XX` re-dispatches a fully-buffered server-error response to another client (bounded by the failover jump budget and method idempotency) instead of returning it; `APERIO_RETRY_STATUSES` narrows which codes qualify.
- **Passive outlier ejection.** `APERIO_OUTLIER_EJECTION` temporarily removes a client from routing after too many 5xx/timeout/connection-loss failures in a short window (independent of the active `/health` probe), with per-route fail-open. Tunable via `APERIO_OUTLIER_MAX_FAILURES` / `_WINDOW` / `_EJECT_SECS`.
- **Per-route request rate limiting.** A `rate_limits:` section (`[{hostname, path, rps, burst}]`) caps the aggregate request rate to a matched host+path via a shared token bucket, answering `429`; validated by `--check-config` and re-applied on hot-reload.
- **Scoped programmatic admin keys.** Least-privilege, revocable `Authorization: Bearer` credentials for automation, scoped to a role + organization (no master token needed). Master-admin CRUD at `/aperio/api/admin-keys` with a one-time secret and a dashboard management section under Users.
- **WAF-lite.** A `waf:` section of deny rules (path regex / method / header) answering `403`, plus per-route `max_body` size rules answering `413`, evaluated before dispatch; invalid rules are dropped and flagged by `--check-config`.
- **Token-to-device pinning (TOFU).** `APERIO_TOKEN_PINNING` pins the first client device key announced for a dynamic token and rejects a later connection presenting a different/missing key (`token_pin_mismatch` event), so a leaked token cannot be replayed from another machine. Clients announce a key via `APERIO_DEVICE_KEY` / `APERIO_DEVICE_KEY_FILE`; rotating the token clears the pin.
- **Per-service response timeout.** A per-service `response_timeout` (announced via the tunnel handshake, `APERIO_RESPONSE_TIMEOUT`) overrides the global gateway response timeout for a slow report/upload endpoint.
- **Per-organization quotas + monthly usage.** Orgs gain `max_clients` / `max_tokens` / `max_users` / `max_bytes_month` quotas enforced at the relevant create/connect/dispatch points; `PUT /aperio/api/orgs/{id}/quota` sets them and `GET /aperio/api/orgs/{id}/usage` reports current-month usage (also emitting an `org_usage` webhook). A per-org quota + usage dialog is added to the dashboard.
- **Per-organization OIDC (SSO).** An org can bring its own identity provider (`PUT /aperio/api/orgs/{id}/oidc`): members sign in at `/aperio/oidc/login?org=<id>` and get a session **bound to that org**, an admin within their own tenant, never the master super-admin. Orgs without an override fall back to the global `APERIO_OIDC_*` settings.
- **Zero-downtime restarts.** `APERIO_REUSEPORT` binds the listener with `SO_REUSEPORT` so a new process can share the port with the draining old one, enabling rolling restarts without dropping visitor traffic.
- **Client cross-server failover.** `APERIO_SERVER_URLS` (comma-separated) lets a client rotate across a fleet of Aperio servers on connection failure, the client half of a highly-available deployment.
- **Protocol fuzzing.** `cargo-fuzz` targets under `fuzz/` for the tunnel binary-frame parser and the JSON/zlib decode paths, with a short CI smoke run.

## [0.3.0] - 2026-07-19

### Added

- **API token rotation with a grace period.** `POST /aperio/api/tokens/{id}/rotate` mints a fresh secret for a dynamic token (returned exactly once) while keeping its identity, permissions, limits, expiry, and every reference to the token id are untouched. The previous secret stays accepted until `now + grace_seconds` so running clients and CI jobs migrate without a hard cutover; `grace_seconds: 0` cuts it off immediately. Only the most recent previous secret is kept; org-isolated, audited (`token_rotated`) and emitted as a webhook event.
- **Per-service security header presets.** A `security_headers:` key (yaml top-level or per `services:` entry) injects standard security response headers without hand-writing `headers:` rules: `true` enables HSTS, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and `Referrer-Policy`, and a mapping picks headers individually (`hsts`/`hsts_max_age`/`frame_options`/`nosniff`/`referrer_policy`/`csp`). The preset folds into the service's response header rules; explicit `headers:` rules win over it.
- **Per-service request body size limit.** `max_request_body` (yaml top-level or per-service, `APERIO_MAX_REQUEST_BODY`) is announced to the server via the tunnel handshake; the server rejects bigger uploads with an early `413` before the body enters the tunnel, for declared content-lengths and while reading buffered or streamed bodies. A declared cap can only tighten the global `APERIO_MAX_BODY_SIZE`, never widen it.
- **Per-hostname custom error pages.** A structured `error_pages:` section in `aperio-server.yaml` maps a hostname to its own `504_page` / `503_page` HTML files, overriding the global `APERIO_504_PAGE` / `APERIO_503_PAGE` for that host on gateway-timeout and maintenance responses. Loaded at startup and re-read on config hot-reload; unreadable files fall back to the global pages.
- **stale-while-revalidate and a cache purge API.** The response cache honors RFC 5861 `stale-while-revalidate=N`: a response advertising it keeps serving for N seconds past its `max-age` (marked `x-aperio-stale`) while exactly one elected leader re-fetches it in the background through the already-selected client, visitors never wait on the refresh, and concurrent stale hits never stampede the backend. `POST /aperio/api/cache/purge` (admin, audited `cache_purged`) drops cached entries by `hostname` and/or `path_prefix`, an empty body clears the whole cache, for immediate invalidation after a deploy.
- **Single-flight coalescing on cache miss.** The first cacheable GET that misses the response cache for a `host|uri` key becomes the leader; concurrent identical misses wait on its watch channel instead of dispatching, then answer from the freshly stored entry (the guard drops on every exit path, including errors and failover). Protects local backends from thundering-herd load when a hot URL expires.
- **Range requests served from cache.** Cache hits satisfy single-range `bytes=` requests at the edge (video scrubbing, resumable downloads): a `206 Partial Content` sliced from the stored full body with `Accept-Ranges`/`Content-Range`, `416` when out of range, `If-Range` honored. Multi-range and non-bytes units degrade to the full body per RFC 9110; partial requests never re-traverse the tunnel while the entry lives.
- **Unix domain socket targets.** `target: unix:///var/run/app.sock` forwards proxied HTTP requests to a local backend over a Unix domain socket (hyper HTTP/1.1 per request; matches socket-activated backends). Unix-only, validated at startup; WebSocket upgrades to a socket target answer `502`.
- **Wait-for-backend startup gate.** `wait_for_backend: true` (`APERIO_WAIT_FOR_BACKEND`, also per `services:` entry) starts the service out of routing and a 1s connect-probe loop marks it routable on the backend's first accepted connection, avoiding the connection-refused window while a slow dev server boots. Superseded by `target_health`, which already gates startup and keeps tracking health.
- **Live log tail (dashboard).** A *Live Tail* page renders each proxied request as a terminal-style monospace line, time, color-coded status, method, hostname, path, latency, error reason, off the existing SSE feed, with auto-scroll pin/unpin, a jump-to-latest button, pause, clear, and a free-text filter over host/path/method/status. Clicking a line opens the request inspector.
- **Webhook inbox.** Services opting in with `webhook_inbox: true` get every inbound POST persisted into a restart-surviving SQLite inbox (newest 500, org-isolated). A *Webhook Inbox* dashboard page browses the entries with redacted headers/payload, deletes, clears, and **re-fires** any event to whichever client currently serves the route (`GET/DELETE /aperio/api/inbox`, `.../{id}`, `.../{id}/refire`; audited `webhook_refired`), the cure for "Stripe fired while my laptop was closed".
- **Embedded API explorer.** An *API Explorer* dashboard page renders the server's own `/aperio/api/openapi.json` as a browsable reference grouped by tag, each operation expandable into a description, parameters, and an inline try-it form that runs against this server with the current dashboard session. Fully self-contained, no external Swagger assets.
- **Right-to-erasure selective purge.** `POST /aperio/api/purge` (master super-admin) deletes traffic records matching a `hostname`, token label, or visitor `ip` without wiping the whole store: the in-memory traffic log, request inspector captures, per-hostname/per-token statistics aggregates, per-route latency stage windows, the response cache, and matching `APERIO_ACCESS_LOG` lines. Responds with per-surface removal counts; audited `data_purged`.
- **Bandwidth accounting report.** Persistent statistics now bucket each token's and hostname's traffic per day and per month (standard retention, restart-surviving). `GET /aperio/api/bandwidth?unit=day|month&count=N` returns chronological buckets per label (bytes sent/received, requests) ordered by total consumption, org-scoped; a *Bandwidth* report on the Breakdown page renders both tables with a day/month toggle and sent/received tooltips.
- **Top-N slowest endpoints report.** A rolling in-memory latency window per endpoint (`host|path`, query stripped; 200 samples, 300 keys with an `__other` overflow bucket) powers `GET /aperio/api/slow-endpoints`, the top 20 by recent-window p95 (p50/p95/max/avg, request and 5xx counts, org-scoped), and a *Slowest Endpoints* table on the Breakdown page.
- **Per-route status-code trend sparklines.** A rolling per-hostname trend of one-minute status-class buckets (2xx/3xx/4xx/5xx; 60 minutes, up to 100 routes) powers `GET /aperio/api/route-trends` (last 30 minutes, org-scoped) and a *Route Trends* table on the Breakdown page rendering the buckets as sparkline bars, height by volume, color by the worst status class seen that minute.
- **Server config lint / dry-run.** `aperio-server --check-config` validates the layered configuration (the `aperio-server.yaml` file plus environment variables) and exits without starting the server, flagging unparsable numeric values that would silently fall back to defaults, unknown `lb_strategy`/`failover` values, a bad `random_subdomain` pattern, malformed `trusted_proxies`/`server_auth`, unreadable page files, invalid structured sections, and incomplete OIDC settings. Exit `0` = valid, `1` = errors.
- **Per-data-type retention policies.** `APERIO_RETENTION_CAPTURES` / `_ACCESS_LOG` / `_AUDIT` / `_STATS` (in days, unset = keep forever) bound how long each data type is held, enforced by a background pruner at startup and hourly: inspector captures and inbox entries, access-log lines (rewritten in place), audit events (rotated generations deleted whole, the active file's leading expired prefix trimmed so the hash chain stays verifiable), and day-granularity stats buckets. Each pruning cycle is audited `retention_pruned`.
- **Disk-usage guard with auto-prune at cap.** `APERIO_DB_MAX_BYTES` caps the on-disk footprint of `aperio.db` plus its WAL/SHM sidecars: at 90% a `disk_usage_warning` webhook/audit event fires once per episode (resetting below 80%), and past the cap the hourly guard sheds the lowest-priority data (oldest inbox entries, delivery-log rows, day-stat buckets), then checkpoints the WAL and vacuums so the file shrinks on disk, recording `disk_pruned`.

### Changed

- **Client `allowed_ips` is now per-candidate, with `denied:` handling (breaking).** Visitor IP allowlists change from route-wide intersection to per-candidate eligibility: during selection each candidate is filtered by its own `allowed_ips` (before the load-balancing strategy, so a passing standby can serve a visitor its primary rejects) and the request dispatches to any passing candidate, **union semantics**, deliberately fail-open (an unrestricted client joining a route opens it; route-wide lockdown belongs to the token-level IP allowlist). When every candidate rejects the visitor, the server answers with the new `denied:` redirect (yaml top-level or per-service, `APERIO_DENIED`; declared in the tunnel handshake, validated as an absolute http(s) URL) of the most-primary declaring candidate, or, with none declared, a **stealth answer identical to an unclaimed route** (`504`). **This replaces the previous `403`**, so blocked traffic no longer reveals the route's existence; resilient-cache answers are withheld for denied visitors, and failover re-picks and the WebSocket path apply the same filter.
- **The traffic log records the request hostname.** Each `RequestLog` (and the live SSE `traffic` event) now carries the request `host`, powering the live-tail view and the right-to-erasure purge's hostname selector.

- **A service can claim several hostnames.** `hostname:` in `aperio.yaml` now accepts a list (`hostname: [app.example.com, www.example.com]`) as well as a single string, and the CLI `--hostname` / `APERIO_HOSTNAME` value may be comma-separated. All declared hostnames are validated against the client's token and route to the same service. Additive on the wire (a new `hostname_binds` Ping field alongside the existing single bind), so mixed-version client/server pairs keep working.
- **Ctrl/Cmd+S saves the Settings page.** Pressing Ctrl+S (Cmd+S on macOS) on the Server Settings page saves pending overrides instead of opening the browser's save-page dialog, matching editor muscle memory.
- **Per-stage latency statistics with anomaly detection.** The timeline data feeds a rolling per-route window (last 500 requests) of per-stage durations, queueing, tunnel transit out, client processing, backend wait, backend body, transit back, serve-to-visitor. `GET /aperio/api/stage-stats` (and a new *Stage latencies* table on the Breakdown page) reports each stage's mean, standard deviation, and latest sample, flagging a stage whose latest sample sits more than 3σ above its mean (with a minimum window and floor, so quiet routes don't false-positive), "requests usually queue +5-10 ms, now +25-30 ms" becomes visible and attributable to a stage.
- **High-resolution request timelines in the inspector.** Buffered responses now carry client-side stage durations (tunnel receipt → backend request sent → first byte → body complete → response handed back, microseconds on the client's monotonic clock; additive protocol field, older peers unaffected). The server anchors them against its own measurements (arrival, dispatch, response received, visitor hand-off) by splitting the unaccounted tunnel transit evenly per direction, clocks are never mixed and the estimate is flagged. The inspector shows the result as a per-stage waterfall with µs/ms offsets from arrival.
- **Live topology view.** A new *Topology* dashboard page draws routes → tunnel clients → backends as a live map: hostname/path binds (and a catch-all node) connect to the clients that serve them, nodes are health-colored (healthy / draining or failing probes / unhealthy), and each client→backend edge carries a live requests-per-second label derived from the SSE stats stream. Pure SVG, no new dependencies.
- **Usernameless passkey sign-in (opt-in per passkey).** Registering a passkey now offers *allow signing in without a username*: the credential is created as a discoverable (resident) key, and pressing the login page's passkey button with an empty username runs a discoverable ceremony, the authenticator's account picker supplies the identity (the user handle stored at registration). Only passkeys registered with the opt-in are accepted on this path (server-enforced); all other passkeys keep the username-first flow unchanged. The passkeys dialog badges usernameless keys, and the new `/aperio/auth/passkey/discoverable/start|finish` endpoints carry the same rate-limit/lockout protections as the classic flow.
- **Active session management.** Sessions now record their sign-in IP, browser (User-Agent), and creation time. Admins get an *Active sessions* table on the Users page, the caller's own session is marked, with per-session revocation and a *Sign out everywhere else* action that ends every session except the caller's; both are audited. API: `GET /aperio/api/sessions`, `DELETE /aperio/api/sessions/{id}`, `DELETE /aperio/api/sessions` (all admin-only).
- **Secret redaction in the request inspector.** Credential-bearing headers (`Authorization` keeps its scheme, cookies keep their names, `X-Api-Key`-style headers are fully masked) and secret-looking body fields (`password`, `token`, `api_key`, `client_secret`, … in JSON, recursively, and form-urlencoded bodies) are replaced with `[REDACTED]` before a captured request leaves the server, so they never reach the dashboard, the cURL copy, or the HAR export. The raw capture stays in memory, so replay still re-sends the original request. `APERIO_INSPECTOR_REDACT=0` opts out.
- **Webhook delivery reliability and a delivery log.** Failed webhook deliveries (transport errors, 5xx, 429) are retried with backoff, 4 retries over ~1.5 minutes by default, tunable via `APERIO_WEBHOOK_RETRY_SCHEDULE` (comma-separated seconds between attempts; empty disables retries); other 4xx are permanent. Every final outcome is persisted (last 500) with status/error, attempt count, and the exact payload, shown in a new *Recent deliveries* table on the Webhooks page and served by `GET /aperio/api/webhooks/deliveries`. Any logged delivery can be redelivered (button or `POST /aperio/api/webhooks/deliveries/{id}/redeliver`): the same payload goes to the webhook's current URL with a fresh signature and normal retries, audit-logged as `webhook_redelivered`.
- **ETag synthesis and edge 304s for cached responses**: entries stored in the response cache without a backend validator get a strong, body-hash `ETag`; a request whose `If-None-Match` matches the entry's validator (backend-sent or synthesized) is answered `304 Not Modified` directly at the edge, no body, no tunnel round-trip. Cached answers also carry an `Age` header now.
- **Serve-stale-on-origin-failure (resilience)**: a service that sets `resilience: true` (CLI `--resilience`, env `APERIO_RESILIENCE`; requires `cache: true` and the server-side cache) keeps answering visitors from the server's response cache while no healthy client is connected, instead of a 504. Entries may be served past their advertised lifetime up to `APERIO_CACHE_MAX_STALE` (default 1 hour, `0` disables); stale answers carry `x-aperio-stale: true` and every cached answer now carries an `Age` header. Only entries stored by a resilience-enabled client qualify, and the moment any healthy client reconnects the normal proxy path takes over, so a newly connected client immediately controls the content again. Covered by a new e2e phase (cache hit, fail-closed for non-resilient routes, stale marker during the outage, fresh takeover after reconnect).

## [0.2.0] - 2026-07-10

### CI

- Tagged releases now also attach the `aperio.yaml` JSON Schema under the stable name **`aperio-client.schema.json`** (next to the versioned `aperio-client.<tag>.json`), so editors and schema managers can reference `releases/latest/download/aperio-client.schema.json`, a URL that always serves the latest release.

### Security

- The **visitor-auth gate now rejects path traversal** the same way share links do (0.1.3 only fixed the share-link scope check despite claiming both): a request path with a `..`/`.` segment (literal or single-percent-encoded) is never treated as public, never unlocks a client-set per-service password, and requires a full session whenever a gate could apply on the host. Previously `/public/../gated` matched a `/public` path bind, skipped the gate as "public", and a backend that resolves `..` served the gated sibling path.
- `CF-Connecting-IP` is **no longer trusted automatically** for client IP resolution (introduced in 0.1.3): any visitor can send that header and a non-Cloudflare proxy passes it through untouched, so on deployments not behind Cloudflare it let clients spoof their IP for rate limiting, audit/access logs, and dynamic-token IP allowlists. Behind Cloudflare, set the new `APERIO_TRUST_CF_HEADER=1` (shorthand for `APERIO_REAL_IP_HEADER=CF-Connecting-IP`); the rewritten-`X-Forwarded-For` diagnostic warning still fires when that header is configured.
- Revoking a dynamic token now **immediately drops any tunnel connections currently using it**, instead of letting them keep serving traffic until they next reconnected (when they would be rejected anyway). The disconnected client leaves the routing pool at once, and its reconnect attempts are refused with the usual 401. Deleting an **ephemeral tunnel** (`DELETE /aperio/api/tunnels/:id`) now drops its live connection the same way, it revokes through the same token store but previously left the tunnel serving until its client reconnected.

### Added

- **Tamper-evident audit log**: every `audit.jsonl` line now carries a `prev` field, the SHA-256 of the previous line exactly as written, forming a hash chain that spans restarts and file rotations (the first line of a rotated file links to the last line of the previous generation). Editing, deleting, or reordering a line breaks every hash after it, so tampering is detectable; the chain is verified at startup and a warning is logged if it is broken. Old pre-chain lines remain valid and new events chain onto them.
- **Token/hostname-labelled Prometheus counters**: `/aperio/metrics` now also exposes `aperio_token_{requests,requests_failed,bytes_received,bytes_sent}_total{token=...}` and the same family with a `hostname` label, backed by the restart-surviving persistent stats store, enough to build per-tenant quota and billing dashboards next to the existing latency histogram. At most 200 distinct labels per family are tracked (overflow folds into `__other`), so a flood of random hostnames cannot blow up scrape size.
- **Shutdown notification to clients**: on SIGINT/SIGTERM the server now broadcasts a `ServerShutdown` protocol message to every connected tunnel client before dropping the sockets. A client that receives it skips the exponential reconnect backoff once the connection drops and retries after a single 100-500 ms jittered delay, so a server restart is barely visible instead of costing clients up to a full backoff cycle. Older clients ignore the unknown message and reconnect on their normal schedule.
- **Richer `aperio-client check` diagnostics**: the token check now reports the WebSocket handshake round-trip time; declared raw-TCP services (`tcp_target` and every `tunnels:` entry) are probed with a plain TCP connect, which previously were not checked at all; and visitor-auth overrides (top-level and per-service `auth:`) are validated to be a non-empty `user:password` pair instead of failing silently at login time.
- **Client-side header rules**: a `headers:` config section (top-level or per `services:` entry) adds/removes headers on proxied HTTP traffic, `request` rules edit what the local backend receives, `response` rules edit what the visitor receives. `add` replaces an existing header of the same name, `remove` strips case-insensitively; hop-by-hop and tunnel-critical headers remain managed by Aperio regardless. Included in the generated `aperio.yaml` JSON Schema and applied on config hot-reload. See [docs/configuration.md](docs/configuration.md).
- **UDP emergency tunnels**: a `tunnels:` entry may now declare `protocol: udp`; `--bind-tunnels` then exposes it as a local UDP socket, with each distinct local peer getting its own relay stream (new `/aperio/udp` endpoint + `UdpOpen`/`UdpDatagram`/`UdpClose` protocol messages) so responses reach the right peer, enough for DNS, statsd, or a WireGuard handshake in an emergency. Deliberately best-effort, matching UDP semantics: congested hops drop datagrams instead of queueing, idle relays expire after 60 s, and the declaring client only ever sends to targets it itself declared (same SSRF guard and same-token rule as TCP). Streams are audited as `udp_stream_opened`.
- **Parallel tunnel connections per service** (`connections: N`, 1-16, per `services:` entry / top level / `APERIO_CONNECTIONS`): the client opens N tunnel connections for the same service and the server load-balances across them like separate clients, so one busy service is no longer serialized behind a single WebSocket. Each connection derives its own instance id (`<id>`, `<id>-c2`, …), the dashboard's shared-id warning is not triggered and failover/`--bind-tunnels` lookups stay unambiguous. `max_concurrent` applies per connection.
- **Server-side response cache** (`APERIO_CACHE=1` on the server + `cache: true` on the client): repeated GETs to an opted-in service are answered from server memory instead of a tunnel round-trip. Strictly `Cache-Control`-driven, only responses that explicitly allow shared caching (`max-age`/`s-maxage`, no `no-store`/`no-cache`/`private`, no `Vary`/`Set-Cookie`) are stored, for exactly the advertised lifetime, and only credential-less plain GETs (no `Authorization`/`Cookie`, no `no-cache` request directive) are served from it. Total memory is bounded by `APERIO_CACHE_MAX_BYTES` (default 64 MB) with closest-to-expiry eviction; hits carry an `x-aperio-cache: hit` header and count in stats/metrics under the serving token and hostname.
- **End-to-end encrypted emergency tunnels** (`encrypt: true` on a TCP `tunnels:` entry): the binding and declaring clients run an ephemeral X25519 key exchange in-band and seal every relayed frame with ChaCha20-Poly1305, so the aperio server (or any relay) only ever carries ciphertext. An optional pre-shared key (`psk`, configured on both sides and never transmitted, it is stripped from the tunnel announcement) is mixed into the HKDF key derivation, making even an actively MITM-ing server fail closed at the first frame. Tampering, reordering, and replay also fail closed (per-direction counter nonces). New client dependencies: `x25519-dalek`, `chacha20poly1305`, `hkdf`.
- **OpenAPI specification for the admin API** (`GET /aperio/api/openapi.json`, behind the dashboard session): an OpenAPI 3.1 document generated from `utoipa` annotations on all ~28 admin/auth handlers, statistics, traffic inspection, dynamic tokens (including refresh), ephemeral tunnels, webhooks, audit, maintenance, share links, settings, login/logout/session, health, and metrics, with request/response schemas for the typed payloads. Point Swagger UI, Bruno, or a client generator at it.
- **Token refresh endpoint** (`POST /aperio/api/tokens/refresh`): a dynamic token created with a TTL can slide its own expiry forward by presenting its secret as a Bearer token, no dashboard session needed, so CI jobs and long-running clients can be given genuinely short-lived tokens that stay valid only while actively refreshed. Never-expiring tokens are not refreshable, an expired token cannot resurrect itself, the endpoint is rate-limited per IP, and each refresh writes a `token_refreshed` audit event.
- **Signed webhook deliveries**: a webhook can be created with an HMAC signing secret (16-128 chars); every delivery then carries `X-Aperio-Timestamp` and `X-Aperio-Signature: sha256=<hex HMAC-SHA256 over "timestamp.body">` so the receiver can verify both origin and freshness (replay window). The secret is write-only, the list API and dashboard only show a *signed* badge. See the verification snippet in [docs/observability.md](docs/observability.md).
- **Login brute-force lockout**: after `APERIO_LOGIN_LOCKOUT_THRESHOLD` (default 5) consecutive failed logins, the source IP is refused outright for `APERIO_LOGIN_LOCKOUT_SECS` (default 60 s), doubling with each repeat lockout up to one hour. The existing rate limit only slowed guessing down; the lockout stops it. Triggering a lockout writes a `login_lockout` audit event; a successful login clears the state.
- **`APERIO_TRUSTED_PROXIES`**, a comma-separated list of reverse-proxy / CDN egress IPs and CIDRs. When set, the real client IP is resolved by walking the `X-Forwarded-For` chain (plus the direct socket peer) from the nearest hop backwards past trusted addresses and taking the first untrusted one, the standard trusted-proxy model (nginx `real_ip`, Express `trust proxy`) that works for **any** CDN or proxy chain, not just Cloudflare. Forwarding headers from an untrusted direct peer are ignored entirely, so nothing is spoofable from outside the chain. Implies `APERIO_TRUST_PROXY`. `APERIO_REAL_IP_HEADER` (and the `APERIO_TRUST_CF_HEADER` shorthand) still work for proxies that rewrite XFF instead of appending, and now also require the direct peer to be trusted when `APERIO_TRUSTED_PROXIES` is set. Invalid entries refuse startup instead of silently shrinking the trusted set.

### Changed

- **Tokens, webhooks, and persistent stats now live in a single SQLite database** (`APERIO_DATA_DIR/aperio.db`, WAL mode) instead of three JSON files. Writes are transactional, so a crash can never leave a half-written store; a file that turns out not to be a valid database is backed up as `aperio.db.corrupt.<epoch>` and a fresh one is created. There is **no migration from the old JSON files**, existing `tokens.json`/`webhooks.json`/`stats.json` are ignored (recreate tokens and webhooks from the dashboard). The audit log stays as the hash-chained `audit.jsonl`.
- The dashboard's **stats/overview now stream over the same SSE connection as the traffic table** instead of polling `/api/stats` every 2 seconds: `/aperio/api/stream` emits named `stats` events (the connections list + counters, pushed every 2s and once on connect) alongside `traffic` events. Only the session-lifetime check is still polled (once a minute); the REST `/api/stats` and `/api/logs` endpoints remain as the seed and the polling fallback used when the stream can't be established.
- A tunnel connection rejected by the server for a bad/expired/revoked token now logs an explicit **authentication failure** (with the HTTP 401/403 status and where to check the token) instead of dumping the raw HTTP response struct, so the cause is obvious in the client logs.
- The generated `aperio.yaml` JSON Schema now carries purpose-oriented one-line field descriptions and `examples` for format-sensitive values (server URL/token, `target`, `hostname`/`path`, `bandwidth`, `auth`, tunnel targets, `client_id`, …), so editors surface a concrete sample and the meaning of each key while editing.

## [0.1.3] - 2026-07-09

### Security

- Dynamic API tokens are now verified with a constant-time hash comparison instead of `==`. Comparing SHA-256 hashes (not the raw secret) was already low risk, but this keeps the token path consistent with the constant-time master-token check and forecloses a future timing regression.
- The dashboard and login pages are now served with security headers: `Content-Security-Policy` (`default-src 'self'` with `data:` images/fonts and inline styles for Radix, no inline scripts), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and `Referrer-Policy: no-referrer`. Only the embedded dashboard/login responses are affected, proxied sites keep their backend's own headers. HSTS is intentionally left to the TLS-terminating proxy so a plain-HTTP self-hosted setup is not locked to HTTPS.
- Share links (and path-bind scope checks) no longer trust a request path containing `..`/`.` traversal segments. Because hyper/axum never normalize the request path, a share link scoped to `/public` previously matched `/public/../admin` (which starts with `/public/`) and, on a backend that resolves `..`, could reach sibling paths. The path is now checked for literal and single-percent-encoded traversal (`%2e%2e`, `..%2f`) before a share claim is considered to cover it; such requests fall back to the normal login gate.

### Added

- **JSON Schema for `aperio.yaml`**: building `aperio-client` now emits `schemas/aperio-client.schema.json` (git-ignored build artifact) via a build script, derived from the shared new `aperio-config` crate so the schema always tracks the parser. Point an editor's `yaml.schemas` (VS Code, Antigravity, …) at it for completion/validation while editing `aperio.yaml`. The release workflow attaches a versioned `aperio-client.<tag>.json` to each tagged release. Also runnable by hand via `cargo run -p aperio-config`.
- **Client-set visitor password (per service)**: a client can gate its own service behind a login it controls, `--visitor-auth user:password`, env `APERIO_VISITOR_AUTH`, or per `services:` entry `auth: user:password`. The server shows its normal login form for that service and accepts only these credentials, whether or not `APERIO_SERVER_AUTH` is set; the client override supersedes the server's own visitor password for that service (only the client's credentials work there, plus the always-valid `aperio:<master token>` and the dashboard password). Gated by the existing *may publish public services* token permission (master always may); all clients serving a route must declare the same value (mirroring `public`). A successful client-credentials login yields a session **scoped to that hostname only**, it never unlocks the dashboard or another host (server/dashboard/master/OIDC logins stay global). The server operator can disable the whole feature with `APERIO_IGNORE_CLIENT_AUTH=1`. The dashboard clients table shows a *custom auth* badge (the credentials themselves are never exposed).
- **Live traffic streaming**: the dashboard traffic table now updates in real time over Server-Sent Events (`GET /aperio/api/stream`) instead of polling `/api/logs` on a timer, each proxied request is broadcast and rendered the moment it completes. The stream sits behind the dashboard session auth, uses a bounded broadcast buffer (a slow subscriber skips lagged entries rather than applying backpressure to request handling), and the client transparently falls back to polling if the stream can't be established. The pause/resume toggle and filters are unaffected.
- **OpenTelemetry trace export**: setting `APERIO_OTEL=1` exports one OTLP span (`proxy.request`) per proxied request over HTTP/protobuf to a collector (`APERIO_OTEL_ENDPOINT`, default `http://localhost:4318`; `APERIO_OTEL_SERVICE_NAME`, default `aperio-server`; the standard `OTEL_EXPORTER_OTLP_ENDPOINT`/`OTEL_SERVICE_NAME` are honored as fallbacks). Each span carries the method, path, host, selected `aperio.client.id` and response status. An inbound W3C `traceparent` is adopted as the span's parent, and the span's own context is injected into the headers forwarded through the tunnel, so visitor → server → backend appears as one distributed trace. Off by default with zero overhead (inbound trace headers pass through untouched). Note: enabling it compiles `aws-lc-sys`/rustls, which needs a C toolchain + CMake at build time.
- Unit tests for previously unit-untested pure logic: the routing pipeline (path/hostname bind normalization and matching, random-subdomain patterns, request-host and client-IP extraction, pool selection, LB strategy and sticky affinity), the `ClientPerms`/`ClientHandle` routing accessors, the auth helpers (token extraction, IP/CIDR allowlists, constant-time compare, safe-redirect), and the settings parsers (`parse_lb_strategy`, `parse_failover_mode`, `override_keys`, `apply_settings_overrides`). 41 new tests; no behavior change.
- E2E phases for previously thinly-covered dashboard handlers: the token API lifecycle (list, edit scope/limits/expiry/public-flag, invalid-permission and unknown-id rejections, revoke + double-revoke), the client control API (overrule validation and clearing, the enable/disable kill switch removing a client from the routing pool and restoring it), and the `aperio-client check` failure path against an unreachable server/target. No behavior change.
- Refresh button on the dashboard audit log section.
- Dashboard command menu (`⌘K` / `Ctrl+K`) for quick page navigation and theme switching, openable from a header button.
- Dashboard light/dark theme toggle: the appearance is persisted and defaults to the operating-system preference; the sticky header, background and heading now adapt to the active theme.
- Dashboard traffic table filters, clickable method (GET/POST/…) and status-class (2xx/3xx/4xx/5xx+error) chips on top of the existing text filter, with a one-click clear.
- Toast notifications confirming dashboard mutations (client enable/disable and overrule, token create/edit/revoke, webhook add/delete, maintenance on/off).
- Loading skeletons on the stat cards and every dashboard table, and richer empty-state rows (icon + hint) instead of a bare line of text.
- Dashboard sign-out: a "Sign out" control in the header with a session-expiry tooltip, backed by new `POST /aperio/auth/logout` (drops the server-side session and expires the cookie) and `GET /aperio/api/session` (remaining session lifetime) endpoints.
- "Copy as cURL" in the request inspector, reconstructing an equivalent `curl` command (URL from the captured Host header, request headers, and a decodable non-truncated body) for the captured transaction.
- Latency percentiles (p50/p95/p99) and a status-class mix bar computed over the recent request window on the dashboard Traffic page.
- Client table search (by id, ip, service, token, hostname/path bind), sortable Last-Ping/Connected-For/Requests columns, and bulk enable/disable of the currently listed clients.
- A pause/resume ("Live") toggle on the traffic table that freezes the view while inspecting.

### Changed

- **Docker images are now published on release, not on every push.** The multi-arch `ghcr.io/.../aperio-server` and `aperio-client` images are built by the release workflow when a version tag is pushed, and tagged with that version (`v0.2.0`, `0.2.0`, `0.2`, `0`); `latest` tracks the most recent **stable** release (a pre-release tag like `v1.0.0-rc1` only publishes its exact tag and never moves `latest`). The CI workflow (`ci.yml`) on `main`/`master` and PRs now runs only build/lint/test, coverage, dependency audit, and the e2e tunnel test, it no longer builds or pushes Docker images (so `latest` no longer follows the default branch).
- Dashboard state is now URL-addressable: the active tab and the traffic filters (text, method, status class) live in the query string, so a reload or shared link restores the same view and the browser back button steps between tabs. When a poll keeps failing the dashboard backs off exponentially (up to 16× the base interval) instead of hammering a down server, and the browser tab title and favicon reflect the connection state (green/amber/red) so a backgrounded tab shows tunnel health at a glance.
- Dashboard accessibility: the status-dot pulse and toast slide-ins are disabled under `prefers-reduced-motion`, and toasts are announced to screen readers via an `aria-live` region.

- Dashboard polling now pauses while the browser tab is hidden and refreshes immediately when it becomes visible again, instead of fetching every endpoint on a timer in the background. When a poll fails the dashboard keeps the last good data but surfaces a banner ("data isn't updating, values may be stale", or "cannot reach the server" on a cold start) rather than silently showing stale numbers.
- Dashboard traffic and audit timestamps render as relative time ("12s ago") with the absolute timestamp on hover; the traffic table renders at most the latest 200 matching requests (with a "showing the latest 200 of N" note) so a busy tunnel no longer paints thousands of rows each poll; and the live request-activity sparkline is persisted across a page reload.

- Client IP resolution now consults `CF-Connecting-IP` automatically (under `trust_proxy`, after any explicit `APERIO_REAL_IP_HEADER`): behind Cloudflare an intermediate proxy such as Traefik often rewrites `X-Forwarded-For` down to the Cloudflare edge address, so audit entries, rate limiting and access logs recorded the edge IP instead of the real visitor. An explicit `APERIO_REAL_IP_HEADER` still wins, so pointing at another header (e.g. `True-Client-IP`) keeps overriding the automatic behavior. When the Cloudflare header is used *and* `X-Forwarded-For` starts with a different address (the tell-tale of an intermediate proxy that does not trust/preserve forwarded headers), the server logs a one-time warning pointing the operator at the actual fix rather than silently masking the misconfiguration.
- The dashboard clients table now shows a client's pinned instance id (`--client-id`) as its primary identifier when set, falling back to the per-connection id; the id tooltip lists both the client id and the connection id.

### Fixed

- The client-id cell tooltip in the dashboard clients table no longer misrenders/overflows: it wrapped the whole cell (including the nested status badges, each with their own tooltip), so hovering produced a broken oversized overlay. The tooltip now wraps only the id text.
- The dynamic-token and webhook JSON stores are now written atomically (temp file + fsync + rename) instead of a truncating in-place write, so a crash mid-write can no longer corrupt them. A store file that fails to parse on load is renamed aside as `<name>.corrupt.<epoch>` and preserved for recovery instead of being silently discarded (and then overwritten with an empty store on the next write).

## [0.1.2] - 2026-07-07

### Added

- **Public services**: a client can declare its service public (`--public`, yaml `public: true`, `APERIO_PUBLIC=1`) and the server skips its visitor password / OIDC gate for routes served exclusively by that client. Gated by a new per-token *may publish public services* permission (off by default; master token always may) and shown as badges in the dashboard.
- The client prints human-readable logs on interactive terminals and keeps JSON when stdout is not a TTY (Docker, pipes); `APERIO_LOG_FORMAT=json|pretty` overrides the auto-detection.
- Global `--target` client flag as an alternative to the positional target, usable with subcommands too, `aperio-client check --target 3000` now works instead of erroring with "unexpected argument".
- **Emergency tunnels**: a client declares normally unexposed local TCP services in a `tunnels:` list (a config with only tunnels is valid); a peer client running `aperio-client --bind-tunnels <client-id>` with the **same token** binds them as local 127.0.0.1 listeners (port = declared target's port, overridable per target via a `bind-tunnels:` yaml section that also supports multiple clients). Port conflicts and already-taken local ports are reported instead of bound. The declaring client only ever dials addresses from its own list; even master-token holders must name an explicit client id. Discovery endpoint: `GET /aperio/tunnels/:client_id`.
- `--client-id` client flag (yaml `client_id`, env `APERIO_CLIENT_ID`) pins the client instance id to a fixed UUID across restarts, useful for failover `wait` mode and `--bind-tunnels`. Invalid (non-UUID) values are rejected at startup. Duplicate ids are allowed but flagged: the dashboard clients table shows a `SHARED ID` badge when two live connections report the same instance id (lookups by that id are ambiguous).
- Test coverage measurement via `cargo-llvm-cov`: a CI `coverage` job merges the unit tests AND the E2E integration run into one report (the instrumented server/client binaries flush profile data on their graceful SIGTERM exit), puts the per-file summary into the job summary, and uploads the HTML/lcov report as a `coverage-report` artifact (reported, not gated).
- E2E phases for the previously untested runtime paths: WebSocket pass-through (upgrade, frame echo, clean close), emergency tunnels (discovery endpoint incl. the same-token 403 rule, `--bind-tunnels` with a port override, byte relay) and the legacy tcp bridge, plus metrics, request inspector & replay, webhooks API and audit API steps in the base phase. New unit test files for bind-tunnels resolution, the same-token rule, and the tunnel wire protocol (binary frames, compression bounds, serde backward compatibility).

### Fixed

- TCP tunnel streams no longer drop the consumer's first bytes: the stream was registered inside a spawned task (after the backend connect), so a `TcpData` frame arriving right behind `TcpOpen` could be discarded silently and the connection appeared to hang. Registration now happens synchronously in the tunnel read loop, with the channel buffering bytes until the backend connect completes (found by the new e2e phase; affected the legacy bridge and emergency tunnels alike).
- The `tcp` bridge and `--bind-tunnels` modes exit cleanly on SIGINT/SIGTERM instead of relying on the default signal handling.

### Changed

- The experimental TCP tunneling feature (`tcp_target`, `aperio-client tcp <port>`, bare `GET /aperio/tcp`) is no longer documented and the `tcp` subcommand is hidden from `--help`; the API keeps working for existing setups. Emergency tunnels are the supported path for raw TCP access.
- **Documentation restructure**: the README is now a short overview (intro, quick start, docs index) at ~110 lines instead of ~650. All reference material moved into `docs/`: the new [Configuration Reference](docs/configuration.md) holds the env/CLI/yaml naming standard, precedence layers, the full client and server settings tables, and the HTTP endpoint list; the new [Development & Releases](docs/development.md) holds building from source, tests & coverage, the release process, and project conventions. Examples (`.env.example`, `docker-compose.yml.example`, docs) now use the canonical `APERIO_TARGET`/`APERIO_PATH`/... names instead of the legacy `APERIO_CLIENT_*` aliases.

### Security

- Bumped the transitive `quinn-proto` dependency to 0.11.16, resolving RUSTSEC-2026-0037 and RUSTSEC-2026-0185 (two high-severity denial-of-service advisories).

## [0.1.1] - 2026-07-07

### Added

- **Multi-service client**: a `services:` list in `aperio.yaml` exposes several targets from one client process, one tunnel connection per entry, each with its own binds, health probe, and tuning knobs. Service names show in client logs and as a badge in the dashboard clients table.
- **Per-token limits**: dynamic tokens accept an optional rate limit (`max_rps`, token bucket) and a daily traffic quota (`daily_max_bytes`); exceeded limits answer `429`. Editable live from the dashboard and the token API.
- **User-level config**: `~/.aperio.yaml` is read as the lowest-precedence layer, keep your shared `server.url`/`server.token` there once.
- **Redirect following**: the client transparently follows same-site backend redirects (`http://x` → `https://x`, hops within the same root domain) up to `max_redirects` jumps (default 5, `0` = old pass-through behavior). Https-to-http downgrades and unrelated hosts still pass through.
- **Random subdomain patterns**: `APERIO_RANDOM_SUBDOMAIN` accepts `example.com` (≡ `*.example.com`) and same-level patterns like `*-test.example.com`, generating `<random>-test.example.com` under the parent wildcard TLS certificate.
- `aperio_request_duration_seconds` Prometheus histogram (5 ms - 30 s buckets) for p95/p99 latency dashboards.
- Size-based audit log rotation (`APERIO_AUDIT_MAX_SIZE`, default 10 MB; `APERIO_AUDIT_MAX_FILES`, default 3).
- `aperio-client check` reports which configuration layer supplied each value and probes every `services:` entry.
- Optional `service` field in the tunnel `Ping` message (backward compatible).
- CI job auditing the dependency tree against the RustSec advisory database (`cargo audit`).

### Changed

- **BREAKING (CLI)**: `aperio-client http <port>` and `run` subcommands are gone, use a positional target (`aperio-client 3000`, `aperio-client example.com`) or plain `aperio-client` with config/env. `tcp` and `check` remain. Old option spellings (`--server`, `--token`, `--host`, `--concurrency`) still work as aliases of the canonical `--server-url`, `--server-token`, `--hostname`, `--max-concurrent`.
- **Configuration layering** is now `CLI > ./aperio.yaml > environment > ~/.aperio.yaml` (the local file previously ranked below the environment).
- Naming is mechanical across surfaces: yaml `server.url`/`server.token` (legacy flat `server:`/`token:` still accepted), env `APERIO_TARGET`, `APERIO_HOSTNAME`, `APERIO_TIMEOUT`, … (legacy `APERIO_CLIENT_*`, `APERIO_HOSTNAME_BIND`, `APERIO_PATH_BIND` remain as aliases).
- Config hot-reload restarts the service(s) with the fully re-resolved configuration, every setting applies now, not just token/server/target/binds/priority.
- Dashboard settings apply to connected clients immediately: changing the random-subdomain pattern re-issues client hostnames on the spot; enabling tunnel compression is offered to connected clients right away.
- CLI parsing moved to clap (proper `--help`, errors, completions groundwork).
- Both crates reorganized into folder-based module hierarchies (`store/`, `api/`, `proxy/`, `tunnel/` on the server; `proxy/` on the client).

### Fixed

- Ephemeral tunnel deletion now emits the `tunnel_deleted` webhook event (was `token_revoked`).
- `client_connected`/`client_disconnected` audit entries and webhooks record the resolved client IP (trust-proxy aware) instead of the raw socket address with port.
- `*-test.example.com` random-subdomain patterns no longer produce the broken `<random>.*-test.example.com` form.
