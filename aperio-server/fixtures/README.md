# Stored-format fixtures

Artifacts written by a previous build and read by the current one. They exist
because every other test in this crate creates what it reads in the same
process, which proves the code agrees with itself and nothing about the data
already sitting on somebody's server.

This is not hypothetical. `#133` moved `rusqlite` from 0.32 to 0.40, carrying
the bundled SQLite from 3.46 to 3.53 under the store, and the whole suite
passed without touching a database that existed beforehand. It was checked by
hand instead, and would have had to be checked by hand again.

| File | Written by | What breaking it looks like |
|---|---|---|
| `store-written-by-0.10.0.db` | SQLite 3.46 via `rusqlite` 0.32 | A store upgrade that cannot open an existing data directory. |
| `password-argon2-0.5.3.phc` | `argon2` 0.5.3 | Every dashboard user is locked out after an upgrade. |
| `passkey-webauthn-rs-0.5.5.json` | `webauthn-rs` 0.5.5 | Every registered passkey stops being loadable. |

The last two are the upgrades `#134` is waiting on. They were captured *before*
that work rather than after, which is the only order that helps: a fixture
generated by the new version proves the new version agrees with itself.

## The known limitation

A fixture is frozen at the version that wrote it, so this set ages. It answers
"can today's code read what 0.10.0 wrote", not "can it read what any supported
version wrote". That is deliberate: the alternative, building an old release
from a git tag inside the test, is slow enough that it would be skipped.

Add a new file rather than regenerating an old one when a format changes on
purpose. A regenerated fixture is a test that cannot fail. If an entry here has
to be replaced because the old format is genuinely no longer supported, that is
a `CONFIG_CHANGES`-shaped decision and belongs in `CHANGELOG.md` too.

The password for `password-argon2-0.5.3.phc` is `password123`, matching the
dashboard test user. It is a fixture, not a credential.
