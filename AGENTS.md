# Project Rules

These rules apply to all future work in this repository.

## Git & Commits
1. **Never push.** Do not run `git push` under any circumstances.
2. **Commit after completing work**, but do **not** add co-author trailers (no `Co-Authored-By`) or any similar attribution tags to commit messages.
3. **Git Flow:** start every requested change on a `feature/<slug>` branch and keep its commits there, never commit directly to `master`. `ci.yml` must run on pushes to `feature/**` and on pull requests to the protected branches. Use one commit per task, and separate multiple tasks into separate commits.

## Verification
4. Do **not** run preview-style checks. Prioritize the project's existing checks instead: `build`, `clippy`, `fmt`, and the `e2e` tests.
8. **Run the `e2e` suite only once, at the very end, after all requested work is done**, not after each individual task. The e2e run is slow; during development rely on `build`, `clippy`, `fmt`, and unit tests, then run `npm --prefix tests/e2e test` a single time before finishing. (New e2e phases/assertions may still be *written* per task; just don't *execute* the suite until the end.)

13. **Run the full test suite locally before finishing, CI is expensive.** GitHub Actions minutes cost real money; never lean on CI to catch a failure we could have caught locally. Before finishing any task, run the **complete** unit/integration suite with `cargo test --workspace`, **not** a filtered subset (`cargo test dial::` passing tells you nothing about the rest of the crate). This is what would have caught the flaky `service::tests::test_run_service_message_loop`. For timing-sensitive or flaky tests, run the affected test several times (a loop) to confirm stability, not just once. This is in addition to the single end-of-work `e2e` run (rule 8).
14. **UI-only changes skip the `e2e` run.** When every change in a task is confined to the dashboard frontend (`aperio-dashboard/`: `.ts`/`.tsx`/CSS/i18n) with **no** Rust (`aperio-server`/`aperio-client`/`aperio-config`), protocol, or config change, do **not** run `npm --prefix tests/e2e test`, the e2e suite exercises the Rust tunnel/HTTP path a UI-only change cannot affect, so it adds no coverage. Verify with the frontend's own checks instead: `tsc -b`, `oxlint`, `vitest run`, `vite build`, and `check-i18n`. (Rules 8 and 13 still apply the moment a task touches any Rust.)

21. **Never run a benchmark or a load test without asking first.** This machine runs other work; a number measured while something else is compiling or serving is not a number, and the load itself takes the machine away from its owner. That includes `wrk`, `ab`, `criterion`/`cargo bench`, any loop that hammers a local server, and any long release build started only to time it. Ask, name what you want to run and roughly how long it takes, and wait for a yes. When the answer is no, or when nobody is there to ask, reason from the code and say plainly that the claim is unmeasured rather than measuring it anyway. Correctness checks that happen to take a while (`cargo test`, `npm --prefix tests/e2e test`, one release build to verify it compiles) are not benchmarks and need no permission.

22. **Rust unit tests live in a sibling `<file>_tests.rs`, never inline.** A module's tests go in a file next to it, wired in with the three lines at the bottom of the module:
    ```rust
    #[cfg(test)]
    #[path = "cache_tests.rs"]
    mod tests;
    ```
    The test file opens with a `//!` doc comment saying what about this module the tests are pinning down, and starts with `use super::*;`, everything private to the module is still reachable, so nothing has to be made `pub` for a test. This is not cosmetic: a module and its tests grow at different rates, and an inline `mod tests` puts a thousand lines of test between the reader and the end of the file it belongs to. It also keeps `<file>.rs` honest about its own length. Applies to every crate; `#[cfg(test)]` helpers that the production code itself uses (a constructor, a fixture) stay in place, only the `mod tests` block moves.

25. **A check that guards two languages belongs on the side whose change breaks it.** Several tests here read across the Rust/TypeScript boundary: the dashboard's explain catalogue against `api/explain.rs`, the audit-event filter against the Rust event names, the config form's schema snapshot against `aperio-config`. Each of those is broken by an edit on one particular side, and it must be asserted from *that* side, because that is the side whose suite the edit actually runs. A check that lives on the far side is a check nobody runs: rule 14 lets a UI-only change skip `e2e`, and there is no rule at all in the other direction, so a Rust change gets `cargo test`, `clippy` and `e2e` and never `vitest`. That is exactly how the explain catalogue stayed red across five commits with every gate green, and how the form's schema snapshot answered for a two-week-old schema.
    - **Both sides is fine and usually right**, because they catch different mistakes: from Rust, "something was added here with no entry there"; from TypeScript, "there is an entry for something no longer sent". Neither is redundant. Having only the far one is.
    - **A generated file checked into the repo is the same trap.** If a script has to be re-run by hand after a change, assume it will not be; assert the file is current from the crate that invalidates it.

26. **A release runs these first, and they are not optional.** Rule 11 says what to *edit* for a version bump. This is what to *run* before it, in this order, because each has been skipped once and cost something:

    1. **`cargo test --workspace`, `cargo clippy --workspace --all-targets`, `cargo fmt --all --check`, and one `npm --prefix tests/e2e test`.** The ordinary gates, and rule 13 already asks for the full suite rather than a filtered one.
    2. **`cargo audit`.** An advisory published the day before a release is still an advisory in the release. `RUSTSEC-2026-0258` was found by CI after 0.11.0 was cut, not before.
    3. **Fresh screenshots: `npm run capture:docs` in `aperio-dashboard/`.** The images in `README.md`, the docs pages and the guide are captured from a live instance, and a release ships them. They go stale silently, which is the whole problem: an old screenshot looks exactly like a current one. This is also the check that the dashboard *works* end to end, which is how the closed-by-default flip was found to have broken the capture script.
    4. **The mutation sweep, on Actions, triggered by hand.** It is a job of the Chore workflow (`chore.yml`), which is `workflow_dispatch` only, so it never runs on a push; before a release, start that workflow from its Run button with mutants ticked and read the survivors it lists. The same workflow carries the post-release compatibility report, off by default: tick that one after the release is published, not before, since it reports on downloaded release binaries. **Do not run it locally.** It is the slowest job here, sharded across thirty-two runners, and far longer on one machine, and it is the job that fills a disk: over the scoped set in `.cargo/mutants.toml` it grew `target/` past 28 GB and left this machine with 3 GB, which is the same wall a release run hit earlier. A runner has a clean disk per shard, which is the whole reason it belongs there.
    5. **Autobahn, locally** (`node tests/conformance/autobahn.mjs`), which needs Docker and is therefore not a CI job. h2spec still runs in CI and needs nothing.
    6. **A rehearsal of the Release workflow itself, on Actions, from its Run button with the tag about to be cut.** `release.yml` takes a `workflow_dispatch` with a `tag` input and then does everything a release does except publish: builds, packages, typesets the guide against that tag, checksums and signs, and uploads the result as a `release-rehearsal-<tag>` artifact. The guide and the .deb/.rpm packaging run nowhere else, which is how both sat broken on master for weeks with every gate green until 0.10.0 tried to ship them. Tag only after the rehearsal is green; a tag is the one run that cannot be retried under the same name.

    **Report each one's result, including the boring ones.** A release note that says "tests pass" and nothing about screenshots is indistinguishable from one where the screenshots were never taken.

27. **Run the gates exactly as CI runs them, on the toolchain CI uses.** Rule 4 says to prefer the project's own checks; this says to spell them the way `ci.yml` spells them, because a weaker spelling is a check that passes locally and fails on push. The three that matter are `cargo fmt --all --check`, **`cargo clippy --all-targets --all-features -- -D warnings`** and `cargo test --all`. Two differences are easy to miss and both have cost a red build: `--all-features` compiles code that a default-feature run never sees, and `-D warnings` turns a warning into a failure, so *counting* warnings and finding none is not the same check.
    - **The toolchain drifts even when the code does not.** CI installs stable, so a clippy release adds or tightens a lint and a commit that changed only a markdown file goes red. That is what `result_large_err` did here. Before concluding anything about a clippy failure, compare `cargo clippy --version` against the version in the CI log's help URL, and `rustup update stable` if they differ, otherwise you are debugging a lint your compiler does not have.
    - **A lint that is wrong for the code is allowed where it fires, with the reason written next to it**, not switched off across the workspace. A workspace-wide `allow` also disarms it for the code that has not been written yet.

## Code structure
24. **Rust files should stay under a thousand lines, test files excepted.** This is a guideline against code smell, not a hard limit: nothing fails because a file is 1050 lines. What it is really asking is that responsibilities be spread out, that a big single file be preferred as several small ones, and that the structure nest, a module beside its `mod/` directory beside that directory's own modules, so somebody opening the project can find where a thing is without reading. Follow Rust idiom while doing it: a `foo.rs` next to a `foo/`, `pub(crate) use` facades so a split is a pure move with no call-site churn, and names that say what the module is for rather than what it was cut out of.

    - **A file over the line is worth *asking* the question of, not automatically splitting.** The criterion was never the number, it is how many distinct subjects the file holds. A file that is one subject stays whole at 1200 lines; a file that is four subjects should have been four files at 600.
    - **Skip a file that is close to the line, or where splitting would damage the structure.** Moving twenty lines to buy a number is churn.
    - **When the objection is "too much state crosses any cut", count it before believing it.** The count is how many values bound outside a candidate cut are read inside it. Strip comments and strings, and exclude struct-literal keys, field accesses and shadowed inner bindings. A high count often points to a missing type rather than an unsplittable function.
    - **Verify a split is a pure move by diffing the test-NAME set, not the count.** `cargo test -- --list`, sorted, before and after. A hand-picked line boundary silently ate a `#[test]` attribute four times in one sweep and the suite stayed green each time, because the count of remaining tests is not what you are checking.

## Configuration surfaces
15. **Every setting must be reachable from yaml. No exceptions.** A setting that exists only as an environment variable is a bug, not a design choice: yaml is the primary surface, it is what the JSON Schemas describe, what editors complete, and what an operator reads to understand a deployment. When adding a setting, add its yaml key in the same change, a field on `FileConfig`/`ServiceEntry` in `aperio-config` for the client, a documented field on `ServerFileConfig` for the server (the server materializes scalar keys into env vars generically, but an undeclared key is invisible to the schema and to editors, so it still counts as missing).
16. **An environment variable should exist wherever it can.** Env is the secondary surface, needed for containers and secret injection, so add it unless the value genuinely cannot be expressed as a flat scalar (a list of mappings such as `routes:`/`headers:`/`expose:` is the legitimate exception; a scalar, a list of scalars, or a grouped block's child is not). Names follow the standard: yaml `<key>` is `APERIO_<KEY>`, a grouped `<group>.<child>` is `APERIO_<GROUP>_<CHILD>`, and `host`/`port`/`log_level` map to their bare names.
17. **Adding a setting means touching all of its surfaces in the same commit:** the yaml struct field (with a doc comment, since it becomes the schema description), the env read, the docs table in `docs/configuration.md`, and the reference table in `docs/book/aperio.tex`. A setting that reaches only one surface is incomplete work.

18. **Record every config-format change that can affect an existing file**, as an entry in `CONFIG_CHANGES` (`aperio-config/src/compat.rs`), in the same commit that makes the change. This is what lets a user upgrade blind: the binaries compare the `version:` a config file declares against their own build and report exactly what moved in between. An unrecorded change is a silent behavior change on someone's server.
    - **What counts:** a key renamed, removed, or given a new meaning; a default that changes what the file does; a value shape that stops being accepted; anything where a file written for the previous version now behaves differently. **Skip** purely additive changes (a new optional key, a new block spelling that leaves the old one working), those cannot break an existing file.
    - **Pick the severity by the nature of the harm, never by what the mechanism will do about it.** `Migration` = the old spelling still works and was translated for them, worth reviewing. `Breaking` = the file no longer does what it says, they must fix it. `Security` = the file claims a protection that no longer exists, so the operator believes something is gated that is not; the binary **refuses to start** until acknowledged. A removed credential is `Security` even though "a key was removed" sounds merely breaking, what matters is that someone is running exposed while believing otherwise.
    - **Set `applies` honestly too, because it is what makes the severity safe.** `WhenSet` = only a file that writes one of `fields` is affected, which is the case for a key that was removed or given a new meaning. `Always` = every file in the range, which is the case for a changed *default*, where the people affected are precisely the ones who never wrote the key. A `Security` entry must be `WhenSet` (a test enforces this): refusing the start of every server in the version range, affected or not, is the outage-generator failure mode.
    - Set `version` to the release the change ships in, name every affected key in `fields`, including both the flat and block spellings, and write `action` as the thing the operator should actually do. History before this mechanism is deliberately not reconstructed; do not backfill guesses.

## Protocol compatibility
23. **Backward compatibility on the tunnel protocol is the default, and breaking it is the user's decision, never yours.** A server is one box and its clients are a fleet, so the two sides are *always* upgraded at different times. Design every protocol change so an older peer keeps working: add optional fields rather than changing existing ones, keep the old spelling accepted alongside the new one, and negotiate a capability instead of assuming it.
    - **When a change genuinely cannot be made compatibly, stop and say so before writing it.** Not after, not in the summary at the end. Say plainly: "this cannot be done while preserving backward compatibility", what specifically breaks, which peer versions stop working, and what the compatible alternative would cost if there is one. Then wait. A break is sometimes the right answer, including when the old behavior is itself the bug, but it is a product decision with a fleet-wide upgrade behind it, and it belongs to the person who operates the fleet.
    - **If the break is approved, the incompatibility must be detected at connect time and refused there, with a message that names it.** The client announces its release version in the handshake, the server compares it against the range it supports, and a pairing outside that range is rejected with an error saying which side is too old and what to upgrade. The failure an operator must never get is a connection that establishes and then misbehaves somewhere deeper, where the cause is three layers away from the symptom. Refusing early is the whole point of having asked.
    - **A break is also a `CHANGELOG.md` entry and a `CONFIG_CHANGES` entry when it touches config**, both saying which versions can no longer talk to each other, and it bumps the protocol version.

## Language
5. Use **English** in all changes (code, comments, commit messages, docs).
20. **Never use the em dash (`, `).** Write a comma instead, or split the sentence. This applies everywhere: code comments, documentation, changelog entries, commit messages, UI strings and their translations. A parenthetical that a comma cannot carry is usually two sentences.

## Feature Planning
6. **GitHub Issues is the active feature backlog.** Record new feature ideas there; do not recreate `planned_features.md`.
7. **Before implementing an issue, inspect the archived plan at deletion commit `493a156`:** run `git show 493a156^:planned_features.md` and use it to recover any matching item's original scope and context.

## Changelog
9. **Always update `CHANGELOG.md` for any user-facing change**, as part of the same task and commit that makes the change (not a separate follow-up). Add an entry under a `## [Unreleased]` section, create that section at the top (above the latest released version) if it does not exist, following the existing Keep a Changelog style: group under `### Security` / `### Added` / `### Changed` / `### Fixed` / `### Removed`, and write a **bold lead-in sentence** followed by a short explanation, matching the voice of the entries already in the file.
10. **What counts as user-facing:** behavior, config/flags/env vars, API/endpoints, security fixes, CLI, defaults, or anything an operator/user would notice. **Skip** purely internal changes: issue metadata, CI/build-infra tweaks, test-only changes, and no-op refactors. If unsure whether a change is user-facing, add a changelog entry.
11. **Releases:** on a version bump, move the `## [Unreleased]` block to a new `## [x.y.z] - YYYY-MM-DD` heading (today's date) and bump the version in all three crate `Cargo.toml` files (`aperio-client`, `aperio-server`, `aperio-config`), `Cargo.lock`, and the book's title page (`\author{Version x.y.z}` in `docs/book/aperio.tex`). The release workflow refuses to build the guide when the book's version disagrees with the tag.
19. **Cutting a release includes a config audit over the whole cycle** (and rule 26 lists what to run before any of it). When asked to release a version, do everything in rule 11, and additionally verify `CONFIG_CHANGES` once against the entire range, `git diff <latest tag>..HEAD` over `aperio-config/src/lib.rs`, `aperio-client/src/config.rs`, `aperio-server/src/settings.rs` and `aperio-server/src/config_file.rs`, plus any new/changed `env::var` read. Rule 18 records these one change at a time, which is exactly the kind of thing that gets forgotten in the moment; a release is the last point where fixing it still costs nothing, so this is the second net, not a replacement for the first.
    - For every config-surface change in the range, decide against rule 18's "what counts" test whether it can alter how an existing file behaves. If it can and no `CONFIG_CHANGES` entry covers it, add one now, with the version being released.
    - **Correct the version on entries added during the cycle.** They were written before the release number was known, so an entry naming a guessed or placeholder version silently never fires, or fires for the wrong upgrade, check every entry newer than the last tag and set it to the version actually being cut.
    - **Report the result explicitly, including when it is empty.** Say what range was audited and what was found ("14 commits, 3 touched the config surface, none can affect an existing file"). A silent pass is indistinguishable from a skipped check, and this audit only has value if the user can tell it actually ran.

12. **A version section is only frozen once its git tag exists.** The topmost `## [x.y.z]` in `CHANGELOG.md` may be a version whose `vX.Y.Z` tag has *not* been created yet (versions are bumped in-repo before the release is tagged/pushed). If the latest version has **no matching git tag** (`git tag -l vX.Y.Z` is empty), keep adding new changelog entries **into that section**, do **not** open a new `## [Unreleased]` above it. Only once that tag exists is the version locked; then the next change starts a fresh `## [Unreleased]`.
    - **Mandatory check, run `git tag -l vX.Y.Z` immediately before writing EVERY changelog entry, for the topmost `## [x.y.z]`.** Never assume from an earlier check or a previous entry in the same session: tags can be created (by the user) between your commits, so a version that was untagged when you last looked may be frozen now. Empty output → add to that version's section; the tag exists → open/append a fresh `## [Unreleased]` above it. This check would have caught writing to a frozen `0.4.2` after its tag appeared mid-session.
